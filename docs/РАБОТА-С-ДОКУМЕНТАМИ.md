## 🔒🔒🔒🔒 ОБЯЗАТЕЛЬНОЕ ПРАВИЛО МОДЕЛИ — спеки/планы/концепты пишутся только самой мощной моделью

**Написание содержания** ЛЮБОЙ спеки (`docs/superpowers/specs/*.md`), ЛЮБОГО implementation plan
(`docs/superpowers/plans/*.md`) и ЛЮБОГО концепт-документа — ТОЛЬКО самой мощной моделью, доступной на
момент составления документа. На 2026-09-01 это Opus (Claude Opus 5, `model: "opus"` в Agent-инструменте) —
сверять заново при появлении более новых моделей, не консервировать конкретное имя навсегда.

**Введено 2026-09-01** после того, как спека BlackSea дошла до 6 раундов правок подряд на Sonnet — владелец
прямым текстом потребовал переписать документ целиком, используя самую мощную доступную модель, вместо
дальнейшего патчинга. Правило распространяется на ВСЕ будущие спеки/планы/концепты в проекте, не только на
этот инцидент.

**Как применять:** основной диалог с пользователем может идти на любой модели (это ограничение НЕ про то, кто
ведёт беседу) — но фактическое АВТОРСТВО содержания документа (первое написание с нуля, и любой раунд
переписывания «с нуля», не точечная правка формулировки) должно идти через `Agent`-инструмент с
`subagent_type` (не `fork` — форк наследует модель текущей сессии) и явным `model: "opus"` (или актуальным
эквивалентом самой мощной модели на момент составления). Точечные правки уже согласованного документа по
конкретным находкам ревью — не обязаны каждый раз идти через отдельного Opus-агента, если правки небольшие и
не меняют архитектуру; но при подозрении, что документ снова скатывается в раунды патчей (тот же триггер, что
и лимит 2 раунда выше) — следующий проход делать не патчем, а полным переписыванием на самой мощной модели,
не очередной точечной правкой.

## Стадия 0 — Scope Decomposition Gate (перед стадией 1, для СПЕК и ПЛАНОВ)

Прежде чем идти по стадиям 1-9 ниже, ответить: это ОДИН документ, или его нужно резать на части?

**Ориентировочный триггер (не механический — хука нет, проверять глазами при каждой правке):**
- документ превысил **300 строк**;
- документ реально смешивает **2 или более независимых задач/тикетов** (в BattleBot — независимых Beads-issues
  или независимых фич), а не растёт за счёт находок и правок одной и той же задачи.

Срабатывание триггера — не автоматический вердикт «дели документ», это сигнал остановиться и явно оценить,
показав оценку пользователю, прежде чем продолжать наполнять документ или представлять его готовым.
**Решение — делить или нет — принимается по СЛОЖНОСТИ И РАЗНОРОДНОСТИ конкретной спеки, не по голому числу
строк**: длинный, но однородный документ об одной задаче может законно остаться одним файлом даже сильно за
порогом; короткий, но разнородный (смешивающий независимые архитектурные слои или исполнителей) может
требовать разбиения даже не дойдя до 300 строк.

**Содержательный критерий:** «один функционал/одна связная задача, а не несколько разных частей». Рост
документа за счёт легитимных находок и правок ОДНОЙ и той же задачи — не повод резать, даже за 300 строк.
Повод резать — когда внутри одного документа реально смешаны разные архитектурные слои или независимые
исполнители: например данные/контракты vs поисковые алгоритмы/конкурентность, несколько независимых
writer'ов одной сущности, или буквально разные подсистемы продукта.

**Как резать, если решение — резать:** по границе домена/слоя сложности (не механически пополам по строкам)
— типичная граница: данные/контракты (enum, dict, сигнатуры, формулы без потребителя) в одну часть,
поисковые алгоритмы/конкурентность с несколькими взаимодействующими инвариантами — в отдельную; простая
часть реализуется и закрывается ПЕРВОЙ.

**Часть за частью, не пачкой:**
1. Написать ОДИН документ — следующий по очереди декомпозиции.
2. Представить его пользователю как черновик с явной просьбой ревью — НЕ как «готово». Собственная
   самопроверка (placeholder-скан, self-audit) — гигиенический минимум ДО показа, не замена одобрения
   пользователя. «0 багов при самопроверке» ≠ «пользователь согласен».
3. Дождаться явного одобрения ИЛИ правок → внести правки → снова дождаться одобрения.
4. Только ПОСЛЕ явного «да» — переходить к следующей части в очереди (даже если она уже физически написана
   в черновике).

Формулировка при показе — «вот часть A, посмотри, когда одобришь — перейду к B», никогда «часть A и часть B
готовы» одновременно.

### Лимит раундов правок ОДНОГО документа — явный, не оценочный

Оценочный критерий «остановиться, ЗАМЕТИВ проблему» ненадёжен ровно в момент, когда он нужен как тормоз —
подтверждено дважды в Nutrition (CKL, Banquet) и один раз уже здесь, в BattleBot (спека BlackSea, 4 раунда
подряд, 2026-09-01). Замена — счётчик, не суждение:

- Счётчик раундов правок ОДНОГО документа ведётся явно с раунда 1, показывается пользователю в каждом
  статусе («раунд 2 из …»).
- **По достижении раунда 2 — ОБЯЗАТЕЛЬНАЯ остановка через `AskUserQuestion`** (не фраза в тексте ответа —
  текстовое «предлагаю остановиться» слишком легко проскакивает в потоке непрерывного выполнения). Вопрос
  пользователю: декомпозировать / продолжить ещё один раунд осознанно / отдать решение пользователю.
- Это правило — только про повторные раунды правок НА ЭТАПЕ Design/Spec/Plan до утверждения, включая раунды,
  вызванные находками Stage 8 (External Agent Review) — рабочая находка Stage 8, требующая переписать
  контракт/инвариант, считается новым раундом этого же счётчика, не отдельным неограниченным циклом. Не
  путать с исполнением уже одобренного implementation plan в коде (там свой режим — fix-loop с ревью между
  раундами, не этот счётчик).

## Порядок стадий (обязательный, не переставлять и не пропускать)

```text
1. CONTEXT
2. CODE ARCHAEOLOGY
3. CONTRACT EXTRACTION
4. DESIGN
5. ADVERSARIAL REVIEW
6. TEST MATRIX
7. SELF-AUDIT
8. EXTERNAL AGENT REVIEW (узкий, адверсариальный — не открытое ревью содержания)
9. FINAL GATE
10. ONLY THEN USER REVIEW
```

### 1. Context

Перед проектированием обязательно прочитать: `CLAUDE.md`, `ANTI-PATTERNS.md`, `STATE.md`, релевантные
design/spec-документы, память (`MEMORY.md` + связанные записи) по затронутой подсистеме. Не начинать писать
решение, пока контекст не собран.

Вопрос объёма/декомпозиции (Стадия 0 выше) должен быть уже отвечен ДО начала проектирования — не откладывать
его на момент, когда документ уже разросся.

### 2. Code Archaeology

Найти 2-3 существующих реализации-аналога, **если такие существуют и действительно релевантны.** Если
релевантных аналогов нет — явно зафиксировать это в документе и исследовать ближайшие фундаментальные
механизмы вместо искусственного притягивания нерелевантного «похожего» кода ради галочки в чек-листе.

Для каждого найденного аналога проверить ФАКТИЧЕСКИЙ КОД: transaction boundaries, commit/rollback,
concurrency, retries, error handling, validation, idempotency, DB constraints, API calls, resource limits,
тесты. Нельзя писать «зеркалируем X, поэтому это безопасно», пока контракт X не проверен в коде лично.

**Отдельное обязательное условие для НОВОГО внешнего SDK/API/LLM-модели/третьей стороны** (не для уже
используемого в проекте кода — та практика уже есть): контракт должен быть извлечён и доказан живой
интроспекцией/реальным вызовом В ТЕКУЩЕЙ СЕССИИ. WebSearch/WebFetch документации или память о старой версии
API — гипотеза, не факт. Прямой прецедент в BattleBot: спека BlackSea строилась на живых `curl`/браузерных
вызовах реального API (см. `MEMORY/project_blacksea_sale_verification_recipe.md`), а не на документации
BlackSea (которая для нужного эндпоинта вообще не существовала) — это ровно то поведение, которое здесь
требуется как норма, не исключение.

**🔒🔒 Общее правило, из которого выведены оба требования этого раздела:** ни одно утверждение вида «сейчас X
делает Y», «существует Z», «паттерн X уже защищает от Y», «тест покрывает Z» не считается установленным, пока
соответствующий код/тест не открыт и не прочитан ЛИЧНО в ТЕКУЩЕЙ сессии — не по памяти о прошлой сессии и не
по факту, что предыдущий агент об этом отчитался (отчёт агента о коде — гипотеза до личной проверки, не
факт).

### 3. Contract Extraction

Для каждого существенного требования определить: `Requirement → Contract/Invariant → Enforcement mechanism →
Verification`. Формула одна и та же для SPEC и PLAN, разница только в том, чем именно является каждое звено.

**Для SPEC** enforcement mechanism может быть ЗАПЛАНИРОВАННЫМ — конкретное место/механизм, которым
предполагается обеспечить контракт (например «SQLAlchemy `UNIQUE(sale_id)` + `db.begin_nested()`»), и
verification описывает, КАК будет доказано выполнение (конкретный тест, который ещё предстоит написать).
Спека по определению описывает то, чего в коде ещё нет — правило «если только в prose — незакреплено» здесь
значит «если требование не имеет ни одного конкретного, называемого enforcement-механизма и способа
проверки», а не «если оно ещё не реализовано».

**Для PLAN** enforcement mechanism уже обязан быть привязан к конкретному изменению кода/БД (файл, функция,
constraint), а verification — к конкретному тесту по имени. План описывает УЖЕ принятые в спеке контракты как
факт кода, который предстоит написать — здесь расплывчатости не должно остаться вообще.

**В обоих случаях** требование, которое существует только как размытая проза без формального контракта и без
названного способа проверки — считается незакреплённым. Особенно проверять: ranges, enum values,
required/forbidden fields, uniqueness, ordering, nullability, transaction semantics, retry limits, concurrency
guarantees.

### 4. Design

До кода/плана определить: invariants, state transitions, ownership, failure modes, retry semantics,
concurrency model, idempotency, внешние side effects, resource budgets, recovery behaviour. Для каждого
внешнего вызова ответить: что если он (A) вернёт ошибку, (B) зависнет, (C) повторится, (D) выполнится дважды,
(E) выполнится частично, (F) будет вызван одновременно вторым worker'ом.

### 5. Adversarial Review — обязательно сломать собственное решение

После первого варианта — НЕ улучшать текст сразу. Отдельный проход с вопросом «как я могу это сломать»:
race condition, duplicate execution, partial failure, retry amplification, transaction boundary, crash между
операциями, malformed response (missing/extra field), duplicate/invalid index, empty input, boundary values
(0, огромный), повторный/конкурентный запуск, изменение данных между SELECT и UPDATE, исключение в середине
batch.

**Ключевое правило:** после КАЖДОГО найденного защитного механизма — обязательно спросить «а есть ли
контрпример, который обходит ИМЕННО эту защиту?». Не принимать один правдоподобный аргумент за доказательство
безопасности.

Для каждого применимого числового ограничения выбрать полный набор граничных и adversarial случаев — не
только нормальный сценарий. Если утверждается «максимум N запросов/начислений» — это нужно математически
доказать; если доказать нельзя, формулировка меняется, а не рационализируется.

Числовые лимиты — частный случай более общего правила: для ЛЮБОГО safety/correctness claim (не только
числового) построить минимум одну попытку минимального контрпримера, который нарушил бы это утверждение,
если бы механизм на самом деле был недостаточен — формула `claim → mechanism → bypass attempt → result`.

### 6. Test Matrix

Таблица `Invariant | Normal | Boundary | Failure | Concurrent | Recovery | Test` — до финализации. Каждый
важный invariant получает конкретный тест по имени. «Это покрывается существующими тестами» без указания
теста — не принимается.

### 7. Self-Audit

Отдельный проход, НЕ продолжение написания. Проверить независимо: requirements coverage, code/prose
consistency, DB correctness, transaction correctness, concurrency, retries/resource budgets, validation, error
handling, test completeness, scope creep. Специально искать требования, описанные словами, но не enforced
кодом — грепнуть собственный текст на `MUST/НЕ ДОЛЖЕН/ОБЯЗАН/РОВНО/ВСЕГДА/НИКОГДА/максимум/минимум/unique/
exactly/at most/at least/atomic/idempotent/concurrent-safe` и для каждого найденного места подтвердить
конкретный механизм в коде/БД/тесте.

Каждое найденное место обязательно триажить в одну из трёх категорий: (a) реальный contract/safety claim,
которому нужен enforcement-механизм; (b) обычная проза/цитата/пример кода, требованием не являющиеся;
(c) уже разобрано в другом месте документа. Только категория (a) требует доказанного enforcement-механизма ДО
прохождения Final Gate.

Для stateful-кода — построить state matrix явно (не только прозой): все состояния, переходы, и отдельно —
поведение при повторном запуске, crash, retry, конкурентных worker'ах A/B.

Любой новый автоматический/unattended/background worker (в BattleBot — в первую очередь: любой вебхук-
обработчик, любой long-poll/фоновый цикл) автоматически получает вопрос: «что будет, если два экземпляра
стартуют одновременно/два вебхука придут одновременно?» — проверить DB constraint/transaction/lock/atomic
claim/unique constraint/`SELECT→INSERT` race/`SELECT→network→UPDATE` race. Если эксклюзивность не
гарантирована — зафиксировать явно как риск/ограничение, не оставлять за пределами внимания.

### 8. External Agent Review — узкий, адверсариальный, не «оцени план»

**Применимость — по классу работы, не всегда автоматически** (`spike/bounded/architectural` из скила
`superpowers:brainstorming`). Диспатч агента стоит реальные токены/время; требовать его для КАЖДОГО документа
независимо от масштаба — не оправдано для маленькой задачи с низким риском. Для **architectural** и
**bounded** — по усмотрению Claude, не безусловно; для **bounded** пропуск допустим ТОЛЬКО если ВСЕ условия
одновременно выполнены: (1) затронуто ≤2 файлов; (2) не вводится новый внешний SDK/API/LLM-контракт;
(3) не затронуты concurrency/транзакции/множественные writer'ы/DB-миграция/деньги-биллинг-регуляторика;
(4) Claude лично прочитал и проверил ВЕСЬ затронутый существующий код. При пропуске — явно зафиксировать,
какие условия проверены и почему риск сочтён низким, не пропускать молча. **Spike** не производит spec/plan
документ, весь протокол к нему не применяется.

Задача агента — узкая и механическая, НЕ открытый вопрос «хороший ли план»: «Проверь документ ПРОТИВ
РЕАЛЬНОГО РЕПОЗИТОРИЯ. Ты ОБЯЗАН перед тем, как оценивать любое утверждение об уже существующем коде, тестах,
моделях/миграциях БД или референсных реализациях — открыть и прочитать соответствующий реальный код/тесты
сам; ревью документа в отрыве от кода недостаточно. Не доверяй утверждениям документа о существующем коде.
Попытайся доказать, что этот документ неверен. Ищи ТОЛЬКО: missed requirements, contradictions, race
conditions, transaction bugs, retry/resource bugs, validation gaps, missing tests, incorrect assumptions about
existing code, scope/decomposition errors. Для КАЖДОГО finding, основанного на утверждении о существующем
коде, указать конкретный файл/символ, который ты реально открыл и прочитал — вывод без указания на реальный
код не принимается. Не предлагай косметические улучшения, если они не влияют на correctness.» Если агент не
может получить доступ к релевантному контексту репозитория — ревью считается НЕ ВЫПОЛНЕННЫМ, а не
«выполненным с оговоркой».

После агента: каждый finding проверяется по РЕАЛЬНОМУ коду лично, не принимается автоматически. «Агент
сказал OK» — не доказательство. Исправить реальные находки. Для ЛЮБОЙ находки, затрагивающей contract,
invariant, state transition, concurrency, retry/resource budget или scope — повторить Adversarial Review →
Test Matrix → Self-Audit (шаги 5-7) не только на изменённых строках, а на всём ЗАТРОНУТОМ фиксом участке И на
его зависимостях.

**Лимит на диспатч:** если агент возвращает промежуточный статус («жду», «in progress») вместо законченного
отчёта с findings — максимум ОДНО повторное возобновление с явным требованием отчёта в этом же ответе; если и
оно не дало финального отчёта — остановить, сообщить пользователю факт зависания, не диспатчить третий раз
молча в надежде, что сработает само.

### 9. Final Gate

Документ НЕЛЬЗЯ показывать пользователю, если: есть непроверенное утверждение о существующем коде; safety
claim не имеет доказательства/контрпримера; concurrency semantics не проверены для автоматического воркера;
retry budget не проверен контрпримером; важное требование существует только в prose; критический invariant не
имеет теста (для SPEC — не имеет названного ПЛАНИРУЕМОГО теста по шагу 3; для PLAN — не имеет теста по имени,
привязанного к конкретному коду); Stage 8 пропущен без явной фиксации в документе/сессии, какие условия
проверены и почему риск сочтён приемлемым; внешний reviewer (если он был) нашёл finding, затрагивающий
correctness, safety, data integrity, concurrency, retry/resource budget, contract или test completeness,
который не исправлен и не разобран явно с письменным обоснованием принятия.

**Дополнительный обязательный gate для PLAN, если у него есть исходная SPEC — SPEC→PLAN consistency check.**
Граница spec→plan — самое частое место провала, поэтому это отдельный, не подразумеваемый шаг:

- каждый invariant спеки покрыт планом (указать, каким именно task'ом);
- ни один обязательный контракт спеки не потерян и не ослаблен планом;
- ни один плановый шаг не противоречит спеке;
- каждый acceptance criterion спеки имеет implementation/test path в плане;
- план не добавляет изменения вне scope спеки без явного зафиксированного решения;
- state transitions, failure semantics, concurrency и resource budgets в плане совпадают со спекой, а не
  переизобретены заново.

План, который внутренне непротиворечив сам по себе, но не прошёл этот check против своей спеки — не готов.

### 10. User Review

Только после прохождения 1-9. Пользователь НЕ является частью QA pipeline — его ревью должно быть
архитектурным/продуктовым, не поиском базовых ошибок реализации, которые можно было найти чтением
собственного кода.

---

## Кто пишет и ревьюит содержание

**Авторство и ревью СОДЕРЖАНИЯ спек/планов — исключительно сам Claude в основном диалоге с пользователем, без
делегирования субагентам.** Ни `writing-plans`-скилу в режиме «напиши за меня», ни независимому
ревьюеру-агенту на открытую проверку «хороший ли план» — это НЕ покрывается узким Stage 8 (External Agent
Review), который специально ограничен адверсариальным поиском конкретных багов, а не открытым содержательным
ревью. Финальный ревьюер документа — сам пользователь, не промежуточный агент.

Более высокая планка self-review: каждое фактическое утверждение о коде (существование поля/функции/
прецедента, поведение пайплайна) проверяется чтением кода ДО того, как попадает в документ, а не по памяти/
правдоподобности формулировки; каждое архитектурное решение проигрывается в голове на «что сломается», не
только happy path — это именно то, что формализовано стадиями 1-9 выше.

Это НЕ распространяется на другую работу — реализацию кода через SDD/TDD, рутинные задачи, парсинг логов и
т.п. — ограничение узко про содержание спек/планов/документации.

---

## Как показывать документ пользователю — молча вычитанным, не с историей опечаток

Финальная техническая полировка (опечатки, несостыковки формулировок, забытые обновления после правки текста,
битые внутренние ссылки, смешение алфавитов и т.п.) выполняется МОЛЧА, в фоне, до реально чистого состояния —
без построчного репортажа «нашёл X — исправил X» в ответе пользователю. Показывать — путь к готовому
документу и, при необходимости, ОДНУ строку итога («вычитал, готово»), не список из шести пунктов правок.

**Это ТОЧЕЧНОЕ исключение из общего правила «писать что делаю перед действием»** (`MEMORY/feedback_always_report_activity.md`),
не его отмена. Базовое правило остаётся в силе для всего остального: содержательные архитектурные решения,
что именно делается и зачем на уровне задачи, любые находки, которые меняют СУТЬ документа (не орфографию) —
по прежнему проговариваются вслух пошагово. Разница — именно в мелкой технической полировке уже
согласованного по сути документа. Найденная в ходе полировки СОДЕРЖАТЕЛЬНАЯ проблема (не опечатка, а реальный
пробел в логике) — не подпадает под тихую полировку, это полноценная находка, о которой сообщается как
обычно.

---

## Spec vs Plan — разделены жёстче

**Спека отвечает: что должно быть истинно?** Invariants, contracts, states, boundaries, failure semantics,
concurrency, resource limits, acceptance criteria.

**План отвечает: как именно изменить код, чтобы эти свойства стали истинными?** Каждый шаг плана — не
«добавить эндпоинт и тесты», а явная цепочка:

```text
Invariant / requirement
    ↓
Existing code (что уже есть)
    ↓
Change (что именно меняется)
    ↓
Test proving the change (какой тест доказывает, что требование теперь выполнено)
```

---

## Золотые правила (короткая форма для быстрой сверки)

1. **Не доверяй собственному выводу. Докажи его кодом, тестом и контрпримером.**
2. **Пользователь не должен находить ошибки, которые можно было обнаружить чтением уже доступного кода,
   построением state matrix, worst-case analysis или простым контрпримером.**
3. Если после N раундов ревью обнаруживаются ошибки ОДНОГО И ТОГО ЖЕ класса — проблема не решается ещё одним
   чек-листом. Меняется процесс (этот документ), не усердие.
4. Обнаружение проблемы ≠ исправление проблемы. Не объявлять весь класс проблемы закрытым, найдя один кусок
   механизма.
5. **SPEC → PLAN — отдельная граница корректности.** Нельзя предполагать, что корректная SPEC автоматически
   породит корректный PLAN. Каждый PLAN обязан доказать покрытие SPEC (Final Gate, SPEC→PLAN consistency
   check), а после ЛЮБОГО изменения PLAN его соответствие SPEC проверяется заново, не считается устоявшимся
   фактом.
