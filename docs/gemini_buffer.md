## 🐲 Релиз v1.8.5 — «Древний» полностью в проде, OCR-фиксы, G/S/M
> Дата: 2026-06-23 | Версия клиента: 1.8.5 (релиз выпущен) | Веб: задеплоено | Сервер: задеплоено на GCP

### Сделано
1. **«Древний» (Часть A) запущен полностью** — калькулятор нормы (Стратегия А/Б) в личном
   кабинете `/dashboard/ancients`, `tournament_reader.py` встроен в GUI бота новой вкладкой
   (Light/Full переключатель, Старт/Стоп), backend импорта турнирной таблицы. Реализовано
   subagent-driven-development, 6 задач + ревью на каждой.
2. **Серия OCR-фиксов по живым тестам владельца на реальной игре**: отключён словарь
   Tesseract (ломал даже простые латинские имена), LIGHT/FULL языковой сплит (как у Сундуков —
   полный набор скриптов одновременно путает Tesseract сильнее, не только медленнее),
   фиксированный порог 90 стирает ВИП-значок до OCR (главная причина мусорных хвостов в
   именах), исправлены 2 краша (Unicode-символ вне кодировки консоли, рассинхрон размеров
   кадра в `matchTemplate`). **Confidence-based выбор кандидата с adaptive-threshold
   эскалацией — попробовано по внешней рекомендации и откачено**: Tesseract уверенно читает
   мусор не реже, чем текст, эскалация перебивала верное имя более «уверенным» мусором.
3. **Fuzzy-match имён** (`difflib`, cutoff 0.75) сверяет сырое турнирное имя с уже
   подтверждёнными алиасами Сундуков того же клана — чистит хвостовой мусор у иначе верно
   прочитанных имён. Не решает межалфавитную путаницу (кириллица читается как латиница
   целиком) — транслитерацию осознанно не делали, риск ложного совпадения с другим игроком.
4. **Уровни войск переименованы в игровой формат G/S/M** («Состав»: `G8 S8 M9` вместо
   «Шаг 8.1») по полной таблице переходов от Gemini — старые лейблы были непонятны лидерам.
5. **Always-on-top бота теперь включён по умолчанию.**

### В долг (следующая сессия)
- Ползунок порога fuzzy-match + кнопка «Отменить» построчно.
- Условное форматирование недобора квоты (3 градации, пороги от лидера) — нужна логика для
  Стратегии А, у неё нет персональной квоты на игрока, только общая на роль.
- Выделить цветом «полные» составы (G8 S8 M8 и т.п.) в списке «Состав» — список монотонный.

## 🔧 Релиз v1.8.4 — архив сундуков, РОЙ без лишних запросов, тюнинг «Открыть»
> Дата: 2026-06-23 | Версия клиента: 1.8.4 (релиз выпущен) | Веб: задеплоено напрямую | Сервер: задеплоено на GCP

   клана автоматически архивируется (снимок итогов + целей), сырые записи `Chest` удаляются,

   калиброванной точке + тюнинг-офсету `chest_collect`.
4. Фикс бага интерфейса: вкладка Сундуки→Калибровка не переключалась напрямую.
5. Публичная страница сундуков: закреплённая шапка+левая колонка (`overflow-y: clip`),

   рангового топ-3-градиента.

## 🔧 Сундуки — OCR-конвейер имени игрока + раскраска публичной страницы
> Дата: 2026-06-23 | Версия клиента: 1.8.3 (релиз выпущен) | Веб: задеплоено напрямую

### Контекст
Владелец нашёл реального игрока со стилизованным именем (диакритика, тип «Marisha»),
который распознавался как «M A R I S H A» или хуже. По цепочке Claude↔Gemini (см.
`docs/Входящие_Gemini.md`) выявлены и устранены три причины:
1. `chest_reader.py`/`navigator.py` хардкодили путь к Tesseract дев-машины — на клиентских
   сборках портативный `tesseract_bin` не использовался для этих модулей вообще.
2. `clean_name()` имел деструктивный цикл, съедавший хвостовые одиночные буквы у имён,
   разнесённых пробелами OCR'ом.
3. Отсутствовал режим буквального чтения (без автокоррекции в словарные слова).

### Что сделано
- **v1.8.2**: новый `tesseract_setup.py` (frozen/dev-детекция пути), безопасный `clean_name`
  (режет только цифровые хвосты), `read_sender_name()` получил `script/Latin` + отключённые
  словари Tesseract. `read_chest_type()` не тронут.
- **v1.8.3**: полное покрытие 19 языков бота (кириллица/арабский/японский/китайский×2/корейский).
  Живой замер: Full-набор ×2.5 медленнее Light (1.0с vs 0.39с на сундук) — добавлен GUI-тумблер
  Light/Full (по умолчанию Light), не переведён на 19 языков интерфейса намеренно.
- Публичная страница `/chests/:slug`: раскраска «зелёный при выполнении обеих целей сезона»
  теперь работает для любого игрока, не только топ-3 (был баг — топ-3-only ограничение). Топ-3
  при выполнении целей получили переливающийся градиент (оранжевый→фиолетовый→синий) только на
  имени игрока (после двух неудачных попыток: на весь ряд — нечитаемо тёмно; на `<td>` напрямую —
  текст становился невидимым из-за конфликта с фоном sticky-колонки, см. ANTI-PATTERNS.md).
- Попытка закрепить шапку таблицы по типу Excel (прилипает к окну, страница скроллится без
  ограничения высоты) — реализована технически рабочим решением, но владелец откатил по
  визуальным ощущениям без детальной причины. Отложено на следующую сессию.

## 🔧 Сундуки Фаза 4 — Личный кабинет, per-clan очки (заменяет Фазы 2/3a)
> Дата: 2026-06-21 | Версия клиента: без изменений — backend+web, релиз бота не требуется

### Контекст
Фаза 3a (резолв родного языка через обратный словарь) оказалась тупиком на живых данных
(см. предыдущую запись буфера) — владелец вводил сленг, система не могла угадать английский
ID. Gemini предложил жёсткую архитектуру: явный выбор сундука из dropdown вместо угадывания
текста, плюс очки/паттерн делает каждый клан сам через личный кабинет, а не владелец через
Google Sheets.

### Что сделано
- Глобальный `ChestTypeCatalog` (очки по pattern, общий на всех) заменён per-collector
  `ChestConfiguration` (`catalog_id, custom_name, points, is_in_pattern`).
- `ChestTypeAlias` упрощён до `raw_type→catalog_id`, без резолва текста вообще.
- Новый `server/chest_dashboard.py`: 5 эндпоинтов под обычной сессией пользователя
  (`GET/POST /web/dashboard/chests`, `.../rows`, `.../management-token`, `.../claim`,
  `PATCH .../{slug}/language`) — самообслуживание без Sheets/ADMIN_TOKEN.
- `/dashboard/chests` (личный кабинет) + `/chests/:slug` (публичная, без логина — заменяет
  отклонённую идею автогенерации Google Sheet, у сервис-аккаунта нулевая квота Drive).
- Alembic-миграция с бэкфиллом — T9-очки 229/BERS перенесены без потерь (18 строк,
  подтверждено `psql` на проде после деплоя).
- TDD subagent-driven (4 задачи), все ревью + финальный whole-branch review.

### Два бага найдены и исправлены после деплоя (живой прогон поймал оба)
1. `POST /rows` — только upsert, не удалял отсутствующие строки (расходилось с
   «full-replace» из спеки). Исправлено.
2. `chest_dashboard.py` — неверный префикс роутера (`/api/v1/web/...` вместо `/web/...`,
   как у всех остальных user-facing эндпоинтов). Личный кабинет вечно показывал «...» без
   ошибки. Исправлено + добавлен try/catch, чтобы будущие сбои не были молчаливыми.

### Что осталось
- **Визуальный редизайн** `/dashboard/chests` и `/chests/:slug` — явно запрошено владельцем,
  сейчас функционально, но «2000-е» по виду. Следующая сессия.
- Player Aliases (имена игроков) — самообслуживание не входило в ТЗ, остаётся Sheets.
- `management_token` без срока действия — принятый компромисс из ТЗ.

## 🔧 Сундуки Фаза 3a — резолв алиасов по родному языку клана (Gemini-предложение реализовано)
> Дата: 2026-06-20 | Версия клиента: без изменений (1.8.1) — backend+скрипты, релиз не требуется

### Что сделано
- Реализовано предложение Gemini из этого буфера (см. ниже архив): админ пишет в «Chest Aliases»
  ТОЛЬКО на родном языке клана, `POST /api/v1/chests/aliases/import` сам резолвит в английский
  ID через обратный поиск по `chest_localizations` (язык коллектора), с fallback на литерал если
  текст уже английский (обратная совместимость со старыми ручными записями).
- Fail-fast: если хоть одна строка не резолвится — вся синхронизация блокируется целиком, ошибка
  называет ВСЕ проблемные строки сразу, без частичной записи в БД.
- TDD subagent-driven (2 задачи), оба ревью + финальный whole-branch review чисто (только Minor).
  Задеплоено на GCP (`edb9799`+`366e59f`), сервис active.
- Источник правды: `docs/superpowers/specs/2026-06-20-chest-alias-language-resolution-design.md`.

### Живой прогон — грабли и уроки
- **Sheet ≠ БД.** Владелец отредактировал «Localizations» прямо в Google Sheet и ожидал, что
  резолв сразу заработает — но без явного запуска `sync_catalog_to_db.py` сервер о правке не
  знает. Нужно явно проговаривать порядок: Sheet → sync-скрипт → БД → только потом второй sync.
- **Наполнение словаря «Localizations» — ручная работа, не автоматика.** Владелец ожидал, что
  программа сама переведёт русский текст на английский («это должна делать программа, а не ты
  руками!») — это никогда не было так задумано: словарь наполняется один раз вручную (Claude по
  эталонному списку 138 названий), резолв на чтении использует уже готовый словарь. Важно
  объяснять это явно и заранее, не после фрустрации.
- **Конфликт одновременного редактирования.** Владелец и Claude правили один Google Sheet
  («Localizations») одновременно вручную — данные сбивались (стёртый RU-текст, дубли,
  потерянные строки). Договорились: «Localizations» правит только Claude по запросу в чате;
  владелец правит только «Chest Aliases» (свой клан, родной язык).
- Из 27 сырых сундуков клана 229/BERS переведено 13 (Common/Elven Citadel/Arena/Epic
  Ancient/Merc Exc/Jormungandr Shop/Heroic 45), 14 остались неразрешёнными — либо неоднозначны
  (уровень банка, цвет богатства клана, какой эпический монстр), либо отсутствуют в справочнике
  138 (возможно контент новее справочника: Алхимия, Сакура изобилия, Инфернальный сундук, сундуки
  майя/гарпий/жреца/дракона) — ждут уточнения владельцем.

### Что осталось
- 14 неразрешённых сундуков 229/BERS — владелец уточняет английские названия или временно
  отключает (колонка C = «Нет»).
- Каталог очков «Chest Catalog» — паттерны T5-T8 остаются пустыми, T9 заполнен (18 типов).
- Публичная страница `/chests/{slug}` — брейнсторм начат, не завершён (решено: без логина).

## 🔧 Сессия после Хангофа #100 — Сундуки: алиасы через Google Sheets + каталог очков/паттернов (Фаза 2)
> Дата: 2026-06-20 | Версия клиента: без изменений (1.8.1) — вся работа сессии backend+скрипты, релиз не требуется

### Что сделано
- **Алиасы на чтении** (не на записи): `summary` теперь делает LEFT JOIN + COALESCE на
  `PlayerAlias`/`ChestTypeAlias` — новый алиас мгновенно правит всю историю без переимпорта.
  `POST /api/v1/chests/aliases/import` (Bearer ADMIN_TOKEN, full-replace DELETE+INSERT).
- **Admin Sheet**: листы «Player Aliases»/«Chest Aliases» в том же Sheet, что и сводка.
  `sync_admin_sheet_to_db.py` (локально, не на GCP) читает листы → шлёт в эндпойнт.
- **Фаза 2 — глобальный каталог очков** (архитектура «English is the Core», предложение Gemini):
  `ChestTypeAlias.canonical_type` — английское имя из эталонного списка 138 сундуков (не язык
  клана — боты работают на 20+ языках). `ChestCollector.pattern`/`language` — константы НА КЛАН.
  Две глобальные таблицы `chest_type_catalog` (очки) и `chest_localizations` (перевод),
  админ-эндпойнты `POST /catalog/import` / `POST /localizations/import`.
- `GET /summary/{slug}`: если у коллектора задан `pattern` → INNER JOIN с каталогом, сундуки не
  из каталога **полностью исключаются** (не в очки, не в счётчик); без pattern — старое поведение.
- Все TDD subagent-driven, все ревью + whole-branch review чисто (2 minor-фикса). Живой прогон на
  реальных данных (коллектор 229/BERS): 1 алиас добавлен через Sheet → мгновенно отразился в
  summary с очками.
- Источники правды: `docs/superpowers/specs/2026-06-20-chest-aliases-admin-sheet-design.md`,
  `docs/superpowers/specs/2026-06-20-chest-catalog-points-localization-design.md`.

### Известное ограничение
Реальные очки видны только для сундуков с уже прописанным алиасом raw→English (сейчас 1 из 18) —
владельцу нужно заполнить оставшиеся ~17 типов в листе «Chest Aliases».

### Что осталось / следующий шаг
- Публичная веб-страница `total-hunter.com/chests/{slug}` — переиспользует уже готовый GET-эндпойнт.
  Решено: страница **полностью публичная, без логина на сайте** (slug = право доступа, как сейчас
  у backend). Брейнсторм начат, дизайн не зафиксирован — продолжить в следующей сессии.
- Вне рамок (Фаза 3): тайм-ивенты (Древний и др.) + норма урона по весам — см. память

### 🔴 КРИТИЧЕСКИЕ ПРОБЛЕМЫ

#### 1. SPA без SSR/prerender на живом билде

**Симптом:** `vercel.json` → все маршруты уходят в `/index.html`. Googlebot (в т.ч. mobile crawler Googlebot-Mobile) получает **пустой HTML**, потом должен исполнить JavaScript.

**Состояние:** `prerender.mjs` был написан в Хангофе #69, но в `vite.config.js` нет ни `vite-plugin-prerender`, ни вызова prerender.mjs в build-шаге. Нужно проверить `package.json → scripts.build` — включён ли `node prerender.mjs` в пайплайн.

**Последствие:** Если prerender не запускается при каждом `vite build`, то на продакшене Googlebot видит скелет без контента. Это **главная причина** неполной индексации. На мобиле особенно критично — Google Mobile-First Indexing.

**Что проверить:**
```bash
# В web/package.json → "build": "vite build && node prerender.mjs" ?
# Или есть vercel.json → buildCommand ?
```

#### 2. Версия `v1.2.2` в CTA на лендинге

**Файл:** `web/src/pages/LandingPage.jsx`, строка 323
```jsx
v1.2.2 · Windows 10/11 · 64-bit
```

**Текущая версия: v1.6.9.** Эта строка видна Google при индексации и пользователям. Создаёт недоверие.

## 🚀 ХАНГОФ #71 — Ghost YOLO + v1.5.8
> Дата: 2026-05-27 | Версия: 1.5.8 | Статус: ВЫПУЩЕН ✅

### Что сделано

**Баг:** Бот после рестарта (обнаружение биржи → 10с пауза → новый старт) двигался в 2x быстрее.

**Корневая причина:** YOLO inference занимает ~1.0с на CPU. `move_wait=0.5с`. Нормальный цикл: sleep(0.01) + YOLO(1.0s) + nav(0.05s) = 1.06s. С блокированной YOLO: sleep(0.01) + sleep(0.45s) + nav(0.05s) = 0.51s = 2x быстрее. Диагностика через лог: ratio 1.059/0.531 = 2.000x.

**Решение — Ghost YOLO (Призрак YOLO):**
- `_last_yolo_inference_time = 1.0` — хранить время последнего реального YOLO
- Когда YOLO заблокирована: `time.sleep(_last_yolo_inference_time)` — симулировать нагрузку
- `_initial_yolo_block_sec = 5.0` при programmatic restart (достаточно чтобы уйти от биржи)

**Дополнительно:**
- `if not self.is_running: break` перед `joystick.step()` — лишний шаг после стопа
- Пауза Step 7 (ожидание диалога): 0.5с → 1.0с (медленные ПК)
- 28 тестов зелёных

**Антипаттерн добавлен в ANTI-PATTERNS.md:** Spatial filter (позиционный cooldown) = День Сурка.

### BUG-1 🔴 ЗНАЧИМЫЙ — `/link/verify`: приглашённый не получает +50 если пригласитель забанен

**Файл:** `server/web_routes.py`, строки 433–444

**Что происходит:**
```python
# ТЕКУЩИЙ КОД (неправильно):
if referrer and not referrer.is_banned:
    web_user.ref_credits += 50      # ← оба начисления внутри одного if

    db.add(Transaction(..., amount=100, meta={"role": "inviter"}))
web_user.ref_bonus_claimed = True   # ← выставляется в любом случае
```
Если пригласитель забанен → приглашённый НЕ получает свои 50 ref_credits. При этом `ref_bonus_claimed=True` выставляется безвозвратно — шанс утерян навсегда.

**Что должно быть:**
```python
# ПРАВИЛЬНО:
web_user.ref_credits += 50         # +50 invited — безусловно
db.add(Transaction(..., amount=50, meta={"role": "invited"}))
if not referrer.is_banned:
    referrer.ref_credits += 100    # +100 inviter — только если не забанен
    db.add(Transaction(..., amount=100, meta={"role": "inviter"}))
```

**Расхождение:** В `/referral/activate` (строки 590–597) логика УЖЕ правильная — +50 приглашённому безусловно, +100 пригласителю только если не забанен. Нужно привести `/link/verify` к тому же поведению.

### BUG-2 🟡 НИЗКИЙ — Возможны циклические реферальные цепочки в БД

**Файл:** `server/web_routes.py`, `/referral/activate`

**Что происходит:** Нет проверки на цикл при активации кода. Если A пригласил B, B пригласил C, C активирует код A — получается цепочка C→A→B→C. В каскаде покупки это ограничено 3 итерациями (не infinite loop), но семантически неправильно: A зарабатывает от своего же реферала C.

**Исправление:** При `/referral/activate` пройтись вверх по цепочке `inviter.invited_by_id` (до 3 шагов) и убедиться, что `web_user.id` не встречается.

**Реальный риск:** НИЗКИЙ — каскад ограничен 3 уровнями, infinite loop невозможен. Но злоупотребление теоретически возможно в кольцах из 3 пользователей.
