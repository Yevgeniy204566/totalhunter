Перепроверил. **В целом архитектура правильная, но в текущем виде я бы ещё НЕ утверждал спеку. Есть несколько конкретных дыр, две из них критические для корректности.**

### 1. Критическая ошибка в SQL CKL

Сейчас написано:

```sql
WHERE ingredient_a_id IN (...)
   OR ingredient_b_id IN (...)
   AND evidence_co_occurrence_count >= min_co_occurrence
```

Из-за приоритета `AND` это означает:

```sql
A IN (...)
OR (B IN (...) AND count >= ...)
```

То есть строки, где ингредиент находится в `ingredient_a_id`, пройдут **без проверки `min_co_occurrence`**.

Должно быть:

```sql
WHERE (
    ingredient_a_id IN (...)
    OR ingredient_b_id IN (...)
)
AND evidence_co_occurrence_count >= :min_co_occurrence
ORDER BY evidence_lift DESC
LIMIT :top_n
```

Это обязательно исправить и добавить отдельный тест на обе стороны пары.

---

### 2. Критическая архитектурная несостыковка `max_candidates` vs quotas

В §0 говорится:

> верхний предел `max_candidates`

Но в фактическом контракте:

```python
retrieve_candidates(..., quotas: RetrievalQuotas)
```

и далее:

> итоговый размер ≤ сумма квот.

То есть **`max_candidates` фактически исчез**.

Получается:

```text
max_candidates = 100
quota passport = 100
quota CKL = 100
quota vector = 100
```

→ результат потенциально 300.

Это противоречит первоначальной цели Candidate Retrieval — гарантировать ограниченный пул.

Нужно выбрать одну модель. Я бы здесь выбрал:

```text
RetrievalQuotas
    ↓
каналы получают свои квоты
    ↓
union/dedup
    ↓
GLOBAL max_candidates
    ↓
Candidate Pool
```

То есть нужны **и квоты каналов, и глобальный потолок**.

Причём это как раз решает твою исходную проблему масштабирования.

### 3. Есть ещё одна существенная дыра: `LayerStrictness`

Ты пишешь:

> Passport-канал использует существующую градацию `LayerStrictness`

Но функция:

```python
retrieve_by_passport_priority(
    pool,
    current,
    top_n,
)
```

**не получает `LayerStrictness`**.

Если существующая логика действительно зависит от `STRICT/WARN/EXPERIMENTAL`, нужно явно определить, откуда Retrieval узнаёт текущий режим строгости.

Иначе фраза:

> «переиспользует уже существующую градацию»

пока не является реализуемым контрактом.

Это легко исправляется добавлением соответствующей зависимости/параметра, если она действительно нужна именно для ranking. Но **не надо придумывать новый механизм** — нужно точно привязаться к существующему API.

---

### 4. Claim `O(|pool|)` для CKL требует аккуратности

CKL-запрос действительно может быть **одним SQL-запросом**, но затем:

> «фильтрует `pool` до рецептов, содержащих хотя бы один из них как MAIN»

Если для каждого Recipe отдельно сканировать его ингредиенты, стоимость уже не просто `O(|pool|)`, а зависит от количества ингредиентов в рецептах.

Это не проблема само по себе — количество ингредиентов обычно небольшое, — но утверждение в §4 лучше сделать честнее:

> **без N+1; стоимость линейна относительно размера входного пула и числа ингредиентных позиций в нём.**

Не надо обещать строгий `O(|pool|)`, если реализация фактически смотрит вложенные ингредиенты.

---

### 5. Важный вопрос с пустым `current`

Вот здесь я согласен с логикой:

```text
current = []
passport → работает
CKL → []
vector → []
```

Но тогда первый ход определяется **только passport retrieval**.

Это допустимо, **если это сознательное решение**. Но поскольку Retrieval является универсальным механизмом, стоит явно написать:

> На первом ходе, когда `current` пуст, Retrieval не пытается искусственно создавать CKL/vector candidates; стартовый Candidate Pool формируется доступными context-free каналами и структурным входным пулом.

Иначе при маленькой passport-квоте первый ход может получить слишком мало кандидатов.

### 6. Есть небольшая терминологическая проблема с `max_candidates`

В §0:

> «верхний предел размера пула (`max_candidates`, параметр)»

А потом:

> «конкретное число `max_candidates` и точный алгоритм квотирования ... решается в Adversarial Review».

Это нормально.

Но тогда **не называй `max_candidates` одновременно параметром входа и не передавай его в сигнатуре**, если реально он является свойством `RetrievalQuotas`.

Лучше сделать:

```python
@dataclass(frozen=True)
class RetrievalQuotas:
    passport: int
    ckl: int
    vector_similar: int
    vector_dissimilar: int
    max_candidates: int
```

Тогда весь контракт находится в одном объекте конфигурации.

## Что в остальном мне нравится

Особенно правильно:

**Retrieval не возвращает score.**

Это очень важная граница:

```text
Retrieval
   ↓
«вот кандидаты, которые стоит рассмотреть»

Solver
   ↓
«какой ход выбрать»

Composition Engine
   ↓
«насколько хороша получившаяся композиция»
```

И правильное решение с vector:

```text
similar TOP-K
+
dissimilar TOP-K
```

а не попытка заранее решить, что «похожее хорошо» или «разное хорошо».

Также правильно, что **structural filter пока остаётся выше Retrieval**. Не надо смешивать две перестройки.

## Мой вердикт

**Не отклоняю — архитектура хорошая и практически готова. Но перед утверждением обязательно исправить:**

1. **SQL-скобки вокруг `A OR B` + тест обеих сторон.**
2. **Вернуть глобальный `max_candidates` в реальный контракт**, поверх channel quotas.
3. **Разрешить несостыковку с `LayerStrictness`** — откуда он берётся в `retrieve_by_passport_priority`.
4. Ослабить слишком жёсткий claim `O(|pool|)` для CKL.
5. Явно зафиксировать семантику первого хода при `current=[]`.

После этих пяти правок **спеку можно утверждать**. Сам принцип — **однозначно правильный**: сначала дешёвое сужение пространства, потом единый Solver, потом полная композиционная оценка.
