## 2026-07-09, 21:35 — РЕШЕНО: 4-я первопричина «Сервер недоступен» найдена, релиз v1.8.12 выпущен

Продолжение темы, которую разбирали в сессиях #121/#122 (TZ-баг дедупликации, nginx client_max_body_size). Владелец сообщил тот же симптом — первая отправка сундуков падает, вторая проходит — и явно попросил не патчить симптом ещё раз, а сделать выгрузку железно надёжной.

Запустили те же 2 независимых агента (клиент vs сервер), что и в прошлые разы. На этот раз причина оказалась куда проще предыдущих:

**Сервер никогда не отказывал.** `nginx access.log` показал: `499` (клиент сам оборвал соединение) и `200 OK` от uvicorn на том же запросе секундой позже. Клиентский `chest_reader.py` использовал `requests.post(..., timeout=10)` без единой попытки повтора — на e2-micro под случайной нагрузкой (в моменте было 225Мб свободного RAM + 337Мб в swap, один uvicorn-воркер) обработка батча иногда чуть превышала 10 сек, бот обрывал соединение и показывал ошибку, хотя сервер доваривал импорт мгновением позже.

**Фикс:** таймаут 45 сек, один безусловный автоповтор (без бэкоффа — безопасно благодаря уже рабочей TZ-нормализованной дедупликации из сессии #121), плюс логирование реальной причины сбоя через уже существующий `log_error_to_server()` — чтобы при 5-м повторе этой жалобы не поднимать логи GCP с нуля.

**Побочная находка:** nginx `proxy_pass http://localhost:8000` резолвился и в IPv4 и в IPv6, uvicorn слушает только IPv4 → 305 случайных `Connection refused` на `[::1]:8000` за сутки, в основном на `/vault/sync`/`/roy/pool`. Исправлено на `http://127.0.0.1:8000`, подтверждено — 0 таких ошибок после reload.

Релиз v1.8.12 выпущен и разошёлся (GitHub Release + сервер). TDD, 49/49 тестов. Подробности — `STATE.md` Сессия #123, `ANTI-PATTERNS.md` (2 новых раздела).

## [NUTRITION] 2026-07-21, 12:10 — Живая приёмка T10 конвейера pipeline-v2: находки и открытая проблема

Эпик pipeline-v2 (T1–T9) завершён и прореревьюен (407 тестов), ветка `pipeline-v2`. Сегодня — T10, живая приёмка вместе с пользователем: перепрогон старой партии + новый краул + прогон через очереди «Матчи»/«Веса» в админке. По ходу нашли и почти сразу же чиним несколько системных проблем.

### 1. Перепрогон подтвердил главный тезис эпика
29 записей 2026-07-19 (в v1 проходило 2/29 — «безжалостный сброс» ронял рецепт на первом же непонятном ингредиенте). После перепрогона в v2 (каскад матчинга + очереди вместо мгновенного fail): **29/29 normalized, 0 failed.** Плюс 10 свежих рецептов klopotenko.com (UA, JSON-LD, без VPN). Итого 39 черновиков в базе.

### 2. Баг маппера USDA-нутриентов (найден и исправлен)
При массовом подтверждении матчей 57 из 224 падали с «неполный набор нутриентов». Живой fetch вскрыл две причины:
- Foundation-записи USDA (напр. тыквенные семечки) кладут энергию не в нутриент 208 (kcal), а в 957/958 (Atwater General/Specific Factors) — маппер знал только 208.
- У части семян/орехов лаборатории реально не измеряют следовый сахар (sugar_g отсутствует, остальное на месте).

Фикс: kcal по приоритету 208>957>958 (fail-closed по единице измерения, как и раньше); sugar_g=0.0 допускается ТОЛЬКО если весь остальной набор полный, с явной пометкой в провенансе (`source = "USDA:<id> (sugar assumed 0)"`) — не тихая подмена, а маркированное допущение. TDD, 414 тестов. После фикса ожило 42 из 57 упавших.

### 3. Главная находка сессии: LLM выбирает «наименее плохого» вместо честного null
Оставшиеся 15 падений (после фикса маппера) чинили через повторный выбор кандидата (LLM пробует следующего в списке, если первый дефектен по валидации) — сработало на всех 15. Но затем при пересчёте 36 «замороженных» строк очереди (кандидаты в match_queue фиксируются в момент постановки, каталог с тех пор вырос с 6 овощей до ~190 validated-ингредиентов) вскрылась системная проблема:

**Для однословных родовых названий ингредиентов (`egg`, `pepper`, `pork`) LLM-предвыбор (`pick_candidate`) вместо null выбирает специфичную/редкую USDA-запись, категорийно неверную:**
- `egg` → «Bagels, egg» (бублик с яйцом вместо яйца) — все 3 честных яичных fdcId в USDA-поиске оказались протухшими (API их не отдаёт), и в остатке кандидатов LLM выбрала бублик вместо null.
- `pepper` → «Pepper, banana, raw» (свежий болгарский перец вместо чёрного молотого перца-специи) — этот алиас, будучи слишком общим словом, заразил ЧУЖИЕ рецепты, которым просто был нужен обычный чёрный перец (борщ, фахитас, суп).
- `pork` → «Pork, pickled pork hocks» (маринованные свиные ножки вместо обычной свинины) — заразил два украинских рецепта (білий борщ, кандьор), где по тексту рецепта нужен был просто кусок свинины.

Суммарно заражено **11 рецептов** — все найдены вручную (глазами, сверкой name_en vs итоговый label), почищены трёхфазным ремонтом (живой fetch честной замены → атомарная транзакция repoint алиаса → requeue+перегенерация черновика), проверены построчно после перегенерации.

**Важно: находка НЕ была поймана автоматикой** — только ручной сверкой результатов после массового апрува.Autoapprove по LLM-пику (введён этой же сессией как разовое операционное решение, чтобы не жать 224 кнопки руками) на масштабе даёт систематическую (не случайную) ошибку категории именно на родовых/однословных именах.

### 4. Побочная находка: кандидаты в очереди — замороженный снимок
`match_queue.candidates` вычисляется один раз в момент постановки в очередь и не пересчитывается при росте каталога (уже был в бэклоге как `nutrition-ex1` — `sweep()` сознательно не умеет пере-спрашивать USDA-поиск, задача просто не реализована). Сегодня это подтвердилось на практике: 36 строк показывали кандидатов из каталога-в-6-овощей спустя рост каталога до ~190 записей.

### 5. Очередь «Веса» — автоматика уже исчерпана (проверено эмпирически)
84 позиции. Гипотеза «прогнать автоматику ещё раз построже» проверена и опровергнута: идемпотентный `sweep()` (бесплатный, без сети) пересчитал все 39 черновиков — **84 было, 84 осталось, ноль сдвига**. Разбивка по причине:
- 62/84 (piece/handful/bunch/sprig/leaf/can) — USDA физически не публикует порции в этих единицах для большинства продуктов (это не баг, а честный предел данных).
- 15/84 (`to_taste`) — по архитектурному принципу «нет цифры — нет блюда» нельзя оценить количество «по вкусу» для не-микро-ингредиента без домысла.
- ~7/84 (tbsp/tsp/ml) — ни точной USDA-порции, ни плотности у конкретного продукта.

### Текущий статус
match_queue: 209 resolved / 23 pending (честный ручной остаток — nduja, гарам масала, пекорино, свежая закваска и т.п., либо нет USDA-аналога, либо специфический бренд). weight_queue: 84, ждут либо ручного ввода в админке, либо расширения фолбэков (напр. синонимы штучных порций для clove/slice/bunch — заведено отдельной низкоприоритетной задачей).

### Открытый вопрос для анализа
Как усилить `pick_candidate` против систематической ошибки «выбрать наименее плохого вместо null» именно для родовых/однословных названий ингредиентов (egg/pepper/pork/oil/rice/potato — по сути любое родовое существительное без уточняющего прилагательного), не потеряв при этом recall (не скатиться в «всё подряд в ручную очередь», что обесценит автоапрув)? Рабочие идеи на нашей стороне: (а) явный запрет в промпте выбирать категорийно другой продукт, чем предпочесть null; (б) sanity-гейт после выбора (проверка совпадения категории/первого слова); (в) отдельная более консервативная политика именно для однословных generic-имён (без прилагательного) — например обязательный ручной ОТК для них, при том что многословные/уточнённые названия («dijon mustard», «extra virgin olive oil») продолжают авто-подтверждаться штатно, так как там куда меньше плацдарма для категорийной ошибки.

## [NUTRITION] 2026-07-21, 12:33 — Ответ на предложение «Словарь-перехватчик» (Bypass Dictionary)

Джемени предложила: собрать локальный маппинг 50–100 самых частых примитивных ингредиентов (egg, salt, water, sugar...) на вручную найденные идеальные `fdcId`, перехватывать их ДО LLM/каскада матчинга — жёсткий хардкод в коде.

**С сутью идеи согласны, с реализацией — нет.** Такой словарь дублирует механизм, который в pipeline-v2 уже есть и уже работает весь сегодняшний день: таблица `ingredient_aliases` + функция `find_exact()` — первый, бесплатный, LLM-less шаг каскада матчинга (T5). Каждый confirm сегодня писал строку в эту таблицу, и все последующие вхождения того же слова резолвились мгновенно, без единого обращения к LLM (каталог вырос с 6 до ~190 записей именно так, органически). Отдельный хардкод-словарь в коде дал бы то же самое поведение, но с двумя реальными минусами:
1. `fdcId` в USDA протухают — сегодня живьём поймали (первый выбор для «egg» на fetch отдавал 404). Если id зашит в код — чинится релизом. Если он в таблице — чинится одним UPDATE или кликом в админке.
2. Провенанс раздваивается: у нас на каждой записи БД есть `source`, у хардкод-словаря в коде его нет без отдельного параллельного аудит-трейла.

**Хорошая новость:** половина инфраструктуры для правильной версии идеи уже существует. `usda_import.py::import_seed()` — это буквально «человек вручную находит идеальный fdcId, скрипт заводит validated-ингредиент» (так уже засеяны 6 овощей в каталоге). А в схеме `IngredientAliasRow.source` уже предусмотрено значение `'seed'` рядом с `'admin-confirm'` — просто оно никогда не использовалось, потому что seed сегодня заводит только сам ингредиент, а не алиас на его текстовое имя.

**Решение:** не новый словарь, а маленькое расширение существующего — `import_seed()` дополнительно пишет строку в `ingredient_aliases` (`source='seed'`) для короткого curated-списка (20–50) по-настоящему универсальных слов, с вручную проверенным `fdcId` (тем же способом, каким сегодня руками проверялись замены egg/pepper/pork). `find_exact()` ловит их бесплатно и мгновенно, единый провенанс в одной таблице, без риска протухания без возможности живого фикса. Заведена задача `nutrition-jzo` (P2), явно НЕ заменяет предыдущую задачу про ужесточение `pick_candidate` (`nutrition-wyj`) — та остаётся обязательной для всего длинного хвоста, что не попадёт в короткий curated-список (paprika, mascarpone, сычуаньский перец и т.п.). Заодно проставлена зависимость: постоянный автоапрув по LLM-пику (`nutrition-bf9`) теперь явно блокирован фиксом `pick_candidate` — сначала лечим системную ошибку, потом включаем автоматику на полном потоке.

## 2026-07-24, 21:00 — Kill-Switch для устаревших версий бота: наш вариант против предложения Джемини

Владелец увидел в админке client_error от игрока на версии 1.8.11, работающей днями без перезапуска, хотя актуальна уже 1.8.14 — старый клиент всё это время долбит сервер long-poll'ом впустую. Спросил, что делать; переслал предложение Джемини из «Входящих».

**Предложение Джемини — 3 независимых механизма:** (1) Kill-Switch по заголовку `X-App-Version` на каждом запросе → `426 Upgrade Required`; (2) Idle Sleep Mode — таймер `last_active_time`, спящий режим через 2ч простоя, будить только вручную; (3) экспоненциальное затухание пингов при простое.

**Наш ответ — берём только упрощённый вариант (1), пункты (2) и (3) отклонены как избыточные.** Long-poll `/vault/sync` уже минимально нагружает сервер с v1.8.13 (`requests.Session`, одно TLS-соединение, ~50-58 сек цикл) — строить поверх ещё и таймер простоя/затухание значит городить вторую систему оптимизации ради пользователей, которые и так почти не грузят сервер. Реальная проблема — не «бот работает днями», а «старая версия не обновляется, пока бот открыт»: автообновитель (`GET /version/latest`) проверяется только при старте процесса.

Упрощение самого Kill-Switch: не новый заголовок на каждый HTTP-запрос, а поле в ответе уже открытого long-poll канала `/vault/sync` (никакого нового эндпоинта). Плюс — обнаружили, что в `check_auth` уже год как лежат мёртвые, никогда не записываемые поля `current_version`/`force_update` (см. `ANTI-PATTERNS.md`, сессия #126) — ровно заготовка под эту задачу, просто не доведена до конца. Решение пока НЕ утверждено владельцем, ждём его финального «да» и в каком виде делать.
