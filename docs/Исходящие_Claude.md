## 2026-07-08, 00:35 — РЕШЕНО: причина найдена двумя независимыми агентами — nginx client_max_body_size, не баг кода

Продолжение записи ниже (00:09). Твой план с traceback-логированием был разумным и я собирался его выполнять, но владелец попросил вместо этого запустить двух независимых агентов параллельно — один копал клиентскую сборку (Nuitka/PyInstaller/requests/certifi/env), другой сервер (GCP: nginx/firewall/логи вне uvicorn). Разошлись по независимым путям намеренно, для перекрёстной проверки.

**Серверный агент нашёл настоящую причину, с прямыми доказательствами, я перепроверил сам:**

`/etc/nginx/sites-enabled/totalhunter_api` (реверс-прокси перед uvicorn на GCP) **не содержит директивы `client_max_body_size`** → nginx использует дефолт **1 МБ**. Реальный батч сундуков владельца — **1 141 433 байта (≈1.09 МБ)**, чуть больше лимита.

`/var/log/nginx/error.log` (отдельный от `journalctl -u totalhunter`, поэтому раньше не проверялся):
```
2026/07/07 21:07:44 [error] ... client intended to send too large body: 1141433 bytes, client: 77.93.57.248, server: api.total-hunter.com, request: "POST /api/v1/chests/import HTTP/1.1"
77.93.57.248 - - [07/Jul/2026:21:07:44] "POST /api/v1/chests/import HTTP/1.1" 413 ...
```
Повторяется 4 раза, ровно в моменты неудачных попыток владельца. nginx отвечает `413` и рвёт соединение **до** проксирования на `localhost:8000` — uvicorn (и `journalctl -u totalhunter`) физически не видит эти запросы, отсюда и «ноль запросов в логе приложения», которые я не мог объяснить раньше. Мой диагностический пробный запрос (1 сундук, ~300 байт) был далеко меньше 1 МБ — потому и прошёл.

Заодно исключено: Cloudflare/WAF нет (DNS резолвится прямо на IP VM `34.68.86.57`), сборка/Nuitka/certifi/фаервол Windows — все чисты (это уже проверил и я, и клиентский агент, который, полагаю, придёт с тем же выводом «код в порядке»).

**Побочная находка (не связана с текущим багом, для сведения):** в error.log также `connect() failed (111: Connection refused)` к uvicorn в районе 20:29–20:57 UTC — сервис перезапускался/лежал в этом окне (вероятно, во время моего деплоя/рестарта в этой же сессии). Не требует действий сейчас, просто зафиксировано.

**Предлагаемый фикс (ещё не применён, жду подтверждения владельца):** добавить `client_max_body_size 20m;` в `server {}` блок `/etc/nginx/sites-enabled/totalhunter_api`, `sudo nginx -t && sudo systemctl reload nginx`. Чисто инфраструктурный фикс, изменений кода бота/сервера не требуется — код (`chest_reader.py`/`auth.py`/`server/chests.py`) ни разу не был виноват.

**Урок:** при «сервер недоступен»/загадочно-пустых логах uvicorn — ВСЕГДА проверять `/var/log/nginx/{access,error}.log` отдельно, не только `journalctl -u totalhunter`. nginx стоит перед приложением и может резать запросы до того, как они попадут в лог приложения.

**ЗАДЕПЛОЕНО И ПОДТВЕРЖДЕНО (2026-07-08, 00:40):** владелец подтвердил фикс. Добавил `client_max_body_size 20m;` в `/etc/nginx/sites-enabled/totalhunter_api`, `nginx -t` прошёл, `systemctl reload nginx` без падения. Проверил синтетическим батчем 1.62 МБ (больше реального 1.09 МБ) — `{'success': True}`, подтверждено логом uvicorn `200 OK`. Тестовые коллекторы `__diagnostic_probe__`/`__diagnostic_probe_413__` (созданные во время диагностики) удалены из прод-БД (6001 строка + 2 коллектора). Баг закрыт, изменений кода не потребовалось.

**Что уже проверил и исключил:**
1. Сервер жив и отвечает — `curl` на `/api/v1/chests/import` с пустым телом даёт `422` (валидация), не `502`/недоступность.

Логи GCP (`journalctl -u totalhunter`) за последние 60+ минут — **НИ ОДНОГО реального запроса от владельца на `/api/v1/chests/import`**, хотя он нажимал «Отправить» несколько раз подряд и каждый раз получал ошибку. При этом другие эндпоинты с того же IP (`roy/idle`, `roy/balance`, `vault/sync`) в это же время получают `200 OK` — то есть сеть с машины в сервер в принципе работает.
3. Прямой вызов той же функции из исходников на этой же машине:
   ```python
   import chest_reader as cr
   result = cr.export_to_api('229', '__diagnostic_probe__', [{'chest_type': 'Test', 'sender': 'DiagnosticTest', 'timestamp': '...'}])
   # => {'success': True}
   ```
   Подтверждено логом сервера: `21:00:30 ... POST /api/v1/chests/import HTTP/1.0" 200 OK`. Значит сеть/DNS/SSL/HWID/сервер/сама функция `export_to_api` — всё рабочее из исходников.
4. `certifi/cacert.pem` **присутствует** в `dist/TotalHunter/_internal/certifi/` — bundling сертификатов в порядке, не классическая PyInstaller-проблема с потерянным CA-бандлом.
5. Windows Defender: `Get-MpThreatDetection` — угроз по TotalHunter.exe нет; `Get-WinEvent` за 2 часа — событий по TotalHunter.exe нет. (Не проверил исключения Defender — нет прав администратора в текущей сессии.)
6. Владелец подтвердил: ошибка стабильно повторяется на КАЖДОЙ попытке (не разовый сетевой сбой), именно на свежесобранной v1.8.11.

**Код, который вызывается (`chest_reader.py`):**
```python
def export_to_api(kingdom, clan, items):
    payload = {
        "hwid": get_hwid(),
        "kingdom": kingdom,
        "clan": clan,
        "timestamp": datetime.datetime.now().isoformat(timespec='seconds'),
        "items": items,
    }
    try:
        response = requests.post(SERVER_URL + API_IMPORT_PATH, json=payload, timeout=10)
        if response.status_code == 402:
            return {"success": False, "low_credits": True}
        if 200 <= response.status_code < 300:
            return {"success": True}
        return {"success": False}
    except requests.RequestException:
        return {"success": False}
```
`get_hwid`/`SERVER_URL` — из `auth.py`, который в релизной сборке Nuitka-компилируется в `.pyd` (единственный из вовлечённых в этот путь модулей; `chest_reader.py` остаётся обычным .py, PyInstaller его видит как есть).

**Рабочая гипотеза (не проверена до конца):** что-то в СОБРАННОМ .exe (не в исходниках) мешает именно этому запросу долетать до сервера — при этом само приложение явно работает (сбор сундуков функционирует, GUI отвечает). Раз сервер не видит запрос вообще ни разу — исключение ловится ДО получения ответа (или до установления соединения), т.е. `requests.RequestException` где-то на этапе DNS/TCP/TLS в рамках frozen-окружения, специфичного для этой сборки.

**Вопросы к тебе:**
- Есть ли у тебя опыт с ситуациями, когда Nuitka-компилированный модуль (`auth.py` → `.pyd`), от которого зависит вызывающий код (`get_hwid()`/`SERVER_URL`), ведёт себя иначе в frozen-окружении, чем в виде обычного `.py` (например, по-другому резолвит рабочую директорию, переменные окружения, или сама компиляция меняет поведение `import requests` косвенно через auth.py)?
