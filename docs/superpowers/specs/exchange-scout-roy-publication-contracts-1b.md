## Стадия 3. Contract Extraction

Формат: `Требование → Контракт → Enforcement → Verification`. Нумерация: контракты **P-**, находки **PA-**,
тесты **PT-** (не пересекаются с C-/A-/T- других спек).

| № | Контракт | Enforcement (планируемый) | Verification |
|---|---|---|---|
| P-01 | Публикация вызывается только при **успешном списании 10◆ и успешном OCR** (`coords_ok = true`: `PositionReader.read()` вернул координаты, Часть A §4.6); иначе не вызывается. **Это контракт штатного клиента, а не серверный инвариант: сервер факта списания не проверяет (PA-5).** Порядок остальных шагов цепочки (показ находки; OCR относительно списания) определяют Части A/B и спека №2 (предпосылка — 4.0); цепочка владельца — в Стадии 1. | ветка consumer'а: `publish` вызывается только при `charged is True and coords_ok is True` | PT-01, PT-02 |
| P-02 | Контракт данных. **Запрос `POST`:** `hwid` (только для проверки пользователя), `kingdom` (строгий int, 1…2147483647), `x`, `y` (строгий int, без приведения типов, в диапазоне 32-битного `Integer` колонки: −2147483648…2147483647; иных бизнес-ограничений на X/Y нет). **В БД:** `kingdom`, `x`, `y`, `reporter_hwid` (внутренний, наружу не отдаётся), `found_at` (задаёт приложение при вставке, UTC). **Публично (`GET`):** ровно `kingdom`, `x`, `y`, `found_at`. Не входят в `POST`, не сохраняются в `roy_scout_finds` и не отдаются в `GET`: изображение, `percent`, `conf`, `box` (внутри процесса consumer они могут существовать). | pydantic-схема `ScoutFindRequest` (`StrictInt` + `Field(ge=-2147483648, le=2147483647)` для x, y; `StrictInt` + `Field(ge=1, le=2147483647)` для kingdom — проверено на pydantic 2.13.1: обычный `int` приводит `"123"`, `1.0`, `True`, `StrictInt` их отклоняет) + публичная схема ответа без hwid | PT-03, PT-04 |
| P-03 | Изоляция от 1.0: 2.0 использует отдельные таблицу, эндпоинт и клиентский метод и **не проходит** через существующий конвейер `/roy/report` → `roy_pool` → SSE / Telegram. Конкретные символы — примеры, а не список запретов: `/roy/report`, `roy_pool`, `_report_rate`, `_broadcast(pool_updated=True)`, `send_telegram_alert`; новая таблица `roy_scout_finds`, эндпоинт `POST /roy/scout-find`. | отдельная функция в `server/roy.py`, отдельная модель в `server/models.py`, alembic-миграция | PT-05 |
| P-04 | Для публикации 2.0 нет rate limit и нет дедупликации (решение владельца). Каждый **валидный авторизованный** вызов (P-05) = новая строка. | в коде эндпоинта нет лимитера и нет `UNIQUE` на (kingdom,x,y) | PT-06 |
| P-05 | Валидация: `hwid` существует и не забанен (404/403 как в `/use_credit`); `kingdom` — строгий int 1…2147483647; `x`, `y` — строгие int в диапазоне `Integer` (P-02). | проверка пользователя как `server/main.py:324-332` (входной hwid, не соответствующий существующему пользователю, в т. ч. слишком длинный, отклоняется до вставки; `User.hwid` `String(16)`, 2.6a) + `kingdom: StrictInt` + `Field(ge=1, le=2147483647)`; `x`, `y`: `StrictInt` + диапазон P-02 | PT-07, PT-08 |
| P-06 | Клиент: если зафиксированное в результате значение `kingdom` ≤ 0 (`_get_roy_kingdom()` даёт `0`, когда поле пусто или не число), публикация **не выполняется** (сервер такое королевство не показывает, `roy.py:130`); причина пишется в лог сессии. Списание при этом уже состоялось (P-01) — находка остаётся в `scout_results.jsonl`. **Значение `kingdom` фиксируется в результате находки в момент её создания и передаётся в `report_scout_find` вместе с результатом; публикация НЕ перечитывает `_get_roy_kingdom()` из GUI** (иначе смена поля между находкой и публикацией даёт чужое королевство). Значение хранится в результате находки в памяти consumer'а, в `scout_results.jsonl` не добавляется (правка Части A вне этой спеки). Точка фиксации — после успешного OCR и до записи строки журнала (4.0); реализует Часть B [→ Часть B], обязанная выдержать последовательность: захват K → создание результата → результат несёт этот K → GUI после этого не читается. | проверка `kingdom > 0` в клиентском методе перед запросом; `kingdom` — параметр `report_scout_find`, читаемый consumer'ом один раз при создании результата | PT-09; PT-18 (тест плана consumer'а) |
| P-07 | Публикация не блокирует consumer: вызов публикации выполняется вне consumer-потока (отдельный тред с `_TIMEOUT = 5`, как `RoyClient.report()`, 2.5) и не блокирует consumer ожиданием HTTP-ответа. Завершение процесса в P-07 не входит: поток non-daemon, как у `RoyClient.report()` (2.5, `roy_client.py:46-48`), и может задержать выход процесса до завершения запроса; согласование с остановкой по ESC — **[→ Часть B]**. | новый метод `RoyClient.report_scout_find()` по образцу `report()` | PT-10 |
| P-08 | Сбой публикации (сеть, 4xx/5xx, таймаут) НЕ отменяет списание; **после успешной фиксации результата в локальном журнале сбой публикации не приводит к потере результата обработки** (до завершения `fsync` записи результат не гарантирован). **Контракт к consumer'у [→ Часть B]:** результат находки фиксируется локально (строка `scout_results.jsonl`, Часть A §4.6) **до запуска публикации** — иначе при падении процесса возможно списание без локального следа. **`scout_results.jsonl` — журнал результата обработки, а не журнал публикации:** после рестарта публикация не восстанавливается, `kingdom` в JSONL отсутствует сознательно (non-goal), для повторной публикации K не сохраняется. Повтор публикации не делается (non-goal), сбой пишется в лог сессии. | `try/except` вокруг запроса, исключение не выходит из треда; consumer: запись строки журнала с `fsync` предшествует вызову `report_scout_find` | PT-11; PT-17 (тест плана consumer'а) |
| P-09 | Чтение сайтом: публичный `GET /roy/scout-finds` (без авторизации) возвращает список `{kingdom, x, y, found_at}`, новые первыми; hwid в ответе отсутствует. Показываются только находки моложе **20 минут** от публикации (`found_at > now − 20 мин`, P-13). **Возвращается не более 500 самых новых находок**; если подходящих строк больше, остальные не возвращаются (число 500 — константа `SCOUT_FINDS_LIMIT`). Порядок детерминирован: `found_at` по убыванию, при равенстве — `id` по убыванию (`id` наружу не отдаётся). Лимит касается только `GET`; `POST` по P-04 остаётся без rate limit и без дедупликации. | отдельная функция в `roy.py` с явным `select` только этих колонок: `WHERE found_at > now − 20 мин ORDER BY found_at DESC, id DESC LIMIT SCOUT_FINDS_LIMIT` | PT-12 |
| P-10 | Сайт: на `RoyPage.jsx` добавляется блок «Находки Биржи 2.0» (список из P-09), данные грузятся при открытии страницы и кнопкой «Обновить». Существующий список королевств и SSE не меняются. | отдельный `useEffect`/`fetch`, отдельное состояние | PT-13 (ручная проверка страницы) |
| P-11 | Текст на сайте — только факты: «Примерное расположение: позиция экрана бота в момент кадра, не точные координаты биржи»; срок показа — «запись показывается 20 минут после публикации». Языки — те же, что у страницы (RU/EN). | строки в `RoyPage.jsx` по образцу `isRu` | PT-13 |
| P-12 | Поведение Биржи 1.0 не изменяется: `/roy/report`, `/roy/pool`, `roy_pool`, `_report_rate`, SSE-поток, `RoyClient.report/get_pool` работают как прежде. | существующие функции, константы, модели и методы не изменяются; допускается только расширение import-строк и добавление новых символов | PT-05, PT-14 |
| P-13 | Срок показа находки на сайте — **20 минут** (решение владельца, как у пула 1.0), от `found_at`, то есть **от момента публикации (POST), а не от захвата кадра или детекции YOLO**. Константа `SCOUT_FIND_TTL_MIN = 20` — **своя**, не `POOL_TTL_MIN` (правка общей константы задела бы 1.0). Чтение показывает только строки моложе срока (`found_at > now − 20 мин`). Каждая публикация, прошедшая проверку пользователя, в одной транзакции удаляет просроченные строки (возраст не меньше срока: `found_at <= now − 20 мин`) и вставляет новую; общий `_cleanup_loop` не трогаем. Это очистка при вставке, а не удаление по таймеру: без новых публикаций просроченные строки физически остаются, но `GET` их не показывает. `now` и `found_at` задаются приложением (`datetime.now(timezone.utc)` в `roy.py`), а не часами PostgreSQL и не временем клиента; `found_at` штатно задаётся приложением; `server_default=func.now()` существует только как fallback для вставок, не использующих явное значение. Наивный `datetime.now()` запрещён: все значения и пороги — только timezone-aware UTC (`ANTI-PATTERNS.md`, Хангоф #70: SQLite в тестах принимает наивное время, прод с `TIMESTAMP(timezone=True)` — нет). | фильтр в `select` + `delete` в той же транзакции вставки; индекс по `found_at` (модель `index=True` + миграция `ix_roy_scout_finds_found_at`) — иначе `DELETE`/`SELECT` сканируют всю таблицу | PT-15, PT-16, PT-19, PT-20 |

**Межспековые контракты.** P-01, P-06 и P-08 реализует consumer (Части A/B): эта спека задаёт контракт и verification (PT-01, PT-02, PT-09, PT-17, PT-18), но их реализацию не содержит и не считается их реализующей.

Неявные границы контрактов: P-09/P-10 — единственное, что видит посторонний посетитель сайта; всё, что не
перечислено в P-02, наружу не выходит.
