## 3.1 Контракты Раздела 1 — единая панель калибровки (12 целей)

Формат: `Requirement → Contract/Invariant → Enforcement (планируемый) → Verification`.

| # | Requirement | Contract / Invariant | Enforcement (планируемый) | Verification |
|---|---|---|---|---|
| C-01 | Один вход вместо двух несвязанных | Сегодня — два раздельных пути (отдельная кнопка калибровки A/Б, сворачивающая окно; выпадающий список тюнинга, инлайн). Панель обязана свести оба в **один** пользовательский путь: единый список/навигация на 12 целей, без второго независимого пользовательского входа/триггера (контракт про UI-путь пользователя, не про запрет любого внутреннего технического вызова) | Design выбирает конкретный виджет (список, вкладки внутри вкладки и т. п.); контракт фиксирует только «один вход», не форму | Ручная проверка UI / GUI-тест на отсутствие второго независимого пользовательского триггера калибровки A/Б |
| C-02 | Тип цели — явное поле данных, не структура кода | Каждая из 12 целей имеет явный тип ∈ {точка, OCR-область, смещение-к-YOLO} (файл 33, находка 2.2). Тип **не выводится** из того, в какой из трёх сегодняшних структур (`_TUNE_POINT_TARGETS`/`_CHEST_TUNE_RECTS`/нигде) цель перечислена — это данные, которые единый источник метаданных обязан хранить явно | Единый источник метаданных 12 целей с явным полем `kind`; конкретная структура хранения (таблица, реестр, что-то ещё) определяется на Design, не здесь | Тест проходит по всем 12 целям и проверяет, что `kind` задан и принадлежит фиксированному множеству |
| C-03 | Единое визуальное поведение на тип, не три параллельных пути | Сегодня три независимые функции рисуют концептуально одно и то же («покажи, где точка»): `calibration_ui._show_red_dot` (только А/Б), `main._show_crosshair_at` (уже переиспользуется между джойстик-точкой и превью тюнинга — файл 33, 2.3), `main._show_chest_rect_overlay` (только области). Для каждого `kind` (C-02) должен существовать **единый путь визуального представления**; исторические независимые пути не используются параллельно друг с другом для одного и того же `kind`. Как именно это реализовано (общий параметризованный рендерер, отдельные функции по типу и т. п.) — вопрос Design, не контракта | А/Б показываются тем же визуальным путём, что и точки тюнинга (не `_show_red_dot` отдельно); область — свой единственный путь; для «смещение-к-YOLO» — явное состояние UI («статичное превью недоступно, позиция определяется в реальном времени»), не молчаливое отсутствие | Ревью на этапе PLAN: для каждого `kind` — ровно один действующий визуальный путь, старые параллельные пути не используются одновременно с новым |
| C-04 | Тематическая группировка и тип — независимые визуальные каналы | Сегодня `chest_collect` (тип «точка») визуально сгруппирован по цвету с `chest_sender`/`chest_type` (тип «область») только потому, что все три — «про сундуки» (`TUNE_CHEST_GROUP`, файл 33, 2.2/2.4). Единая панель обязана сохранять возможность такой тематической группировки (сундуки — не единственная будущая тема), но **тип цели должен быть определим по любой цели независимо от её тематической группы** — группировка по теме не должна маскировать различие точка/область/смещение-к-YOLO | Design выбирает конкретное визуальное решение (иконка типа, форма маркера, отдельная колонка и т. п.) — контракт фиксирует независимость каналов, не конкретный визуальный приём | **После Design:** ручная проверка, что для каждой из 12 целей тип считывается с экрана без обращения к тематической группе. До выбора конкретного визуального решения эта проверка невыполнима — контракт фиксирует требование к будущему UI, не к сегодняшнему |
| C-05 | Единый стиль не переопределяет существующую координатную модель | Панель не меняет существующую модель хранения координат и офсетов: `coord_manager.calibrate()` (абсолютные координаты A/Б) и `coord_manager.set_ui_offset()` (смещения 10 целей тюнинга) сохраняют прежнюю семантику (файл 33, 2.1). Новый слой метаданных из C-02 (явный тип цели для единого UI) описывает **цели**, а не координаты — это не третий формат хранения координат и не замена существующих значений `coord_manager` | Единая панель вызывает существующие `calibrate()`/`set_ui_offset()` как есть; метаданные C-02 живут отдельно от координатных данных и не изменяют их формат | Тест: после ввода через новую панель значения в `coord_manager` идентичны тем, что дал бы старый раздельный UI при тех же введённых числах |
| C-06 | Видео — гиперссылка, не плеер | Раздел содержит ссылку на YouTube-ролик (URL будет предоставлен позже); видео не встраивается в интерфейс бота | Обычный текстовый/кликабельный элемент со ссылкой | Ручная проверка наличия ссылки и отсутствия встроенного видеоплеера |

## 3.2 Явные non-goals

1. **Порядок отображения 12 целей в списке** — сознательно не решается здесь (Context, файл 32, «Что НЕ
   решено», п.1). Design может выбрать любой порядок, контракты C-01…C-06 от этого не зависят.
2. **Конкретная визуальная реализация типов** (иконки, цвета, форма маркера для «смещение-к-YOLO») —
   Design, не Contract Extraction (Context, п.5 «Что НЕ решено»).
3. **Математика/логика существующих точек и офсетов не меняется** — уже зафиксировано входящими и
   подтверждено C-05.

## 3.3 Зависимости между контрактами

```
C-02 (тип как данные) ──> обязательный вход для ──> C-03 (единая отрисовка на тип)
C-02 ──> обязательный вход для ──> C-04 (независимость каналов группировка/тип)
C-01 (один вход) ──> не зависит от C-02…C-06, но их проще выполнить, если единый источник метаданных
   из C-02 существует и используется тем же единственным входом
```

Конфликтов между контрактами не найдено. C-05 ограничивает все остальные: что бы ни выбрал Design для
UI (C-01, C-03, C-04), это не должно потребовать изменения формата данных `coord_manager`.

## 3.4 Контракты Раздела 2 — рекомендуемые значения (добавлено после закрытия owner decisions)

| # | Requirement | Contract / Invariant | Enforcement (планируемый) | Verification |
|---|---|---|---|---|
| C-07 | Область действия — все 19 без исключений | Механизм рекомендуемых значений применяется ко всем 19 `CTkSlider` бота (10 навигация/нейросеть, 7 склепы, 1 комбо, 1 сундуки), не только к части. Закрыто владельцем 2026-09-19 (файл 32) | Единый источник данных C-08 покрывает все 19 идентификаторов слайдеров | Тест: для каждого из 19 известных слайдеров есть запись рекомендуемого значения |
| C-08 | Рекомендуемые значения — фиксированные данные, не вычисляются | Конкретные 19 чисел зафиксированы владельцем (файл 32, таблица) и являются данными для реализации, а не результатом измерения/вычисления на этапе PLAN/Design. 18 из 19 — текущие фактические значения из реального профиля/конфига владельца на 2026-09-19; один явный owner override («Дальность марша Картера» = 120, а не фактические 202) | Значения переносятся в код как есть, один в один с таблицей файла 32; никакое новое измерение/пересчёт не производится | Тест сверяет 19 захардкоженных значений в реализации с таблицей файла 32 дословно |
| C-09 | Форма — только пассивная зелёная зона, без активного действия | Единственная форма интерфейса — визуальное выделение зоны на самой шкале ползунка. Кнопка «вернуть рекомендуемое» **не реализуется** — владелец явно выбрал только пассивную подсказку (файл 32, закрыт вопрос 4). Пользователь видит, попадает ли его текущее значение в рекомендуемую зону, без клика и без принудительного перемещения ползунка | Design выбирает конкретную реализацию отрисовки зоны на `CTkSlider` (заливка сегмента дорожки и т. п.) — контракт запрещает только добавление кнопки-действия | Ручная проверка UI: на каждом из 19 слайдеров есть визуальная зона, нет кнопки «вернуть рекомендуемое» |
| C-10 | Ширина зелёной зоны — открытый вопрос, не решается здесь | Owner decision дал **одно число на слайдер** (точку), а не диапазон/ширину «зоны». Механическое превращение точки в зону требует ширины (например, ±X% или ±X единиц), которую владелец не задавал — это тоже число, которое Contract Extraction не имеет права придумать (тот же принцип, что и для остальных владельческих чисел проекта). Design обязан либо получить от владельца ширину зоны, либо показывать точку/тонкую метку без ширины — оба варианта допустимы, выбор не здесь | Не определяется на этой стадии | Не тестируется до выбора Design |

**Зависимость:** C-07/C-08/C-09 не зависят от контрактов Раздела 1 (C-01…C-06) — общий источник данных
возможен, но не обязателен. C-10 блокирует только точную реализацию C-09, не сам факт наличия зелёной
зоны — Design может временно показать зону нулевой/минимальной ширины (точку) без нарушения контрактов,
если ширина ещё не решена владельцем.
