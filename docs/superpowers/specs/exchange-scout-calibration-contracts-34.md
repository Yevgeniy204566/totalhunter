## 3.1 Контракты Раздела 1 — единая панель калибровки (12 точек)

Формат: `Requirement → Contract/Invariant → Enforcement (планируемый) → Verification`.

| # | Requirement | Contract / Invariant | Enforcement (планируемый) | Verification |
|---|---|---|---|---|
| C-01 | Один вход вместо двух несвязанных | Сегодня — два раздельных пути (отдельная кнопка калибровки A/Б, сворачивающая окно; выпадающий список тюнинга, инлайн). Панель обязана свести оба в **один** пользовательский путь: единый список/навигация на 12 точек, без скрытого второго входа | Design выбирает конкретный виджет (список, вкладки внутри вкладки и т. п.); контракт фиксирует только «один вход», не форму | Ручная проверка UI / GUI-тест на отсутствие второго независимого триггера калибровки A/Б |
| C-02 | Тип цели — явное поле данных, не структура кода | Каждая из 12 точек имеет явный тип ∈ {точка, OCR-область, смещение-к-YOLO} (файл 33, находка 2.2). Тип **не выводится** из того, в какой из трёх сегодняшних структур (`_TUNE_POINT_TARGETS`/`_CHEST_TUNE_RECTS`/нигде) цель перечислена — это данные, которые единый реестр 12 точек обязан хранить явно | Единая таблица/реестр 12 точек с полем `kind`, заменяющая три сегодняшние разрозненные структуры | Тест проходит по всем 12 записям реестра и проверяет, что `kind` задан и принадлежит фиксированному множеству |
| C-03 | Единая отрисовка маркера на тип, не три реализации на всё | Сегодня три независимые функции рисуют концептуально одно и то же («покажи, где точка»): `calibration_ui._show_red_dot` (только А/Б), `main._show_crosshair_at` (уже переиспользуется между джойстик-точкой и превью тюнинга — файл 33, 2.3), `main._show_chest_rect_overlay` (только области). Панель обязана рисовать маркер **одним путём на тип** (один рендерер для «точка», один для «область», явное состояние для «смещение-к-YOLO»), не тремя историческими путями | `_show_red_dot` выводится из употребления, А/Б рисуются тем же путём, что и точки тюнинга; область — отдельный, но единственный путь; для «смещение-к-YOLO» — явное состояние UI («статичное превью недоступно, позиция определяется в реальном времени»), не молчаливое отсутствие | Тест/ревью кода на этапе PLAN: не более одной функции отрисовки маркера на каждый тип |
| C-04 | Тематическая группировка и тип — независимые визуальные каналы | Сегодня `chest_collect` (тип «точка») визуально сгруппирован по цвету с `chest_sender`/`chest_type` (тип «область») только потому, что все три — «про сундуки» (`TUNE_CHEST_GROUP`, файл 33, 2.2/2.4). Единая панель обязана сохранять возможность такой тематической группировки (сундуки — не единственная будущая тема), но **тип цели должен быть определим по любой точке независимо от её тематической группы** — группировка по теме не должна маскировать различие точка/область/смещение-к-YOLO | Design выбирает конкретное визуальное решение (иконка типа, форма маркера, отдельная колонка и т. п.) — контракт фиксирует независимость каналов, не конкретный визуальный приём | Ручная проверка: для каждой из 12 точек тип считывается с экрана без обращения к тематической группе |
| C-05 | Единый стиль не переопределяет существующую математику | Панель — это способ ВВОДА/ОТОБРАЖЕНИЯ 12 точек, не новая модель данных. `coord_manager.calibrate()` (абсолютные координаты A/Б) и `coord_manager.set_ui_offset()` (смещения 10 целей тюнинга) остаются теми же вызовами с той же семантикой (файл 33, 2.1) — панель не вводит третий формат хранения | Единая панель вызывает существующие `calibrate()`/`set_ui_offset()` как есть; новый реестр (C-02) — только слой представления поверх них | Тест: после ввода через новую панель значения в `coord_manager` идентичны тем, что дал бы старый раздельный UI при тех же введённых числах |
| C-06 | Видео — гиперссылка, не плеер | Раздел содержит ссылку на YouTube-ролик (URL будет предоставлен позже); видео не встраивается в интерфейс бота | Обычный текстовый/кликабельный элемент со ссылкой | Ручная проверка наличия ссылки и отсутствия встроенного видеоплеера |

## 3.2 Явные non-goals

1. **Порядок отображения 12 точек в списке** — сознательно не решается здесь (Context, файл 32, «Что НЕ
   решено», п.1). Design может выбрать любой порядок, контракты C-01…C-06 от этого не зависят.
2. **Конкретная визуальная реализация типов** (иконки, цвета, форма маркера для «смещение-к-YOLO») —
   Design, не Contract Extraction (Context, п.5 «Что НЕ решено»).
3. **Математика/логика существующих точек и офсетов не меняется** — уже зафиксировано входящими и
   подтверждено C-05.
4. **Раздел 2 (рекомендуемые значения) контрактов не имеет** — три открытых вопроса (список ползунков,
   источник диапазонов, форма UI) требуют ответа владельца, Contract Extraction не производит их из кода.

## 3.3 Зависимости между контрактами

```
C-02 (тип как данные) ──> обязательный вход для ──> C-03 (единая отрисовка на тип)
C-02 ──> обязательный вход для ──> C-04 (независимость каналов группировка/тип)
C-01 (один вход) ──> не зависит от C-02…C-06, но их проще выполнить, если реестр из C-02 существует
   и используется тем же единственным входом
```

Конфликтов между контрактами не найдено. C-05 ограничивает все остальные: что бы ни выбрал Design для
UI (C-01, C-03, C-04), это не должно потребовать изменения формата данных `coord_manager`.

## 3.4 Что дальше

Design (Stage 4) для Раздела 1 может начинаться после одобрения владельцем этого файла — здесь нет
зависимостей от ещё не написанной Части B или GUI-спеки Биржи 2.0 (подтверждено уже в Context). Раздел 2
остаётся заблокированным до получения от владельца: списка ползунков, источника диапазонов, формы
интерфейса.
