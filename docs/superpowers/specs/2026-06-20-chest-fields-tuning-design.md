# Тюнинг полей распознавания сундуков — Design Spec

**Дата:** 2026-06-20
**Статус:** Approved

## Проблема

После сборки v1.8.0 владелец сообщил, что бот читает `chest_type` неверно — попадает на строку
заголовка карточки («Божественный сундук Золотого Стража») вместо строки «Источник:» под именем
игрока («Эпический отряд Древних»). Диагностика на живой игре показала, что геометрия и формулы в
`chest_reader.py` (`SENDER_REF_RECT`, `SOURCE_REF_RECT`, `coord_manager.to_region_dialog`) дают
точный результат при прямом вызове с тем же профилем калибровки — то есть сами координаты и
формулы верны. Расхождение проявляется только в собранном EXE и теоретически может зависеть от
условий рендера/DPI на конкретной машине пользователя, которые невозможно гарантированно
воспроизвести из исходников. Владельцу нужен ручной механизм подстройки на месте, без пересборки.

## Решение

Расширить существующий D-Pad «Тюнинг кликов» (вкладка Калибровка) двумя новыми пунктами —
**«Имя игрока (сундуки)»** и **«Источник (сундуки)»**. Механизм идентичен существующему:
выпадающий список выбора цели, переключатель шага 1px/5px, 4 стрелки (▲►▼◄), кнопка «Сброс».

Отличие от тюнинга кликов: те смещают точку клика (визуализации точки сейчас нет вообще), эти —
смещают **прямоугольную зону распознавания** (OCR crop), поэтому при выборе одного из двух новых
пунктов поверх игры показывается **прямоугольник** реального размера зоны чтения (а не точка),
обновляющийся при каждом нажатии стрелки — чтобы владелец на глаз подвёл рамку под нужный текст.

Хранение — через существующий `coord_manager.ui_offsets` (тот же механизм, что для
`wt_icon`/`carter`/`top_accel`/`march_accel`): просто два новых имени в одном словаре, persisted в
профиль тем же `save()`/`load()` без изменений в их коде.

## Изменения по файлам

### `coord_manager.py`
`_UI_BUTTON_NAMES` дополняется двумя именами: `"chest_sender"`, `"chest_type"`. Это всё — `save()`,
`load()`, `get_ui_offset()`, `set_ui_offset()` уже общие для любого имени из этого списка.

### `chest_reader.py`
`read_fixed_field(frame, ref_rect, offset_name=None)` — новый необязательный параметр. Если
передан, к экранному прямоугольнику от `coord_manager.to_region_dialog(*ref_rect)` прибавляется
`coord_manager.get_ui_offset(offset_name)` (dx, dy) перед вырезкой ROI.

`read_sender_name` вызывает `read_fixed_field(frame, SENDER_REF_RECT, "chest_sender")`.
`read_chest_type` вызывает `read_fixed_field(frame, SOURCE_REF_RECT, "chest_type")`.

Без тюнинга (offset 0,0 по умолчанию) поведение не меняется — обратная совместимость гарантирована
тем, что `get_ui_offset` на новое имя возвращает `(0, 0)` пока пользователь не нажал ни одной
стрелки.

### `main.py`
- `_TUNE_INTERNAL` дополняется `"chest_sender"`, `"chest_type"` — два новых пункта в существующем
  `CTkOptionMenu`.
- Переводы `cal_tune_chest_sender` / `cal_tune_chest_type` на все 19 языков (тот же блок, что
  `cal_tune_wt_icon` и пр.).
- Live-прямоугольник: при выборе одного из двух новых пунктов в выпадающем списке и при каждом
  нажатии стрелки D-Pad — показывается `Toplevel` с прозрачной рамкой (border, без заливки),
  размером равным реальной ширине/высоте `SENDER_REF_RECT`/`SOURCE_REF_RECT` (после масштабирования
  `coord_manager.to_region`), позиционированный в экранных координатах
  `to_region_dialog(*ref_rect) + ui_offset`. Автоскрытие через 3 сек по аналогии с существующим
  `_show_calibration_dot` (тот же таймер-паттерн, отдельный `Toplevel`/`after`-handle).
- Для существующих 4 пунктов (`wt_icon` и др.) поведение не меняется — оверлей у них не было и не
  появляется (вне рамок задачи).

## Тестирование

- TDD на `chest_reader.py`: `read_fixed_field` корректно прибавляет offset к ROI-прямоугольнику
  (monkeypatch `coord_manager.get_ui_offset`), и не меняет поведение при offset (0, 0) /
  отсутствующем `offset_name` — регрессия существующих тестов `read_sender_name`/`read_chest_type`.
- `coord_manager.py`: `chest_sender`/`chest_type` — валидные имена для `get_ui_offset`/
  `set_ui_offset` (как и 4 существующих).
- GUI-часть (`main.py`: дропдаун, D-Pad, прямоугольник-оверлей) — без автотестов, по аналогии с
  предыдущей задачей (слайдер скорости сундуков); финальная проверка — ручная, владельцем, на живой
  игре.

## Вне рамок

- Drag-and-drop / resize прямоугольников мышью — отклонено в пользу D-Pad (проще, переиспользует
  готовый паттерн).
- Изменение поведения существующих 4 пунктов тюнинга кликов (точка-оверлей для них не добавляется).
- Расследование первопричины (DPI/рендер) самого расхождения между `python main.py` и EXE — этот
  тюнинг даёт владельцу способ компенсировать расхождение вручную, не устраняя его источник.
