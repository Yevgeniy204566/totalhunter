# Сундуки — Настройки сезона (Спека 1 из 3)

Дата: 2026-06-21

## Контекст

Gemini прислал ТЗ (`docs/Входящие_Gemini.md`) на геймификацию публичной
страницы клана: сезонные рамки (период сбора), нормативы (цели по очкам и
сундукам), таймер обратного отсчёта, цветовая подсветка строк по выполнению
нормы. Запрос покрывает 3 независимые подсистемы — решено разбить на 3
последовательных спеки/плана:

1. **Эта спека** — схема БД + бэкенд CRUD + UI кабинета для настроек сезона.
2. Бэкенд публичной сводки — фильтрация по датам, отдельный подсчёт «квоты»
   только по сундукам, помеченным как квотные (см. ниже), передача
   `targets`/дат в JSON. Отдельная спека, после этой.
3. UI публичной страницы — шапка с целями, таймер, колонка `#`, закреплённые
   колонки, кастомный скроллбар, подсветка строк. Отдельная спека, после Спеки 2.

## Решённые вопросы

- **Часовой пояс** — хранится как фиксированный сдвиг от UTC в минутах
  (`timezone_offset_minutes`, например `+180` для GMT+3), не IANA-зона. Без
  летнего/зимнего времени и без библиотек часовых поясов — админ выбирает
  дату/время в своём поясе, фронт переводит в UTC перед отправкой.
- **Квота сундуков** (`target_chests`) считается только по сундукам,
  отмеченным конкретным кланом как «квотные» — **новый переключатель**
  в существующей таблице сундуков кабинета (рядом с «В паттерне»), не
  хардкод по названию/catalog_id. Сама логика подсчёта квоты — Спека 2;
  здесь только переключатель в модели данных (`ChestConfiguration`).
- Все новые поля **nullable**, без backfill. `NULL`/не настроено = функция
  выключена для этого клана — публичная страница (до Спеки 2/3) ведёт себя
  как сейчас, никаких изменений для кланов без сезона.

## Бэкенд (`server/chest_dashboard.py`)

### `GET /web/dashboard/chests`

В сериализацию каждого `collector` в `get_dashboard_chests` добавляются 5
полей сезона as-is (даты — ISO-строки через стандартную FastAPI/Pydantic
сериализацию `datetime`, без отдельного форматирования).

### Существующая таблица сундуков — переключатель квоты

`RowIn`/`RowsPayload` (используются в `POST /web/dashboard/chests/rows`)
получают новое поле `counts_toward_quota: bool = False`; `post_dashboard_rows`
передаёт его в конструктор `ChestConfiguration` рядом с `is_in_pattern`.
`_collector_rows` (чтение) тоже включает это поле в каждую строку ответа.
Full-replace семантика не меняется — это просто ещё одно поле строки,
как `is_in_pattern`.

### Новый `PATCH /web/dashboard/chests/{slug}/season`

```python
class SeasonSettingsPayload(BaseModel):
    timezone_offset_minutes: Optional[int] = None
    period_start: Optional[datetime] = None
    period_end: Optional[datetime] = None
    target_points: Optional[int] = None
    target_chests: Optional[int] = None
```

Частичное обновление: только переданные (не-`None`) поля записываются —
если клиент не отправил поле, существующее значение в БД не трогается (то
есть `None` в payload означает «не менять», а не «очистить»; очистка
конкретного поля в этой версии не предусмотрена — не запрошена владельцем,
сезон один раз настраивается и продлевается/двигается, а не сбрасывается
в пустоту). Валидация даты: вычисляется **эффективная** пара
`effective_start`/`effective_end` — новое значение из payload, если оно
передано, иначе текущее значение в БД у этого коллектора. Если оба
эффективных значения не `None` и `effective_end <= effective_start` —
`400`, запись не происходит (защищает и от одновременной отправки обоих
полей с неверным порядком, и от частичного обновления одного поля, которое
конфликтует с уже сохранённым другим). Owner-check — как у всех остальных
ручек, через `_get_own_collector(db, slug, user)`.

## Кабинет (`web/src/pages/ChestsPage.jsx`)

Новая карточка «Настройки сезона» — отдельный `<div className="card">` над
блоком вкладок «Сундуки/Игроки» внутри карточки коллектора (видна сразу, не
под вкладкой):

- `<select>` часового пояса — список стандартных смещений UTC-12:00 до
  UTC+14:00 с шагом 30/45 минут где это реально существующие зоны
  (значения в минутах: ..., -720, ..., -180, ..., 0, ..., 180, ..., 330,
  345, ..., 840), подпись вида `UTC+3:00`.
- Два `<input type="datetime-local">` — начало/конец периода. Значение,
  введённое админом, интерпретируется как локальное время в выбранном
  поясе; перед отправкой на сервер фронт конвертирует его в UTC ISO-строку
  с учётом выбранного смещения (`new Date(localValue).getTime() -
  offsetMinutes * 60000`, либо эквивалент через явное построение UTC-таймстампа).
- Два `<input type="number">` — «Цель (очки)», «Цель (сундуки)».
- Кнопка «Сохранить» → `api.dashboardChestsSeason(slug, payload)` →
  `PATCH /web/dashboard/chests/{slug}/season`.

В существующей таблице сундуков (вкладка «Сундуки») добавляется ещё один
toggle-switch столбец «Считать в квоту» рядом с «В паттерне», тот же
визуальный компонент `.toggle-switch` из предыдущего редизайна.

## Вне рамок (Спека 2/3)

- Сама фильтрация публичной сводки по `period_start`/`period_end`.
- Подсчёт `target_chests` только по сундукам с `counts_toward_quota=true`.
- Передача `targets`/дат в публичный JSON, таймер, цвета строк, колонка `#`.

## Тестирование

- Backend: pytest на `GET` (поля сезона в ответе), `PATCH .../season`
  (частичное обновление, валидация `period_end > period_start`, 403 на
  чужой коллектор), и на `POST /rows` (новое поле `counts_toward_quota`
  сохраняется и читается обратно).
- Frontend: живая проверка в браузере — ввод дат в своём поясе, сохранение,
  персистентность после F5, новый toggle в таблице сундуков.
