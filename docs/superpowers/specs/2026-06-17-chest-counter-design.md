# Сундуки — модуль подсчёта и учёта (дизайн)

Дата: 2026-06-17

## Контекст

Источник идеи — мастер-план Джемини (`docs/Входящие_Gemini.md`, 2026-06-17), описывающий
полную трёхуровневую систему (клиент-сборщик → сервер → веб-дашборд). Этот документ фиксирует
только клиентскую часть, реализуемую сейчас: распознавание и локальный учёт сундуков клана,
встроенный в основной GUI бота.

Скриншот целевого экрана: `Сундуки_1.png` (диалог «Мой клан → Подарки»).

Архитектурная база — Фаза 2 (`tournament_reader.py`): HSV-поиск рамки диалога, построчный OCR,
`clean_name` для очистки распознанных имён. Отличие: здесь список не скроллится — после клика
«Открыть» верхняя строка исчезает и все нижние сдвигаются вверх сами, поэтому скролл/`matchTemplate`
не нужны вовсе.

## Экран игры

«Мой клан → Подарки»: список строк, каждая содержит иконку, тип сундука (например, «Сундук
Эпического Монстра»), строку «От: <имя>», таймер истечения и зелёную кнопку «Открыть». Внизу —
отдельные кнопки «Удалить просроченные» и «Получить сундуки» (массовый сбор) — в этой версии
не используются: модуль кликает только по кнопке «Открыть» верхней строки.

## Алгоритм сбора (без скролла)

1. Найти рамку диалога (`detect_dialog_bbox`, HSV — откалибровать по аналогии с
   `tournament_reader.detect_dialog_bbox`, цвет рамки уточнить на `Сундуки_1.png`).
2. OCR верхней строки: тип сундука + имя после «От: » (теми же приёмами, что в `tournament_reader`:
   psm/threshold подбор, `clean_name`-регулярки для артефактов OCR — без alias-словаря).
3. Найти кнопку «Открыть» в верхней строке через существующий `button_finder.find_colored_button(
   ..., color='green')`, ограничив область поиска верхней строкой.
   - Кнопка не найдена → список пуст → стоп, показать итог.
4. Кликнуть на найденную позицию (анти-детект: смещение 5–8px, пауза 0.4–0.9с).
5. Записать прочитанную строку в локальный SQLite (см. ниже) и обновить live-счётчик в GUI.
6. Повторить с шага 1.

Остановка: ESC (стандартный паттерн `_esc_stopped`/`after_cancel` проекта) или конец списка (шаг 3).

## Локальное хранилище — SQLite (`chest_buffer.db`)

Каждая прочитанная запись пишется немедленно (защита от потери данных при крашах,
накопление между сессиями до отправки):

```
local_chests:
  id              PRIMARY KEY
  raw_player_name TEXT   -- как распознал OCR, очищенный clean_name, без alias-маппинга
  chest_type      TEXT
  timestamp       TEXT
  is_synced       BOOLEAN DEFAULT 0
```

## GUI — вкладка «СУНДУКИ»

Позиция в порядке вкладок: СКЛЕПЫ → БИРЖИ → **СУНДУКИ** → РЕФЕРАЛЫ → КАЛИБРОВКА.

Элементы:
- Поля ввода «Королевство» и «Название клана» (сохраняются в конфиге, как в Фазе 0/2).
- Кнопка «Старт»: требует, чтобы диалог «Мой клан → Подарки» был уже открыт пользователем
  вручную (`detect_dialog_bbox` не находит рамку → ошибка в интерфейсе, без автозапуска диалога
  ботом). Сбрасывает live-счётчики текущей сессии в 0 (SQLite не трогает).
- Live-список «Тип сундука: N шт», обновляется в реальном времени по мере открытия.
- Кнопка «Стоп» / ESC.
- Кнопка «Отправить на сервер»:
  1. Проверка локального/серверного баланса (`auth`-паттерн, как `spend_credit`).
  2. Списание 10 алмазов.
  3. Выборка всех `is_synced=0` из `chest_buffer.db`, формирование JSON-пакета
     `{kingdom, clan, timestamp, items: [{chest_type, raw_player_name, timestamp}, ...]}`.
  4. POST на `/api/v1/chests/import` (endpoint пока не существует — ожидаемо 404, как у
     `tournament_reader`/`clan_roster_reader`; обрабатывается как известное текущее ограничение,
     без дополнительного JSON-fallback файла — данные уже защищены в SQLite).
  5. При HTTP 200 — пометить отправленные записи `is_synced=1`.
  Отправлять можно в любой момент и с любой частотой (хоть раз в час) — это не противоречит
  серверной агрегации.

## Серверная часть (вне рамок этой реализации, контекст на будущее)

Сервер копит очки клана за фиксированный 2-недельный «турнирный» период (как турнирная таблица
сундуков). По истечении периода данные архивируются, счётчики обнуляются, начинается новый период.
Это бизнес-логика бэкенда — реализуется отдельно, когда появится сам endpoint
`/api/v1/chests/import`. Привязка ценности сундуков к очкам — через глобальные неизменяемые
паттерны (Джемини, второе сообщение во входящих) — тоже отдельный будущий шаг, не входит в эту
спеку.

## Из мастер-плана Джемини — отложено на будущее (не в этой реализации)

- Alias Map (Identity Resolution) — связывание вариантов ника с каноническим именем: делает
  админка на сайте, не клиент.
- Раздел «Сундуки» в админке (матрица ценности, паттерны очков).
- Публичный дашборд клана.
