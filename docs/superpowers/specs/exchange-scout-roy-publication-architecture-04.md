## Стадия 4. Design

**4.0 Порядок обработки одной находки.** Предпосылка из спек №2 и №3 (не определяется здесь): по спеке №3 (C-12: OCR-координаты входят в строку журнала) и спеке №2 (4.8, C-17(c): списание строго после записи строки) кадр сохранён в `found/<sid>/` → OCR (`coords_ok`) → строка `scout_results.jsonl` с `fsync` → списание 10◆ (`charged`) → публикация (P-01: только при `charged is True and coords_ok is True`). **Требование этой спеки (P-06):** `K` захватывается в момент создания результата, после успешного OCR, и входит в объект результата (в памяти consumer'а) до записи строки журнала; далее значение K не перечитывается из GUI. Итоговая цепочка: **кадр → OCR → захват K → результат(K, X, Y) → `fsync` журнала → списание → публикация (успешная или неуспешная) → удаление кадра** (порядок «обработка → передача результата в публикацию → удаление кадра»; исход публикации на удаление не влияет — кадр удаляется и при `PUBLISH_FAILED`, повтор публикации не делается, P-08). Место «показа находки пользователю» определяют спека №2 (матрица исходов) и Часть A. Продуктовая цепочка владельца (Stage 1) — описание, а не порядок вызовов: OCR в реализации идёт до записи журнала, потому что координаты — часть записи. **Эта спека не переопределяет и не ослабляет порядок `fsync журнала → списание`, заданный C-17(c) спеки №2** — он остаётся обязательным межспековым prerequisite, на который прямо опирается 4.6 (запись уже существует к моменту списания). Сверх этого prerequisite и P-01/P-06 данная спека добавляет ровно одно требование к порядку — своё, P-08 (`fsync` журнала строго раньше запуска публикации); других требований к порядку эта спека не предъявляет.

**4.1 Данные.** Таблица `roy_scout_finds`: `id` (PK), `kingdom` (Integer, без индекса — `GET /roy/scout-finds` не фильтрует по `kingdom`), `x`, `y` (Integer),
`reporter_hwid` (String(16), для админской трассировки, наружу не отдаётся), `found_at`
(`TIMESTAMP(timezone=True)`, `server_default=func.now()` как fallback; штатная вставка **обязана явно передавать `found_at=now`** (P-13), `server_default` в TTL-логике не участвует; индекс по `found_at` — единственный индекс таблицы, нужен и `SELECT`, и `DELETE` в P-13). Типы — по образцу `RoyPool` (`models.py:279-289`). Без `UNIQUE` (P-04).

**4.2 Серверные эндпоинты (в `server/roy.py`, router `/roy`).**
- `POST /roy/scout-find` — тело `{hwid, kingdom, x, y}`. Шаги: найти пользователя → 404/403 (P-05) → удалить строки
  с `found_at <= now − 30 мин` (P-13; `now` — только `datetime.now(timezone.utc)`, aware UTC) → вставка строки → `commit` → `{"success": True}`. Одна транзакция, `async with db.begin()` как в остальном файле.
  SSE не трогается.
  **Ограничение реализации (ANTI-PATTERNS, Хангоф #70):** любой SELECT до входа в `async with db.begin()` (в т. ч. в dependency) запускает autobegin и даёт `InvalidRequestError`. У `scout-find` единственная dependency — `get_db` (открывает сессию, SQL не выполняет: `database.py:35-44`); поиск пользователя, удаление и вставка выполняются ВНУТРИ одного блока `async with db.begin()` — как в `/roy/report` (`roy.py:265`) и `/use_credit` (`main.py:315`). `begin_nested()` не нужен.
- `GET /roy/scout-finds` — публичный список, не более 500 самых новых (P-09).

**4.3 Клиент.** В `roy/roy_client.py` — новый метод `report_scout_find(kingdom, x, y)`; существующие методы не
меняются. Вызывается consumer'ом 2.0 после OCR (Часть B определит точку вызова).

**4.4 Сайт.** Новый блок под списком королевств в `RoyPage.jsx`: заголовок, поясняющая строка (P-11), список
`K · X · Y · время`, кнопка «Обновить», пустое состояние.

**4.5 Внешние вызовы и отказы** (A — ошибка, B — зависание, C — повтор, D — дважды, E — частично, F — параллельно):

| Вызов | A | B | C | D | E | F |
|---|---|---|---|---|---|---|
| `POST /roy/scout-find` из клиента | лог, находка остаётся локально (P-08) | `timeout=5` `requests` (5 с на подключение и 5 с на чтение отдельно, суммарного лимита нет) — тред не гарантированно завершается за 5 с, consumer при этом не блокируется (P-07, PA-7) | повтора нет (non-goal) | две строки — решение владельца (P-04) | транзакция БД атомарна: строка есть или нет | два процесса 2.0 одного hwid — две независимые вставки, конфликтов нет |
| `GET /roy/scout-finds` с сайта | блок показывает пустое состояние/ошибку | браузерный таймаут по умолчанию | безопасен (read-only) | безопасен | — | безопасен |

**4.6 Состояния публикации одной находки** (после успешного списания и успешного OCR; порядок шагов — 4.0).
**Состояния логические, для описания цепочки — ни одно из них не персистируется** (не пишется в
`scout_results.jsonl`, не хранится на сервере); это не state machine с точкой хранения, а способ говорить о
моменте цепочки. `READY_TO_PUBLISH → PUBLISH_SENT → {PUBLISHED | PUBLISH_FAILED}`; пропуски: `SKIPPED_NO_KINGDOM |
SKIPPED_NOT_CHARGED | SKIPPED_NO_COORDS`. Переходы вперёд необратимы. Краш процесса между списанием и
`PUBLISH_SENT`: кредит списан, `scout_results.jsonl` уже содержит запись к моменту списания (C-17(c) спеки №2) и
обязательно содержит её до запуска публикации (P-08), публикация не выполнена и **при рестарте не доигрывается** (нет
журнала повторов — non-goal).

**4.7 Non-goals (явно вне документа).** Восстановление публикации после рестарта; хранение `kingdom` в `scout_results.jsonl`; серверная привязка публикации к списанию (PA-5); Публикация изображения/кропа мини-карты (в `CLAUDE.md` запрещено
хранить файлы на GCP; в цепочке владельца только координаты); повтор неудачной публикации; дедупликация;
live-обновление сайта через SSE; уведомления/звук у других пользователей; сортировка/фильтры на сайте;
правка Части A (`scout_results.jsonl` не получает новых полей).
