## Часть A — Fallback на PlayerProfile (предпосылка для Части Б)

### Проблема

`PlayerProfile` — общая таблица «звание + состав войск» на `(collector_id,
canonical_name)`, уже используемая публичной страницей Сундуков
(`POST /api/v1/chests/public/player-profile`, кулдаун 15 мин на повторную
запись). `ancients_dashboard.py._roster_rows` уже подставляет
`PlayerProfile.troop_level` как fallback, когда `AncientRoster.troop_level`
пуст — но:
- `rank` такого fallback не имеет вообще, ни в `_roster_rows`, ни где-либо ещё;
- `calculate()` (реальный расчёт квоты, Стратегия Б) строит список игроков из
  `AncientRoster.troop_level` напрямую, без fallback на `PlayerProfile`.

Итог: игрок, заполнивший данные впервые именно на публичной странице
Древнего (а не Сундуков), либо не увидит звание в кабинете лидера вообще
(нет fallback), либо увидит состав войск в кабинете, но он не попадёт в
реальный расчёт квоты Стратегии Б.

### Решение

**A1. `_roster_rows` (`server/ancients_dashboard.py`)** — добавить
`PlayerProfile.rank` в тот же `outerjoin`, что уже тянет `profile_troop`, и
использовать `r.AncientRoster.rank or r.profile_rank` — по тому же паттерну,
что уже применён к `troop_level`.

**A2. `calculate()`, Стратегия Б (`server/ancients_dashboard.py`)** — при
построении списка `players` для `split_strategy_b` подмешивать
`PlayerProfile.troop_level` тем же способом: для каждой строки ростера, если
`AncientRoster.troop_level` пуст — брать значение из `PlayerProfile` по
`canonical_name == player_name` (с учётом уже существующего разрешения через
`mapped_names`, если строка ещё не физически слита).

Стратегии А это не касается: она распределяет уже введённые лидером
`officer_count`/`veteran_count` (агрегированные числа, не per-row), per-row
`rank` используется только в `_roster_rows` для отображения — этого
покрывает A1.

## Часть Б — Публичная страница «Древнего»

### Бэкенд

**Новый файл `server/ancients_public.py`**, роутер
`prefix="/api/v1/ancients/public"`, один эндпоинт:

```
GET /api/v1/ancients/public/{slug}
```

Без авторизации, 404 если `ChestCollector` с таким `slug` не найден (не
зависит от `ancient_hidden` — это приватная настройка отображения в личном
списке владельца, на публичный доступ не влияет, как и было явно
задокументировано при добавлении этого флага).

Возвращает:
```json
{
  "kingdom": "...", "clan": "...",
  "quota_thresholds": {"light_pct": ..., "medium_pct": ..., "critical_pct": ...},
  "roster": [
    {"player_name": "...", "rank": "...", "troop_level": "...",
     "points": ..., "quota": ..., "shortfall_pct": ...}
  ]
}
```

Логика формирования `roster` — упрощённый, публично-безопасный вариант
`_roster_rows`: те же fallback на `PlayerProfile` (A1/A2) и та же quota-lookup
логика (Стратегия А/Б по последнему `AncientCalculation`), но **без**
`raw_ocr_name`, `mapped_name`, `suggested_name`, `mapping_confirmed` —
механика маппинга сырых OCR-имён остаётся исключительно внутренним
инструментом лидера в кабинете, наружу не выставляется. Реализуется как
отдельная функция в новом файле (не переиспользует `_roster_rows` напрямую
— пересекающаяся, но не идентичная логика; дублирование fallback-паттерна
и quota-lookup осознанное, ради простоты и чтобы не тащить
mapping-специфичные параметры в публичный путь).

**Запись данных** — новых эндпоинтов не создаём. Публичная страница
Древнего использует **тот же самый** `POST /api/v1/chests/public/player-profile`
(файл `server/chests.py`), с тем же `collector_slug` (коллектор общий с
Сундуками) и тем же `canonical_name` = `AncientRoster.player_name` строки, по
которой игрок редактирует. Кулдаун 15 минут, вся валидация — уже готовые,
без изменений.

### Фронтенд

- Новый роут `/ancients/:slug` → `PublicAncientsPage.jsx` (по образцу
  `ChestSummaryPage.jsx`, но проще — без вкладки истории, без сезонных
  таймеров, которых у Древнего нет).
- Таблица `AncientPublicTable.jsx` — колонки № | Имя | Звание | Войска |
  Очки | Квота | Недобор. Звание и войска — те же селекторы, что в
  `ChestSummaryTable.jsx` (`RANKS`, `TIERS`), кнопка сохранения 💾 → ✓ на 3
  сек, `alert()` при 429 (кулдаун) — идентичный UX, без каких-либо новых
  «замочков» (в коде Сундуков их нет, см. предыдущее ревью). Колонка
  «Недобор» подсвечивается по `quota_thresholds` — переиспользуем
  `rowShortfallClass` (сейчас живёт в `AncientsPage.jsx`, выносится в общий
  модуль, например `web/src/lib/ancientQuota.js`, чтобы не дублировать).
- API-хелперы (`web/src/api.js`): `fetchAncientsPublic(slug)` — новый;
  `postPublicPlayerProfile` — уже существует, переиспользуется как есть.

### Личный кабинет

- `GET /web/dashboard/ancients` — добавить `public_url:
  "https://total-hunter.com/ancients/{slug}"` на каждый коллектор (по
  аналогии с `chest_dashboard.py:253`).
- `AncientsPage.jsx` — блок со ссылкой на публичную страницу, по образцу

  реальном коде Сундуков, а не как подписано в письме Gemini).

## Вне рамок

- «Красивый» URL вида `/a/{kingdom}/{slug}` (аналог `/c/{kingdom}/{slug}` у
  Сундуков) — явно не запрошен в исходном ТЗ (там указан только `/a/{slug}`
  вариант), не делаем ради YAGNI. Можно добавить отдельной задачей позже.
- Улучшение маппинга сырых OCR-имён для кланов без Сундуков (у них
  `canonical_names` пуст, дропдаун «Правильное имя» в кабинете нефункционален)
  — реальная смежная проблема, обнаруженная при исследовании, но не часть
  этого ТЗ. Публичная страница просто показывает текущее состояние
  `AncientRoster.player_name` как есть (сырое или уже слитое).
