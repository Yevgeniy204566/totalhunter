## Стадия 2. Code Archaeology — что реально есть в коде

Всё ниже открыто и прочитано лично. Утверждения о коде без цитаты файла/строки в этом документе отсутствуют.

### 2.1 `PositionReader` — `navigator.py:30-74`

```python
class PositionReader:
    def __init__(self, crop_box: tuple[int, int, int, int] = (0, 1000, 250, 1080)):
        self.crop_box = crop_box
        self._pattern = re.compile(r'X\s*[:]\s*(\d+)\s+Y\s*[:]\s*(\d+)', re.IGNORECASE)
    ...
    def read(self, screenshot_np: np.ndarray) -> tuple[int, int] | None:
```

Факты, извлечённые из кода (не из предположений):

1. **Королевство (K) НЕ читается.** Регэксп (`navigator.py:33`) захватывает ровно две группы — X и Y.
   `_parse_ocr` (`navigator.py:42-49`) возвращает `(int(m.group(1)), int(m.group(2)))`. Никакого `K`.
   Для сравнения: `K` умеет читать другой, отдельный компонент — `roy/exchange_reader.py`
   (`docs/exchange_bot_spec.md:145` — `return {'kingdom':K, 'x':X, 'y':Y, 'percent':P}`), и он читает
   **открытый диалог биржи**, которого в 2.0 нет, потому что в 2.0 нет клика.
2. **Возврат:** `tuple[int, int] | None`. `None` означает одновременно «текста не было» и «OCR не смог» —
   различить нельзя: `read()` целиком обёрнут в `except Exception: return None` (`navigator.py:73-74`).
3. **Стоимость вызова:** 4 варианта кропа × 2 варианта препроцессинга × 3 psm-конфига
   (`navigator.py:57-70`) = **до 24 вызовов `pytesseract.image_to_string` на один кадр** в худшем случае
   (когда координаты не распознаются вообще). Ранний выход — на первом успехе.
4. **Таймаута нет.** В отличие от ROY-пайплайна (`docs/exchange_bot_spec.md:226` — «pytesseract timeout=3
   (бот не зависает)»), `PositionReader` вызывает `image_to_string` без `timeout=`.
5. **Доказанный формат входа — 4-канальный BGRA от `mss`, без конвертации.** Единственный живой
   потребитель `PositionReader` в проекте — `calibration.py:29,36` — кормит его результатом
   `calibration.py:17-21`:

   ```python
   def grab_screen() -> np.ndarray:
       with _mss() as sct:
           monitor = sct.monitors[1]
           return np.array(sct.grab(monitor))      # BGRA, 4 канала, БЕЗ cvtColor
   ```

   А `read()` делает `Image.fromarray(screenshot_np)` (`navigator.py:54`), то есть PIL интерпретирует
   эти байты как RGBA. **Красный и синий каналы фактически переставлены — и именно в таком виде OCR
   работает сегодня.** Это не косметика: кадр `PacmanEngine` — трёхканальный BGR после
   `cv2.cvtColor(screen, cv2.COLOR_BGRA2BGR)` (`navigator.py:1012`), то есть **другая** подача каналов.
   Прямое следствие для 2.0 — контракт C-11 ниже.
6. **`crop_box` не масштабируется `coord_manager`.** В `navigator.py` нет ни одного упоминания
   `coord_manager` (проверено грепом по файлу). Первые три кропа — абсолютные пиксели эталона 1920×1080,
   четвёртый (`navigator.py:61`) привязан к высоте кадра `h` и потому переживает другое разрешение.
   `calibration.py:29` использует доказанный на практике `crop_box=(0, 990, 300, 1080)`.

### 2.2 `CoastalSnakeNavigator` — `navigator.py:421-923`

Реальная сигнатура конструктора (`navigator.py:439-456`, приведены значимые для 2.0 параметры):

```python
class CoastalSnakeNavigator:
    DIVE_DEPTH_CAP = 10  # потолок роста глубины нырка — максимум GUI-ползунка   (navigator.py:437)

    def __init__(self, center_x=90, center_y=925, step=13,
                 max_inland_steps=5, ocean_land_ratio=0.03, min_water_px=500,
                 homing_max_steps=10, smooth_alpha=0.5, footprint_ttl=120.0,
                 footprint_enabled=True, pixels_per_step=20, force_shift_after=0,
                 diagonal_blind_coeff=0.5, coast_detect_radius=50, return_delta_px=0):
```

Главный шаг (`navigator.py:808`):

```python
    def step(self, is_water: bool = False, frame=None) -> bool:
```

Сброс состояния (`navigator.py:502`): `def reset(self):` — переводит в `HOMING`, обнуляет счётчики,
`self._footprint.reset()`.

**Проверка утверждения владельца про `max_inland_steps=50` — подтверждено кодом, не принято на веру:**

- Конструктор присваивает значение напрямую: `self.max_inland_steps = max_inland_steps`
  (`navigator.py:465`). **Клэмпа к `DIVE_DEPTH_CAP` в конструкторе нет.**
- `DIVE_DEPTH_CAP` фигурирует ровно в одном месте — `_maybe_grow_dive_depth` (`navigator.py:629`):
  `while now >= self._dive_growth_next_at and self.max_inland_steps < self.DIVE_DEPTH_CAP:`.
  При `max_inland_steps=50` второе условие ложно с первой итерации → тело цикла не исполняется,
  значение **не понижается** и бесконечного цикла не возникает (условие короткозамкнуто по `and`).
- Производные величины на глубине 50: `_return_steps = max_inland_steps + 15` = 65 (`navigator.py:876`),
  `_return_blind_steps = round((max_inland_steps - 3) * blind_factor)` ≤ 47 (`navigator.py:885-887`).
  Модульная константа `MAX_STEPS_SAFETY = 80` (`navigator.py:85`) используется только в `CompassNavigator`
  (`navigator.py:379,401`) — на `CoastalSnakeNavigator` не влияет, то есть 65 < 80 её и не задевает.

**По прямому указанию владельца число 50 не превращается в отдельную тему и не получает собственного
smoke-теста поведения цикла** — это то же самое, уже оттестированное поведение с другим числом итераций.
Единственная проверка — одна строка `assert nav.max_inland_steps == 50` в тесте конструирования (T-16).

### 2.3 `PacmanEngine` — `navigator.py:930-1178` (эталон формы, НЕ изменяется)

```python
    def start(self):                                            # navigator.py:988
        if self._thread and self._thread.is_alive():
            self._thread.join(timeout=3.0)
        if self._yolo_unblock_time <= time.time():
            self._yolo_unblock_time = 0.0
        self.joystick.reset()
        self.is_running = True
        self._thread = threading.Thread(target=self._run, daemon=True)
        self._thread.start()

    def stop(self):                                             # navigator.py:999
        self.is_running = False
```

Два факта, важных для контракта 2.0:

- `start()`/`stop()` — **без аргументов**; все параметры принимаются в `__init__` (`navigator.py:931-959`).
- `stop()` **не джойнит поток**. Он только выставляет флаг; фактический джойн отложен до следующего
  `start()` (`navigator.py:989-990`). То есть возврат из `PacmanEngine.stop()` НЕ означает, что поток
  завершился. Слепо копировать эту слабость в 2.0 нельзя — 2.0 владеет файлами на диске, а не только
  кликами (см. контракт C-05 и его честное ограничение).

Вызов YOLO — дословно (`navigator.py:1025-1026`, идентичный второй вызов в `_fresh_scan`,
`navigator.py:1092-1093`):

```python
                        results = self.yolo_model.predict(
                            frame, conf=self.conf, imgsz=1280, verbose=False)
```

Разбор результата (`navigator.py:1028-1032`): `for r in results: if len(r.boxes) > 0: ... r.boxes[0]`.
У бокса используются `box.conf[0]` (`navigator.py:1078`) и `box.xyxy.cpu().tolist()[0]`
(`navigator.py:1116`).

Захват кадра (`navigator.py:1007-1012` и `1061-1062`):

```python

        with mss() as sct:
            monitor = sct.monitors[1]
            screen  = np.array(sct.grab(monitor))
            frame   = cv2.cvtColor(screen, cv2.COLOR_BGRA2BGR)
```

Звук находки (`navigator.py:1127-1131`): `winsound.PlaySound(self.sound_path, SND_FILENAME | SND_ASYNC)`
с запасным `winsound.Beep(1000, 500)`.

### 2.6 `debug_reporter.py` — существующий канал в debug-Telegram (добавлено в раунде 2)

Файл прочитан целиком (87 строк). Для 2.0 значимы шесть фактов, каждый — из кода, не из описания.

1. **Ошибки сети глушатся полностью.** `_send` (`debug_reporter.py:14-24`) целиком обёрнут в
   `try: ... except Exception: pass` (`debug_reporter.py:23-24`). Таймаут — модульная константа
   `_TIMEOUT = 10` (`debug_reporter.py:11`), передаётся в `requests.post` (`debug_reporter.py:21`).
   То есть недоступный сервер, 500, DNS-сбой и таймаут 10 с — все одинаково приводят к тихому `return`,
   без исключения у вызывающего. Это факт кода, а не предположение.
2. **Fire-and-forget — только сетевая часть, и это важно.** `report_find` (`debug_reporter.py:27-56`)
   выполняет **синхронно, в потоке вызывающего**: `frame_bgr.copy()` (строка 29), отрисовку bbox и подписи
   (30-41) и DPI-диагностику, которая лезет за живыми `mss().monitors[1]` и `pyautogui.size()` (42-54).
   В фоновый `threading.Thread(..., daemon=True)` уходит **только** `_send` (`debug_reporter.py:56`).
   Формулировка «report_find не блокирует вызывающего» была бы неточной — блокирует, но на копию кадра и
   два локальных замера, а не на HTTP.
3. **Формат bbox жёсткий.** Отрисовка делает `bbox.xyxy.cpu().tolist()[0]` (`debug_reporter.py:32`), то есть
   ждёт объект бокса YOLO, а не список float. Список из поля `box` записи журнала (4.6) сюда не подойдёт.
   Сбой отрисовки не теряет кадр: он проглатывается (`debug_reporter.py:40-41`), и кадр уходит без рамки.
4. **Исходный кадр не мутируется** — рисование идёт по `img = frame_bgr.copy()` (`debug_reporter.py:29`).
   Значит отправка в Telegram не может испортить кадр, который параллельно пишется/читается с диска.
5. **`hwid` не берётся внутри `debug_reporter`** — он параметр (`debug_reporter.py:14,27,59,77`). Реальный
   источник у 1.0 — ленивый импорт в месте вызова: `from auth import get_hwid` и
   `report_find(get_hwid(), frame, box, conf=_conf)` (`navigator.py:1077,1079`), тот же приём в
   `navigator.py:1139-1140` (`report_dialog`) и `engine.py:253-256` (`report_ocr_result`). Сам `get_hwid` —
   `auth.py:32-35`: `SHA256(str(uuid.getnode()))[:16].upper()`, без сети и без кэша. Оба вызова в
   `navigator.py` дополнительно обёрнуты в `try/except Exception: pass` (`navigator.py:1075-1081`,
   `1137-1142`) — то есть даже падение импорта не роняет охоту.
6. **`shot_type` сервером НЕ валидируется.** Приёмник — `server/debug_router.py:19-49`; поле объявлено как
   свободная строка `shot_type: str = Form(...)` (`debug_router.py:23`, комментарий `# "FIND" | "DIALOG"` —
   это комментарий, а не проверка). Значение попадает только в подпись сообщения (`debug_router.py:36`) и в
   одно условие: строка «🎯 Точность» добавляется, **только если `shot_type == "FIND"`**
   (`debug_router.py:35`). Практическое следствие для 2.0: новый тип снимка можно ввести **без изменения и
   деплоя сервера**, но `conf` отобразится только под типом ровно `"FIND"`.

### 2.7 Монетизация 1.0 — точная цепочка (добавлено в раунде 2)

Владелец потребовал для 2.0 «точно такую же логику, что и 1.0». Цепочка 1.0 прослежена по коду целиком,
звено за звеном, чтобы «такая же» означало проверенное, а не правдоподобное:

1. **Гейт на старте:** `toggle_bot()` → `if self.current_credits <= 0: messagebox.showwarning(...); return`
   (`main.py:3574-3575`) — до любой инициализации движка (`engine.start(...)` идёт ниже, `main.py:3587`).
2. **Привязка callback'а:** `self.engine.on_found_callback = self.on_target_found` (`main.py:1600`) →
   `self._pacman.on_found_callback = self.on_found_callback` (`engine.py:203`; при включённом ROY — тот же
   callback внутри обёртки, `engine.py:201`, `236-245`).
3. **Момент вызова:** `PacmanEngine` зовёт его последним шагом обработки находки —
   `if self.on_found_callback: self.on_found_callback()` (`navigator.py:1145-1146`), то есть **после**
   повторного подтверждающего скана `_fresh_scan()` и **после** фактического клика. Обе ранние ветки
   «биржа не подтвердилась» (`navigator.py:1112`) и «клик не удался» (`navigator.py:1124`) возвращаются
   `return` до этой строки — кредит в этих случаях не тратится.
4. **Списание:** `on_target_found` → `self.after(0, self._process_found)` (`main.py:3751-3753`) →
   `res = spend_credit("exchange")` (`main.py:3759`).
5. **Контракт `spend_credit`** (`auth.py:106-124`): POST `/use_credit` с `timeout=5` (`auth.py:114-118`),
   `_mark_contact_success()` при любом ответе (`auth.py:119`), при HTTP 402 —
   `{"success": False, "low_credits": True, ...}` (`auth.py:120-121`), при сетевом сбое —
   `{"success": False}` (`auth.py:123-124`). Цена биржи — 10 кредитов (`auth.py:109`).
6. **Реакции GUI** (`main.py:3760-3767`), ровно три ветки: успех → обновить счётчик; `low_credits` →

## Стадия 4. Design

### 4.1 Структура на диске

```
<app_dir>/scout_sessions/
├── pending/                       ← сносится ЦЕЛИКОМ при каждом start() (C-02)
│   └── 2026-09-18_14-32-05_a3f1/
│       ├── 000001.jpg
│       └── 000002.jpg
├── found/                         ← НЕ чистится автоматически никогда (C-03)
│   └── 2026-09-18_14-32-05_a3f1/
│       ├── 000123.jpg
│       └── scout_results.jsonl
└── errors/                        ← лежит рядом с found/, тот же режим хранения
    └── 2026-09-18_14-32-05_a3f1/
        └── 000077.jpg
```

**Почему папка сессии, а не плоский `found/`.** Счётчик кадров начинается с нуля в каждой сессии
(C-06). При плоском `found/` кадр `000123.jpg` второй сессии затёр бы кадр `000123.jpg` первой — то есть
автоматическая потеря результата, прямо противоречащая C-03. Изоляция папкой сессии закрывает это
структурно, без зависимости от того, угадали ли мы уникальность имени.

**Почему `errors/` — отдельная ветка, а не удаление.** Кадр, на котором consumer упал (битый JPEG,
исключение YOLO), — это диагностическая улика. Удалять её значит терять единственный след. Режим хранения
тот же, что у `found/` (ручная очистка), и это **не создаёт нового неограниченного роста**: суммарное
число кадров в `errors/` не может превысить число кадров, произведённых producer'ом за сессию, то есть
ту же границу, что у `pending/`. Отдельный числовой лимит не вводится — он был бы выдуманным числом без
необходимости.

**Имя сессии.** `YYYY-MM-DD_HH-MM-SS_xxxx`, где `xxxx` — 4 hex-символа из `os.urandom(2)`. Секундной
метки одной было бы недостаточно: два старта в одну и ту же секунду (двойной клик по кнопке) дали бы
один `sid` на две сессии. Суффикс убирает это без рассуждений о вероятности.

**Формат кадра.** JPEG (задано владельцем). Качество — **параметр по умолчанию библиотеки OpenCV
(`IMWRITE_JPEG_QUALITY = 95`)**, то есть осознанный отказ от подбора собственного числа: берётся
документированный дефолт инструмента, а не «подкрученное» значение. Обоснование именно такого выбора:
цель кадра — пережить повторный `YOLO.predict(imgsz=1280)` и OCR мелкого HUD-текста, а оба этих
потребителя чувствительны к JPEG-артефактам; дефолт 95 — наименее разрушительная из общепринятых
настроек. Оценка объёма: 1920×1080 q95 ≈ 0.4-0.7 МБ/кадр; «прикидочные ~200 кадров» владельца — это
≈ 80-140 МБ на сессию. **Число 200 нигде в коде не появляется** — ни как константа, ни как лимит очереди,
ни как размер буфера (требование владельца). Это единственный технический дефолт Части A, который стоит
подтвердить одной строкой на ревью.

### 4.2 Инварианты состояния и владение

| Ресурс | Владелец | Кто ещё пишет |
|---|---|---|
| `pending/<sid>/*.jpg` | producer (создаёт), consumer (удаляет/переносит) | никто |
| `found/<sid>/*.jpg` | consumer | никто; удаляет только пользователь вручную |
| `found/<sid>/scout_results.jsonl` | consumer — **единственный писатель** | никто |
| счётчик кадров | producer | никто |
| `active_mode` в GUI | главный тред Tkinter | фоновые треды пишут только через `self.after(0, ...)` |

Состояния сессии: `IDLE → STARTING → RUNNING → STOPPING → IDLE`. Переход `STARTING → IDLE` (сбой C-04)
не оставляет следов в `found/`. Переход `RUNNING → STOPPING` инициируется кнопкой, ESC или C-15.

**Поведение при повторном запуске и после краша.** Недообработанные кадры прошлой сессии никогда не
дообрабатываются: они гарантированно уничтожаются следующим `start()` (C-02). Это сознательное решение
владельца («биржи живут недолго»), и оно же — причина, по которой уборка привязана к старту, а не к
стопу: крашнувшийся процесс не может выполнить уборку на выходе, а старт может.

### 4.4 Контракт `ExchangeScoutEngine` (`exchange_scout.py`, новый файл)

Форма симметрична `PacmanEngine` (`navigator.py:988-1000`): **все параметры — в конструкторе,
`start()`/`stop()` без аргументов**. GUI создаёт новый экземпляр на каждый старт — ровно так, как это уже
делает `HuntEngine.start()` с `PacmanEngine` (`engine.py:178-196`).

```python
class ExchangeScoutEngine:
    def __init__(
        self,
        yolo_model,                       # уже загруженная модель (HuntEngine.model)
        conf: float,
        center_x: int, center_y: int, step: int,
        move_wait: float,
        max_inland_steps: int = 50,       # передаётся в навигатор как есть (см. 2.2)
        sessions_root: str | None = None, # None → <app_dir>/scout_sessions
        sound_path: str | None = None,
        position_crop_box: tuple[int, int, int, int] = (0, 990, 300, 1080),
        on_found_callback=None,           # (record: dict) — из фонового треда
        on_progress_callback=None,        # (stats: dict)  — из фонового треда
        on_error_callback=None,           # (message: str) — из фонового треда
        on_credit_callback=None,          # (res: dict от spend_credit) — из фонового треда (C-17)
        # сквозные параметры навигатора, значения по умолчанию совпадают с CoastalSnakeNavigator:
        ocean_land_ratio: float = 0.03, min_water_px: int = 500,
        footprint_ttl: float = 120.0, diagonal_blind_coeff: float = 0.5,
        coast_detect_radius: int = 50, return_delta_px: int = 0,
        smooth_alpha: float = 0.5, pixels_per_step: int = 20,
    ) -> None: ...

    def start(self) -> None: ...
    def stop(self) -> None: ...
```

`position_crop_box` по умолчанию — **не выдуманное число, а значение из `calibration.py:29`**, то есть
единственный крop, доказанный практикой на реальных экранах.

**Что `start()` гарантирует до возврата** (C-04):

1. Сессионный `sid` выделен; `pending/`, `found/<sid>/`, `errors/<sid>/` существуют.
2. Дерево `pending/` снесено целиком, включая осиротевший мусор прошлых сессий (C-02).
3. Права на запись проверены реальной пробной записью (probe-файл создан и удалён), а не предположением.
4. `found/<sid>/scout_results.jsonl` открыт на дозапись.
5. Producer- и consumer-треды созданы и запущены (только факт запуска; их внутреннее поведение — **[→ Часть B]**).
6. `is_running == True`.
7. При сбое любого из шагов 1-4 — исключение, треды не созданы, `is_running == False`, `found/` не тронут.
8. Повторный `start()` без `stop()` на том же экземпляре — `RuntimeError`, новая сессия не создаётся.

**Что `stop()` гарантирует до возврата** (C-05): пункты (a)-(d) из таблицы C-05. Честное ограничение,
которое я не прячу: гарантия «оба треда физически завершились» в Части A **не даётся** — она требует
join/таймаутов, а это Часть B. Часть A даёт более слабую, но проверяемую гарантию: состояние на диске
после возврата из `stop()` консистентно при любом моменте фактического завершения тредов, потому что
(i) журнал дописывается построчно с fsync, (ii) перенос кадра атомарен, (iii) любой недоделанный кадр
остаётся в `pending/` и будет уничтожен следующим стартом. Именно эта композиция — причина, по которой
уборка живёт в `start()`, а не в `stop()`.

### 4.8 Монетизация 2.0 — ЗАКРЫТО решением владельца (раунд 2), контракт C-17

Решение владельца дословно: «списывает кредиты», «точно такая же логика, что и 1.0». Открытый вопрос
раунда 1 снят; ниже — что именно «такая же» означает после сверки с кодом (2.7).

**1. Гейт баланса на старте.** Кнопка старта 2.0 повторяет `if self.current_credits <= 0: warning; return`
(`main.py:3574-3575`) до конструирования движка. Зеркало буквальное, включая источник числа
(`self.current_credits`) и текст предупреждения.

**2. Точка списания — запись находки, а не клик.** В 1.0 точка — подтверждённый клик
(`navigator.py:1145-1146`); в 2.0 клика нет по определению (non-goal 4.9.1), и единственное событие того
же смысла — момент, когда находка становится фактом для владельца: строка в `scout_results.jsonl`.
Порядок внутри обработки находки жёсткий: `os.replace` кадра в `found/<sid>/` → запись строки журнала с
`flush()+fsync()` → **и только потом** `spend_credit("exchange")` → отправки в Telegram (C-18, C-19).

**Почему списание именно ПОСЛЕ записи, а не до.** Крах процесса между двумя операциями возможен в обе
стороны, и направления неравноценны: «оплачено, но не записано» — владелец заплатил за находку, которой
нет ни в журнале, ни в Telegram; «записано, но не оплачено» — владелец получил находку бесплатно.
Первое — потеря денег пользователя из-за дефекта программы, второе — потеря копейки владельца сервиса.
Выбрано направление, которое никогда не берёт деньги за несуществующий результат.

**3. `coords_ok: false` — кредит СПИСЫВАЕТСЯ.** Решено по прямой аналогии с 1.0, а не по вкусу, и вот
основание в коде: `_process_found` (`main.py:3756-3767`) зовёт `spend_credit` **безусловно**, а чтение
координат в 1.0 живёт в полностью отдельной ветке ROY (`engine.py:248-262`) и на списание не влияет —
у 1.0 биржа, найденная и кликнутая, но с нераспознанным диалогом, оплачивается полностью. Содержательное
обоснование того же вывода: оплачивается **находка биржи** (кадр в `found/`, bbox, снимок в Telegram),
а не успех OCR; при `coords_ok:false` владелец всё равно получает кадр и ×4-зум зоны координат (C-19) и
может прочитать их глазами — ровно для этого зум и вводится. Разная цена за одну и ту же находку в
зависимости от удачи tesseract была бы новой, не существующей в 1.0 механикой, то есть нарушением
«точно такой же логики».

**4. Реакции на исход** — те же три ветки, что `main.py:3760-3767`: `success` → обновить счётчик кредитов;
`low_credits` (HTTP 402, `auth.py:120-121`) → остановить сессию 2.0 + открыть страницу пополнения;
иначе при `seconds_since_last_contact() > HEARTBEAT_TIMEOUT` (120 с, `auth.py:20,29-30`) → остановить
сессию + сообщение «offline_stopped». Обычный сетевой сбой (`{"success": False}` без `low_credits`)
сессию не останавливает — так же, как в 1.0.

**5. Единственное намеренное расхождение с 1.0 — тред, а не политика.** В 1.0 `spend_credit` исполняется
в главном треде Tkinter: `on_target_found` делает `self.after(0, self._process_found)` (`main.py:3751-3753`),
а `_process_found` синхронно вызывает блокирующий HTTP с `timeout=5` (`auth.py:114-118`) — то есть GUI 1.0
может замирать до 5 секунд на каждую находку. В 2.0 вызов делает consumer в своём фоновом треде, а в
главный тред через `self.after(0, ...)` уходит только результат. Причина не «так красивее»: (i) документ
уже отказался слепо копировать слабости 1.0 там, где они видны (2.3, про `stop()` без join);
(ii) в 2.0 фоновый тред уже есть, поэтому блокировать GUI нечем оправдать; (iii) правило проекта —
не блокировать основной поток без таймаута; таймаут здесь есть и он чужой, уже существующий (5 с).
Политика оплаты при этом не меняется ни в одном пункте. **Это единственный пункт C-17, который стоит
подтвердить владельцу одной строкой** — на случай, если под «точно так же» он понимал и место вызова.

### 4.10 Канал контроля качества — debug-Telegram (добавлено в раунде 2; C-18, C-19)

Мотив владельца зафиксирован дословно, чтобы позже не выдать его за продуктовое решение: доверия к
YOLO/OCR на новом кадровом материале 2.0 пока нет, поэтому на первом этапе результаты 2.0 идут **владельцу
в Telegram для контроля качества**, а не пользователю как готовый UX («потом будем смотреть, что и как
подавать людям»). Это временный режим наблюдения, и он так и должен быть назван.

**Два сообщения на находку, оба после записи строки журнала и после списания кредита:**

| # | Что уходит | Как | Почему так |
|---|---|---|---|
| 1 | Полный кадр с отрисованным bbox и подписью `CONF: xx.x%` | `report_find(get_hwid(), frame_bgr, box, conf)` — **существующая функция, дословно** (`debug_reporter.py:27`) | Требование владельца — переиспользовать, а не изобретать. Рамку, подпись, DPI-строку и фоновую отправку она уже делает (`debug_reporter.py:29-56`); `shot_type` внутри неё зашит как `"FIND"`, и только при этом значении сервер печатает строку точности (`server/debug_router.py:35`) |
| 2 | ×4-зум зоны `position_crop_box` | новая тонкая обёртка `report_scout_zoom(hwid, crop_bgr)` в `debug_reporter.py` | Разбор ниже |

**Нужна ли новая функция для зума — разбор, а не вкус.** Рассмотрены три варианта:

- *Передать зум-кроп в существующий `report_find` как `frame_bgr` с `bbox=None`.* Технически работает, но
  сообщение придёт с типом `FIND` и подписью «🎯 Точность: —», то есть в канале появятся два внешне
  одинаковых FIND-снимка на одну находку. Для канала, смысл которого — «владелец глазами сверяет», это
  прямое ухудшение читаемости. Плюс `report_find` тащит на кроп ненужную DPI-диагностику
  (`debug_reporter.py:42-54`).
- *Звать приватный `_send` напрямую из `exchange_scout.py`.* Работает, но `_send` **синхронный**
  (`debug_reporter.py:14-24`) — 2.0 пришлось бы самому заводить `threading.Thread`, то есть скопировать
  паттерн из чужого модуля и одновременно залезть в его приватную функцию.
- **Выбрано: тонкая обёртка `report_scout_zoom` рядом с остальными в `debug_reporter.py`.** Она аддитивна
  (ни одна существующая функция не правится, поведение 1.0 не меняется — C-16 говорит о `navigator.py` и
  `engine.py`, `debug_reporter.py` в него не входит), повторяет ровно тот же однострочный паттерн
  `threading.Thread(target=_send, args=(...), daemon=True).start()` (`debug_reporter.py:56,84`) и даёт
  сообщению собственный `shot_type="SCOUT_ZOOM"`. Последнее безопасно и проверено, а не предположено:
  поле объявлено свободной строкой `Form(...)` (`server/debug_router.py:23`) и используется только в
  подписи (`debug_router.py:35-36`) — **правка и деплой сервера не требуются**.

**Синхронно или fire-and-forget — fire-and-forget.** Обоснование — существующий паттерн, а не новое
поведение: весь `debug_reporter` уже так устроен (`debug_reporter.py:56,74,84`), HTTP ограничен
`_TIMEOUT=10` (`debug_reporter.py:11`), а ошибки глушатся внутри (`debug_reporter.py:23-24`). Синхронная
отправка добавила бы consumer'у до 10 секунд на находку при недоступном сервере — а consumer и без того
самое узкое место пайплайна (YOLO + до 24 вызовов tesseract, 2.1.3), и его замедление напрямую растит
хвост `pending/` (A-5). Изобретать иное поведение причины нет. Честная оговорка про «fire-and-forget» —
см. факт 2.6.2 и A-18: фоновой является только сетевая часть.

**Что именно кропается.** Кроп берётся из **того же BGR-кадра**, который записан на диск и прочитан
consumer'ом, по прямоугольнику `position_crop_box` (`(x1, y1, x2, y2)` → `frame[y1:y2, x1:x2]`, по умолчанию
`(0, 990, 300, 1080)` из `calibration.py:29`), затем увеличивается в 4 раза методом «ближайший сосед».
**Коэффициент не выдуман:** `PositionReader` сам делает `crop.resize((w*4, h*4), Image.NEAREST)` перед
подачей в tesseract (`navigator.py:66`) — то есть владелец видит тот же масштаб и тот же способ
интерполяции, что видит OCR, а не произвольно подобранную картинку.

**Две честные оговорки, которые нельзя опускать, потому что они меняют смысл увиденного:**

1. **Зум показывает зону, а не пиксель-в-пиксель вход OCR.** По C-11 в `PositionReader` подаётся массив в
   представлении каналов `mss` (фактически с переставленными R и B, 2.1.5), а в Telegram отправляется
   визуально корректный BGR, иначе владелец увидел бы неверные цвета. Содержимое зоны и масштаб те же,
   но яркость цветных пикселей после `RGB2GRAY` (`navigator.py:37`) у OCR другая. Вывод «текст читаем
   глазами ⇒ OCR обязан был прочитать» из этой картинки **не следует**.
2. **Отправляется только первый, номинальный кроп.** `PositionReader` пробует четыре прямоугольника
   (`navigator.py:57-62`), три из которых шире номинального. Поэтому пустой/обрезанный зум не доказывает,
   что у OCR не было другого шанса.

**Почему нет нового параметра-выключателя.** Отправка безусловна — владелец просил слать на каждую
находку. Отдельный тумблер был бы новой механикой без запроса; тесты подменяют отправку так же, как это
уже делают существующие тесты 1.0 — `patch('debug_reporter.report_find', MagicMock())`
(`test_exchange_esc_guard.py:87-88`, `test_exchange_backtrack.py:92-93`).

## Стадия 5. Adversarial Review — ломаю собственные контракты Части A

Формат: `claim → mechanism → bypass attempt → result`. Race conditions **внутри** producer/consumer
сознательно не рассматриваются (Часть B); рассматривается только граница GUI ↔ движок ↔ файловая система.

**A-1. «Сессионная папка всегда создаётся».**
Механизм: `os.makedirs(..., exist_ok=True)`. Обход: `scout_sessions` лежит внутри установочной папки;
у части пользователей бот распакован в `Downloads\TotalHunter` (`MEMORY/project_bot_install_location.md`),
но у кого-то — в `C:\Program Files\...`, где запись без прав администратора запрещена. Результат:
**находка реальна.** `makedirs` бросит `PermissionError` уже после того, как GUI переключил кнопку в
«идёт сканирование». Закрытие: C-04 — probe-запись выполняется **первым** шагом `start()`, исключение
поднимается до запуска тредов, GUI показывает текст ошибки и остаётся в `IDLE`.

**A-2. «probe-запись доказывает, что писать можно».**
Механизм: создать и удалить пробный файл. Обход: probe прошёл, а через 5 минут диск кончился или папку
заблокировал антивирус. Результат: **probe не является гарантией на всю сессию** — это гарантия только
на момент старта. Честная формулировка: probe закрывает «нельзя писать вообще», а не «нельзя писать
сейчас». Второй эшелон обязателен — C-15 (проверка результата каждой записи).

**A-3. «`pending/` пуст после старта».**
Механизм: `shutil.rmtree(pending_root)`. Обход: один из JPEG открыт в просмотрщике Windows или
удерживается антивирусом → `rmtree` бросает `PermissionError` на середине, часть файлов уже удалена.
Результат: **находка реальна — частичный отказ.** Закрытие: `rmtree` с `ignore_errors=False`, и его сбой
трактуется как сбой старта (C-04) — сессия не стартует, пользователь видит причину. Тихо продолжать с
полуубранным `pending/` нельзя: остатки чужой сессии были бы обработаны как свои и попали бы в `found/`
текущей сессии, то есть в отчёт владельца попали бы координаты из другого запуска. Контрпример к
альтернативе «удалять по маске только свои файлы»: осиротевшие папки прошлых крашей под маску не
попадают и остались бы навсегда — прямое нарушение C-02.

**A-4. «Два экземпляра `ExchangeScoutEngine` не появятся».**
Механизм: GUI-флаг `active_mode`. Обход: программный путь мимо кнопки — например, будущий аналог
`_programmatic_restart` (`main.py:3651`), который у 1.0 уже существует и зовёт `engine.start()` минуя
`toggle_bot()`. Результат: **находка реальна, GUI-флага недостаточно.** Закрытие двухуровневое:
(1) `start()` на уже работающем экземпляре бросает `RuntimeError` (C-04.8); (2) даже если кто-то создаст
второй экземпляр, `sid` содержит случайный суффикс — сессии не пересекутся в `found/`, а `pending/` будет
снесён вторым стартом, что второй экземпляр обнаружит как сбой записи (C-15). Полная защита от «двух
процессов бота одновременно» (два запущенных exe) Частью A **не даётся** — фиксирую это явно как
ограничение: два процесса делят один `scout_sessions/`, и второй старт снесёт `pending/` первого.
Lock-файл — очевидный кандидат, но он затрагивает конкурентность и потому **[→ Часть B]**.

**A-5. «Диск не кончится».**
Механизм: оценка 80-140 МБ на сессию. Обход: пользователь оставил бота на ночь, сессия идёт 8 часов →
кадров не 200, а десятки тысяч → десятки ГБ. Результат: **находка реальна.** Смягчение по построению:
consumer удаляет пустые кадры сразу (C-07), поэтому в `pending/` живёт только необработанный «хвост», а
не весь скан. Но если consumer медленнее producer'а (а он медленнее по построению — YOLO + до 24 вызовов
tesseract), хвост растёт неограниченно, потому что очередь по решению владельца не ограничена.
**Это не дефект Части A, а прямое следствие принятого владельцем решения «никогда не выбрасывать
непроверенные кадры».** Часть A закрывает последствие (C-15: при заполнении диска сессия останавливается
с видимой ошибкой, а не портит данные молча). Управление темпом producer'а — **[→ Часть B]**.

**A-6. «`found/` не удаляется автоматически».**
Механизм: в коде нет удаления под `found_root`. Обход: пользователь удалил `found/` вручную между
сессиями — а движок ожидает, что путь существует. Результат: не дефект, а обычный случай: `start()`
создаёт `found/<sid>/` заново через `makedirs(exist_ok=True)`. Второй обход: пользователь удалил папку
**во время** работы сессии, между переносом кадра и записью строки журнала. Результат: **находка
реальна** — `os.replace` или запись в jsonl бросит `OSError`, кадр потерян. Закрытие: такой сбой
обрабатывается как C-15 (стоп сессии с видимой ошибкой), а не как тихий пропуск.

**A-7. «Имена кадров уникальны».**
Механизм: монотонный счётчик одного producer'а. Обход: счётчик стартует с 0 в каждой сессии, а `found/`
общий → коллизия между сессиями. Результат: **находка была реальной — закрыта структурно** папкой
`found/<sid>/` (см. 4.1), а не надеждой на уникальность.

**A-8. «Запись в jsonl атомарна».**
Механизм: `write` одной строки + `flush` + `fsync`. Обход: питоновский `write` одной строки в режиме
`'a'` не обязан быть атомарным на уровне ОС при многопоточной записи. Результат: обход не срабатывает —
писатель **ровно один** (consumer, таблица 4.2). Второй обход: краш процесса ровно посреди `write`.
Результат: **возможна обрезанная последняя строка.** Формулировка контракта меняется, а не
рационализируется: C-05(b) гарантирует целостность **уже записанных** строк, а не то, что последняя
строка всегда целая. Потребитель файла обязан переживать битую последнюю строку — это фиксируется как
требование к любому будущему читателю `scout_results.jsonl` и проверяется T-13.

**A-9. «OCR по историческому кадру даёт те же координаты, что и живой экран».**
Механизм: `PositionReader` читает HUD из левого нижнего угла полнокадрового скриншота, который мы
сохраняем без кропа. Обход: HUD показывает координаты **центра экрана в момент съёмки**, а не позицию
самой биржи. Результат: **находка реальна и содержательна.** Записанные `x/y` — это координаты
камеры/центра экрана на кадре, а не точные координаты биржи; смещение биржи внутри кадра известно из
`box`. Поэтому `box` **обязательно** попадает в запись (4.6) — без него находку нельзя донавести позже.
Документ не имеет права называть `x/y` «координатами биржи»; корректно — «координаты позиции на момент
кадра». Во всём тексте формулировка приведена к этому виду.

**A-10. «JPEG-кадр даст тот же результат YOLO, что и живой кадр».**
Механизм: качество 95. Обход: биржа — крошечный объект, JPEG-артефакты на мелких деталях могут снизить
уверенность ниже `conf`. Результат: **риск реален и не устраняется на уровне дизайна** — он проверяется
только живым прогоном. Фиксирую как явное ограничение Части A: эквивалентность детекции «живой кадр vs
JPEG q95» не доказана, а лишь сделана правдоподобной выбором высокого качества. Если владелец увидит
пропуски — первый кандидат на изменение именно этот параметр (или PNG ценой объёма).

**A-11. «Подача каналов в OCR не важна».**
Механизм: предполагалось, что текст белый и порядок каналов не влияет. Обход: `PositionReader._preprocess`
делает `cvtColor(RGB2GRAY)` с весами 0.299R/0.587G/0.114B (`navigator.py:37`) — перестановка R и B меняет
яркость любого **цветного** пикселя, а первый проход OCR идёт вообще по цветному кропу без препроцессинга
(`navigator.py:67`). Результат: **эквивалентность не доказана.** Именно поэтому C-11 требует не
рассуждения, а теста T-21 на реальном сохранённом кадре.

**A-12. «Переключатель режима гарантирует взаимное исключение».**
Механизм: `active_mode` + disabled-виджет. Обход: пользователь жмёт СТОП 2.0 и немедленно СТАРТ 1.0,
пока треды 2.0 ещё живы (`stop()` не обещает завершения тредов — 2.3). Результат: **находка реальна** —
живой producer 2.0 продолжит кликать джойстиком, пока 1.0 уже ведёт свою змейку: два навигатора на одном
экране. Закрытие в Части A — только частичное и я это не маскирую: `active_mode` снимается не сразу по
возврату из `stop()`, а по подтверждению завершения сессии; сам механизм подтверждения (join/таймаут/
callback) — **[→ Часть B]**, и это **обязательный** пункт, который Часть B должна закрыть. До тех пор
контракт C-13 обеспечен на уровне GUI-намерения, а не на уровне физического завершения тредов.

**A-13. «Глубина 50 безопасна, раз конструктор не клэмпит».**
Механизм: проверено по коду (2.2). Обход: не ломает ли 50 сам цикл змейки — `_return_steps = 65` против
`MAX_STEPS_SAFETY = 80`? Результат: константа `MAX_STEPS_SAFETY` (`navigator.py:85`) применяется только в
`CompassNavigator` (`navigator.py:379,401`), который в 2.0 не используется; на `CoastalSnakeNavigator` она
не влияет вовсе. Второй обход: `_maybe_grow_dive_depth` не зациклится ли при 50? Условие `and
self.max_inland_steps < self.DIVE_DEPTH_CAP` ложно → тело не исполняется → нет. Обходов не найдено.

### Раунд 2 — ломаю два новых контракта (C-17, C-18, C-19)

**A-14. «Гейт баланса на старте не даёт работать без кредитов» (C-17a).**
Механизм: проверка `current_credits <= 0` в момент нажатия кнопки. Обход — ровно тот, который должен быть
разобран честно: **баланс кончается МЕЖДУ находками, в разгар восьмичасовой сессии.** Гейт на старте про
это ничего не знает, а перечитывать баланс с сервера синхронно на каждой находке «на живую» — это и есть
лишний сетевой вызов, которого нет и в 1.0. Результат: **обход не срабатывает, и причина конкретная, а не
успокоительная.** Проверка баланса не нужна отдельно, потому что **само списание и есть проверка**:
`spend_credit` возвращает `{"success": False, "low_credits": True}` на HTTP 402 (`auth.py:120-121`), то есть
сервер отказывает в первой же неоплачиваемой находке, и по C-17.4 сессия немедленно останавливается с
открытием страницы пополнения — тот же механизм, что у 1.0 (`main.py:3762-3764`). Цена ошибки при этом
ограничена и её размер известен: **максимум одна находка** между «деньги кончились» и «сессия
остановлена», и эта находка не оплачена (402 = списания не было), то есть уходит владельцу бесплатно, а не
в минус пользователю.
Второй обход: между 402 и фактической остановкой consumer успевает обработать ещё кадры и записать ещё
находки. Результат: **находка реальна.** Закрытие: флаг остановки выставляется в самом consumer'е сразу
по получению `low_credits`, синхронно, до перехода к следующему кадру, а не только в GUI-колбэке — GUI
узнаёт об этом параллельно через `on_credit_callback`. Момент физического завершения тредов после этого —
прежнее известное ограничение (A-12, **[→ Часть B]**), и оно здесь ничего не ухудшает: лишние находки
после остановки списаний не порождают, потому что дальше `spend_credit` не вызывается.
Третий обход: 402 пришёл, а окно пополнения не открылось (нет браузера) — деньги при этом не тронуты,
сессия всё равно остановлена; это деградация UX, не денег.

**A-15. «Списание 2.0 идентично 1.0» (C-17b).**
Механизм: та же функция, тот же `hunt_type`, та же точка «по факту находки». Обход: **точки не
эквивалентны по частоте срабатывания.** 1.0 списывает только после того, как находка пережила второй,
подтверждающий скан `_fresh_scan()` и фактический клик — обе ранние ветки (`navigator.py:1107-1112`,
`1115-1124`) возвращают управление ДО `on_found_callback` (`navigator.py:1145-1146`). У 2.0 второго скана
нет и быть не может: кадр исторический, карта давно уехала. Результат: **находка реальна и она денежная.**
Честный вывод, который я не смягчаю: при одинаковом `conf` 2.0 будет списывать кредиты **чаще**, чем 1.0 на
той же карте, ровно на долю ложных срабатываний YOLO, которые 1.0 молча отбрасывал вторым сканом.
Это прямое следствие требования «точно как 1.0» в модуле, где кликов нет, а не дефект реализации, и
скрывать его в тексте нельзя — владелец должен знать это ДО запуска на живых пользователях. Смягчений два,
оба уже в дизайне: (i) каждая оплаченная находка физически лежит в `found/<sid>/` и одновременно приходит
в Telegram (C-18) — то есть ложные списания видимы и доказуемы, а не анонимны; (ii) порог `conf` —
существующий ползунок GUI, и он же единственный честный регулятор этой частоты. Отдельный «второй скан по
соседнему кадру» здесь не изобретается: это была бы новая механика детекции, а не Часть A.

**A-16. «Один вызов `spend_credit` = одно списание» (C-17b).**
Механизм: ровно один вызов на записанную находку, повторов нет. Обход: HTTP-таймаут (`timeout=5`,
`auth.py:117`) **не означает, что сервер не списал** — запрос мог дойти и выполниться, а ответ потеряться;
клиент получит `{"success": False}` (`auth.py:123-124`) и не обновит счётчик. Результат: **находка
реальна** — расхождение локального счётчика и реального баланса. Почему это не закрывается повтором:
повтор ровно здесь и создал бы двойное списание, то есть лечение хуже болезни; поэтому повтора нет
сознательно (таблица 4.3, столбец C). Почему это приемлемо в Части A: (i) расхождение — в пользу
пользователя по видимости (показано больше, чем есть) и самоисправляется при любом следующем успешном
ответе, который приносит актуальное `credits` (`main.py:3761`); (ii) точно то же поведение уже сегодня
работает в 1.0 — 2.0 не вводит новый класс риска, а наследует существующий.
**Явно не проверенный факт:** синхронизирует ли серверный long-poll баланса (`vault.py`,
`notify_balance_changed`) счётчик бота после такого расхождения — в этой сессии я серверный `/use_credit`
не читал и утверждать не буду. Это помечено в Final Gate как единственный непроверенный внешний факт и
подлежит проверке при реализации.

**A-17. «Владелец увидит каждую находку в Telegram» (C-18, C-19).**
Механизм: две отправки на находку. Обход первый: сервер недоступен/таймаут. Результат: **сообщение
теряется молча** — это подтверждено кодом, а не предположением: `_send` целиком обёрнут в
`except Exception: pass` (`debug_reporter.py:23-24`), а серверная сторона при ошибке Telegram возвращает
`{"ok": True, "forwarded": False}` (`server/debug_router.py:45-49`), то есть даже успешный HTTP-ответ не
доказывает доставку. Принимается осознанно: канал — диагностический, и он **не является источником истины**.
Источник истины — `found/<sid>/scout_results.jsonl` и кадры на диске, которые пишутся до отправки и от неё
не зависят. Именно поэтому C-18/C-19 стоят **после** записи журнала, а не вместо неё.
Обход второй: FIND ушёл, SCOUT_ZOOM не ушёл (или наоборот) — в канале окажется половина пары, и владелец
может принять её за полную картину. Результат: **находка реальна**, закрытие частичное и честное: обе
отправки несут один и тот же `hwid` и идут подряд, но порядок доставки Telegram не гарантирует. Опорой для
сверки служит номер кадра, который и так виден в GUI-списке и в журнале; выдумывать общий id сообщения
ради этого не стал — это не улучшит диагностику, а добавит механику.
Обход третий: **лимиты Telegram.** Много находок подряд × 2 сообщения — Telegram отвечает 429, сервер
трактует это как `ok = False` (`server/debug_router.py:45-47`) и снова теряет сообщение молча. Результат:
**находка реальна**, и она — прямое ограничение режима: при большом потоке находок Telegram-канал
**неполон по построению**, а не «иногда сбоит». Фиксирую это как свойство, а не как баг.
Обход четвёртый: FIND-снимок 2.0 неотличим в канале от FIND-снимка 1.0 — подпись формируется сервером из
`shot_type` (`server/debug_router.py:36`), а `report_find` жёстко шлёт `"FIND"` (`debug_reporter.py:56`).
Результат: различение обеспечивается двумя фактами: парным сообщением `SCOUT_ZOOM` рядом и взаимным
исключением режимов (C-13) — одновременно работающих 1.0 и 2.0 не бывает. Ломать существующую функцию
ради отдельного типа не стал: владелец просил переиспользовать её буквально.

**A-18. «Отправка в Telegram не тормозит consumer» (C-18, C-19).**
Механизм: fire-and-forget. Обход: «fire-and-forget» — неточное описание `report_find`. Синхронно, в треде
вызывающего, исполняются `frame_bgr.copy()` (`debug_reporter.py:29`), отрисовка (30-41) и DPI-замер,
который **создаёт живой `mss()` и зовёт `pyautogui.size()`** (`debug_reporter.py:42-54`); в фон уходит
только `_send` (56). Результат: **находка реальна** — на каждую находку consumer платит копией полного
кадра (1920×1080×3 ≈ 6 МБ) и двумя локальными замерами. Оценка честная: это доли секунды против
