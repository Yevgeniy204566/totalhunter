# Древний — калькулятор нормы урона (Часть A)

## Контекст

Подсистема «Норма урона по Древним» (Ancients Damage Quotas) обсуждалась с Gemini в
`docs/Входящие_Gemini.md` (несколько раундов уточнения матрицы весов). Решено называть
фичу **«Древний»**, не «Фаза 2» — чтобы не путать с уже частично реализованной Фазой 2
системы очков сундуков (распознавание тайм-ивентов, см. [[project_chest_events_phase2]]
в памяти — та запись теперь частично устарела по терминологии, актуальна по содержанию
блокера Фазы 2 каталога сундуков).

Полная архитектура из Gemini-переписки распадается на три независимые подсистемы:
- **A. Калькулятор квот** — этот документ. Ввод данных лидером в Личном кабинете.
- **B. Публичный frictionless-сбор войск с PIN-кодом** — отложено, не проектируется сейчас.
- **C. Аудит/откат/lock/rate-limit** — отложено, не проектируется сейчас.

Часть B зависит от структуры данных, заложенной в Части A (поле «уровень войск» на
игрока). Часть C имеет смысл только после существования Части B. Обе откладываются
осознанно владельцем — фиксируется как будущая работа, не текущий долг.

## Цель

Лидер клана в Личном кабинете указывает параметры события «Древний» (сколько раз
вызван, на каких уровнях, клановый бафф) и стратегию распределения нормы между
игроками клана (по рангу или по уровню войск). Жмёт «Рассчитать» → видит итоговую
норму и разбивку по людям/категориям. Бесплатно для всех пользователей, премиум не
требуется.

## Источник ростера клана

Чат с владельцем выявил два конкурирующих источника списка игроков:
- **Сундуки (`PlayerAlias`)** — неполный, не все участники открывают сундуки.
- **Tournament Reader** (`tournament_reader.py`, бот-сторона) — OCR таблицы турнира,
  даёт полный список клана (даже с нулевыми очками за турнир).

Выбран **Tournament Reader** как источник ростера — он полнее. Текущий скрипт — это
самостоятельный CLI (не в GUI бота), со своим конфигом `tournament_config.json`
(`alliance_tag` + `api_token` Bearer), бьющий в несуществующий
`/api/v1/tournaments/import`. Это не совпадает с тенант-моделью бота (`hwid` → `User` →
`kingdom`/`clan`, как в `chest_reader.py`/`chests.py`).

**Решение:** переписать `tournament_reader.py` на тот же контракт, что и
`chest_reader.py` — `from auth import SERVER_URL, get_hwid`, payload
`{hwid, kingdom, clan, timestamp, items}`, без `alliance_tag`/`api_token`. Турнирный
импорт бьёт в тот же `ChestCollector` (kingdom+clan+user_id), что и сундуки — один
лидер, один клан, один `collector_id` на все фичи. own_data (закреплённая своя строка)
включается в `items` как обычная запись (дедуп по имени, если уже встречалась в
видимых строках).

Импорт ростера **бесплатный** — не списывает кредиты (в отличие от импорта сундуков),
весь функционал «Древний» бесплатен по требованию.

## Модель данных

### `ancient_roster` (новая таблица)
Одна строка = один игрок клана в текущем ростере (per `collector_id`).

| Поле | Тип | Описание |
|---|---|---|
| id | PK | |
| collector_id | FK → chest_collectors.id | тот же tenant, что у сундуков |
| player_name | varchar | каноническое имя (после применения PlayerAlias) |
| place | int nullable | место в турнире на момент последнего импорта |
| points | bigint nullable | очки в турнире на момент последнего импорта |
| troop_level | varchar nullable | одна из 13 ступеней войск (см. матрицу ниже), ручной ввод лидера |
| updated_at | timestamp | |

Unique: `(collector_id, player_name)`.

**Семантика импорта турнира (полная замена ростера):**
- Для каждого игрока из нового импорта: upsert по `(collector_id, player_name)` —
  обновить `place`/`points`; если строка новая — `troop_level = NULL`; если строка уже
  существовала — `troop_level` **не трогать** (ручной ввод лидера переживает обновление
  турнирных данных).
- Любая существующая строка `ancient_roster` для этого `collector_id`, чьего игрока
  **нет** в новом импорте — **удаляется целиком** (вместе с её `troop_level`). Никаких
  «мёртвых душ»: ротация состава клана каждые 2 недели, владелец явно подтвердил —
  хранить неактивных смысла нет.

### `ancient_calculations` (новая таблица — история)
| Поле | Тип | Описание |
|---|---|---|
| id | PK | |
| collector_id | FK | |
| computed_at | timestamp | |
| strategy | varchar | `'A'` или `'B'` |
| clan_preset | varchar nullable | `'T5'..'T9'`, только для B |
| summon_levels | JSON | список 1-6 целых (81-250) |
| amplification_coef | float | клановый бафф, свободный ввод (например 1.7) |
| officer_count | int nullable | только для A |
| veteran_count | int nullable | только для A |
| total_quota_millions | float | итоговая норма |
| result_json | JSON | разбивка (см. ниже) |

При вставке 6-й записи для `collector_id` — удаляется самая старая (лимит 5).
Запись создаётся **только** по нажатию «Рассчитать» (это и триггер автосохранения).

## Справочные таблицы (статические константы в коде)

### `ANCIENT_LEVEL_HP: dict[int, float]`
Уровень Древнего (81-250) → суммарный требуемый урон в миллионах (вся его HP). Источник
— Google Sheet (вкладка «Древний», колонка «Очки, Миллионы»). Часть значений в исходной
таблице (уровни 235-250) имеют артефакт форматирования (потерян множитель) — **при
реализации перепроверить с владельцем эти конкретные строки до того, как кодировать
константу**, не угадывать.

### `TROOP_QUOTA_PRESETS: dict[str, dict[str, float]]`
13 ступеней войск (М→С→Г переходы) × 5 прессетов клана (**T5, T6, T7, T8, T9** — все
пять доступны в UI). Точные веса — финальная версия из Gemini-переписки
(`docs/Входящие_Gemini.md`, секция «Мастер-таблица для Клода (с переходными
войсками)»), правило cap: если фактический тир игрока выше выбранного прессета —
вес фиксирован на 1.0 (уже встроено в таблицу, отдельной cap-логики в коде не нужно).

## Формула расчёта

```
hp_i = ANCIENT_LEVEL_HP[level_i]            # для каждого из 1-6 вызовов
total_quota = Σ hp_i × amplification_coef   # клановый бафф как множитель

# Стратегия А — по рангу. Только Офицеры (вес 1.0) и Ветераны (вес 0.5).
denom = officer_count × 1.0 + veteran_count × 0.5
quota_officer = total_quota × 1.0 / denom
quota_veteran = total_quota × 0.5 / denom

# Стратегия Б — по уровню войск.
weight_i = TROOP_QUOTA_PRESETS[clan_preset][player_i.troop_level]
denom = Σ weight_i   # только игроки из ancient_roster с заданным troop_level
quota_i = total_quota × weight_i / denom
# игроки с troop_level = NULL исключаются из расчёта, в UI помечаются как
# "не указан уровень войск" (не получают квоту, пока лидер не заполнит)
```

`result_json` (Стратегия А): `{"officer_quota": ..., "veteran_quota": ...}`
`result_json` (Стратегия Б): `{"players": [{"name": ..., "troop_level": ..., "quota": ...}, ...], "excluded": ["имя без уровня войск", ...]}`

## UI — вкладка «Древний» в Личном кабинете

Дизайн идентичен «Сундукам» (премиум-стиль). Авторизация Google, доступ бесплатный.

1. **Таблица ростера** — имя / место / очки (из последнего импорта турнира) + поле
   «уровень войск» (dropdown, 13 значений) редактируется лидером прямо в таблице.
   Нет кнопки импорта в кабинете — ростер обновляется автоматически, когда лидер на
   своей машине запускает обновлённый `tournament_reader.py`.
2. **Панель калькулятора**:
   - Количество вызовов Древнего (1-6) — для каждого вызова отдельный выбор уровня
     (81-250).
   - Прессет клана: T5 / T6 / T7 / T8 / T9, default T8.
   - Коэффициент усиления — свободный числовой ввод (например 1.7).
   - Переключатель стратегии: А (по рангу) / Б (по уровню войск).
   - Если А: два числовых поля — «Офицеры» и «Ветераны».
   - Большая зелёная кнопка **«Рассчитать»**.
3. **Результат** — общая норма + разбивка (два числа для А; таблица по игрокам для Б,
   с явным списком исключённых без указанного уровня войск).
4. **История** — список ≤5 последних расчётов (дата, стратегия, итоговая норма), клик
   открывает прошлую разбивку (read-only).

## Тестирование (TDD)

Backend, pytest, по аналогии с существующими `server/tests/test_chests.py`:
- Функция веса/распределения для Стратегии А (денормализация, граничные случаи: 0
  офицеров, 0 ветеранов).
- Функция веса/распределения для Стратегии Б (cap-правило, игроки без уровня войск
  исключены, корректность с пустым ростером).
- Endpoint импорта турнира: upsert + delete семантика на `ancient_roster` (новый игрок,
  обновление существующего без потери `troop_level`, удаление выпавшего игрока вместе
  с его `troop_level`).
- Endpoint расчёта: запись в `ancient_calculations`, лимит истории 5 (вставка 6-й
  удаляет самую старую), бесплатность (не списывает кредиты).

Frontend — без отдельного автоматического тестового слоя, если в `web/` для
`/dashboard/chests` его тоже нет (сверить перед реализацией и следовать тому же
паттерну).
