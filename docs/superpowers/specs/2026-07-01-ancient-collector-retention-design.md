# Спека: Скрытие коллектора в «Древнем» + авто-очистка неиспользуемых данных

Дата: 2026-07-01
Статус: одобрено владельцем, готово к написанию плана реализации

## Проблема

Техдолг сессии #113, пункт А, изначально формулировался как «кнопка Удалить
коллектор в Древнем». В процессе диагностики выяснилось: `ChestCollector` —
общая сущность для Сундуков и Древнего (одна строка на клан/королевство).
Единственное существующее полное удаление коллектора (`DELETE
/web/dashboard/chests/{slug}` в `chest_dashboard.py`) каскадно стирает ВСЁ,
включая данные Сундуков — многомесячную историю очков клана. Кнопка «Удалить»
на странице Древнего означала бы риск случайно стереть чужой (для этой
страницы) массив данных.

Решение по требованию владельца: вместо удаления — **скрытие** (`ancient_hidden`
флаг на `ChestCollector`, реализовано и задеплоено локально в этой сессии,
см. `ancients_dashboard.py`, миграция `a9h2i3d4e5n6`). Скрытие убирает
коллектор из основного списка `/web/dashboard/ancients` для владельца, ничего
не удаляет, обратимо кнопкой «Показать» в разделе «Скрытые».

Далее владелец предложил дополнение: если коллектор скрыт и **не используется**
в Древнем 2 месяца — данные Древнего для него самоочищаются автоматически
(не нужно вручную удалять мусорные/заброшенные кланы). При этом:
- Сундуки (`Chest`, история сезонов) этого коллектора не затрагиваются вообще —
  скрытие в Древнем не влияет на Сундуки никак.
- Общая база имён (`PlayerAlias.canonical_name`) должна переживать любую чистку
  навсегда, в том числе уже существующую (см. ниже).

По ходу диагностики найден смежный факт: `server/chest_history.py` уже содержит
`run_stopped_collector_tick` — суточный тик, удаляющий коллектор целиком через
90 дней после `stopped_at` («Закрыть сезон досрочно»), каскадом по `Chest`,
`ChestSeasonHistory`, `ChestTypeAlias`, `ChestConfiguration` и **`PlayerAlias`**.
Он также **не чистит** таблицы Древнего (`AncientRoster` и т.д.) — те же
осиротевшие строки, что и в ручном удалении из `chest_dashboard.py`. Это две
отдельные, но связанные проблемы, которые фиксируются одним заходом.

## Архитектура

### Часть 1 (уже сделано в этой сессии, до брейнсторма) — скрытие

- `ChestCollector.ancient_hidden` (Boolean, default False) — миграция `a9h2i3d4e5n6`.
- `GET /web/dashboard/ancients` — исключает собственные (`is_owner`) коллекторы
  с `ancient_hidden=True` из `collectors`, возвращает их отдельно в
  `hidden_collectors: [{slug, kingdom, clan}]`. На редакторов (`AncientEditor`)
  скрытие не влияет — они по-прежнему видят коллектор как обычно (это
  owner-only настройка отображения, не блокировка доступа).
- `PATCH /web/dashboard/ancients/{slug}/ancient-visibility {hidden: bool}` —
  owner-only, переключает флаг.
- Фронтенд (`AncientsPage.jsx`): кнопка «Скрыть» с двухшаговым подтверждением
  рядом с «Пригласить сокланера»; блок «Скрытые (N)» внизу страницы со
  списком и кнопкой «Показать» на каждой записи.

### Часть 2 (новое, требует плана) — авто-очистка по неактивности

**Новое поле** `ChestCollector.ancient_hidden_at` (nullable TIMESTAMP) —
следующая миграция после `a9h2i3d4e5n6`.

Семантика:
- `PATCH .../ancient-visibility {hidden:true}` → `ancient_hidden_at = now()`.
- `PATCH .../ancient-visibility {hidden:false}` → `ancient_hidden_at = NULL`
  (таймер снят, пока коллектор виден).
- Любая активность по Древнему для коллектора, **у которого `ancient_hidden_at`
  не NULL** (то есть коллектор сейчас скрыт), сдвигает `ancient_hidden_at =
  now()` — таймер стартует заново:
  - `POST /api/v1/tournaments/import` (бот выгружает ростер турнира);
  - `POST /web/dashboard/ancients/{slug}/calculate` (расчёт нормы урона).

  Это покрывает случай «редактор продолжает пользоваться скрытым для владельца
  коллектором» — активность видна независимо от того, кто её произвёл.

**Новый суточный тик** (`server/ancient_retention.py`, новый файл, по образцу
уже существующих циклов в `chest_history.py`):

```
ANCIENT_HIDDEN_RETENTION_DAYS = 60  # 2 месяца
```

Для каждого `ChestCollector`, где `ancient_hidden_at IS NOT NULL AND
now() - ancient_hidden_at >= 60 дней`:
- Удалить: `AncientRoster`, `AncientNameMapping`, `AncientCalculation`,
  `AncientEditor`, `AncientInviteCode` (всё, что относится к Древнему,
  `collector_id = c.id`).
- НЕ трогать: `Chest`, `ChestSeasonHistory`, `PlayerAlias`, сам `ChestCollector`.
- После очистки: `ancient_hidden_at = NULL` (нечего больше отсчитывать),
  `ancient_hidden` остаётся `True` — коллектор остаётся в разделе «Скрытые» с
  чистого листа. Если позже (даже пока скрыт) придёт новый импорт ростера —
  данные появятся заново, и таймер вновь включится с этого момента (через
  правило «активность сдвигает `ancient_hidden_at`» выше).

Регистрация фонового цикла — `ensure_background_tasks()` в новом модуле,
вызов добавляется в `main.py` рядом с существующим вызовом для `chest_history`.

### Часть 3 (фикс попутного бага) — 90-дневный `run_stopped_collector_tick`

**Пересмотрено:** изначально планировалось сохранять `PlayerAlias` даже при
полном удалении коллектора (Часть 3), но `PlayerAlias.collector_id` — внешний
ключ на `chest_collectors.id` без `ondelete='SET NULL'`/`CASCADE`. Удалить
`ChestCollector`, оставив дочерние `PlayerAlias`, физически нельзя в Postgres —
упадёт ошибка нарушения внешнего ключа (в тестах на SQLite это могло тихо
пройти и замаскировать проблему). Владелец подтвердил: раз коллектор (клан)
удаляется целиком навсегда, привязанные только к нему имена больше никому не
нужны — накапливать их незачем. Решение: **поведение `PlayerAlias` не
меняется**, она по-прежнему удаляется вместе с коллектором, как и сейчас.

В `server/chest_history.py` фиксируется только реальный баг — недостающие
таблицы Древнего в каскаде (сейчас они осиротевают, а `ChestCollector` уже
удалён): добавить `AncientRoster`, `AncientNameMapping`, `AncientEditor`,
`AncientInviteCode`, `AncientCalculation` в тот же каскад удаления, рядом с
уже существующими `Chest`/`ChestSeasonHistory`/`ChestTypeAlias`/
`ChestConfiguration`.

Это ограничение (FK без `ondelete`) не касается Части 2 — там `ChestCollector`
никогда не удаляется, чистятся только его дочерние таблицы Древнего.

## Тестирование (TDD)

Часть 2 (`server/tests/test_ancient_retention.py`, новый файл):
- Коллектор скрыт < 60 дней назад, без активности → тик не трогает данные.
- Коллектор скрыт ≥ 60 дней назад, без активности → тик удаляет
  `AncientRoster`/`AncientNameMapping`/`AncientCalculation`/`AncientEditor`/
  `AncientInviteCode`, не трогает `Chest`/`PlayerAlias`/`ChestCollector`.
- Импорт ростера (или расчёт) во время скрытия сдвигает `ancient_hidden_at` →
  тик (на дату, которая была бы просрочена по старому значению) больше не
  чистит коллектор.
- После очистки `ancient_hidden_at` сброшен в `NULL`, `ancient_hidden` остаётся
  `True`.
- Показ коллектора (`hidden:false`) обнуляет `ancient_hidden_at` независимо от
  того, сколько он был скрыт.

Часть 3 (новые тесты в `server/tests/test_chest_history.py`, для функции, у
которой пока нет прямого тестового покрытия):
- Коллектор, остановленный >90 дней назад → удалён целиком (как и сейчас),
  `PlayerAlias` тоже удалена (поведение не меняется, фиксируется явным тестом,
  чтобы не сломать молча в будущем).
- Таблицы Древнего (`AncientRoster`/`AncientNameMapping`/`AncientCalculation`/
  `AncientEditor`/`AncientInviteCode`) для того же коллектора удалены тем же
  тиком (сейчас — баг, осиротевают).
- Коллектор, остановленный <90 дней назад → тик его не трогает.

## Зоны риска / открытые решения для плана реализации

- Нужно решить, в каком месте кода `POST /calculate` и `POST
  /tournaments/import` получают доступ к текущему `ancient_hidden_at`
  коллектора и обновляют его — вероятно, добавить одну строку в начале
  каждого хендлера (`if collector.ancient_hidden_at is not None: collector.
  ancient_hidden_at = datetime.now(timezone.utc)`), не выделяя отдельную
  функцию ради двух вызовов (YAGNI).
- `tournaments.py` — проверить, что там уже есть доступ к объекту `ChestCollector`
  в текущем виде (или только к `collector_id`) — если только id, потребуется
  дополнительный `SELECT` перед апдейтом.
- Единицы измерения "60 дней"/"90 дней" — простые календарные дни (не месяцы),
  как и существующий `STOPPED_COLLECTOR_DAYS = 90` — расхождение с бытовым
  «2 месяца»/«3 месяца» на пару дней в разных месяцах не имеет значения для
  этой задачи (не биллинг, не юридический SLA).
