## Стадия 5. Adversarial Review (формула `claim → mechanism → bypass → result`)

- **PA-1. «Посторонний не увидит hwid».** Механизм: явный `select` колонок (P-09). Обход: `SELECT *` в
  будущей правке. Результат: тест PT-04 падает, если в JSON ответа есть `hwid`/`reporter_hwid`.
- **PA-2. «Через x/y нельзя внедрить разметку».** Механизм: только `StrictInt` (pydantic) + React экранирует текст.
  Обход: строка (в т. ч. числовая `"123"`), float или bool вместо int → 422 (`StrictInt`; без него обычный `int` приводил бы `"123"`, `1.0`, `True` к числу), строка в БД не попадёт. Результат: безопасно; PT-03.
- **PA-3. Флуд публичной страницы.** Механизм: только hwid существующего небаненого пользователя (P-05).
  Обход: любой зарегистрированный (в т.ч. бесплатный триал) может слать без лимита, а server не связывает
  публикацию со списанием. **Контрпример найден и ПРИНЯТ:** rate limit и дедуп запрещены решением владельца
  (P-04). Единственный серверный access gate — существующий и не заблокированный пользователь; ограничения частоты нет. Это осознанный остаточный риск, не закрытый механизмом.
  Следствие: размер ответа `GET /roy/scout-finds` ограничен 500 строками (P-09), но поток публикаций одного пользователя может вытеснить из этих 500 находки других королевств. Риск принят вместе с флудом; фильтр по королевству и пагинация не вводятся.
- **PA-4. Один и тот же объект в нескольких кадрах.** Без дедупа список содержит повторы одной биржи.
  Принято владельцем (решение 3). Не «баг», ожидаемое поведение.
- **PA-5. Принятый остаточный риск: запись в РОЙ без списания.** Штатный клиент вызывает публикацию только после успешного списания (P-01), но `POST /roy/scout-find` принимает `hwid, kingdom, x, y`, а сервер не имеет связи этого запроса с конкретным успешным списанием, поэтому модифицированный клиент может вызвать эндпоинт напрямую. Серверная привязка публикации к операции списания (payment-token и т. п.) в этой версии сознательно не реализуется (Stage 1 п. 7). Риск принят владельцем 2026-09-18 («остаточные риски принимаем; дедупликацию и лимит не добавляем»). Ущерб — запись на публичной странице, живёт 20 минут (P-13).
- **PA-6. Рост таблицы.** Физический размер таблицы не имеет жёсткого лимита: очистка выполняется при следующей успешной публикации и удаляет записи старше 20 минут (P-13), не по таймеру; при длительном отсутствии публикаций таблица временно содержит все строки с момента последней очистки (например, 1000 находок, затем сутки тишины — 1000 строк остаются, `GET` их не показывает; следующая публикация их удалит). В штатном потоке интенсивность вставок естественно ограничена частотой обнаружений биржи сканером (не произвольным HTTP-вводом, PA-5). Картинки не хранятся. Очистка вынесена в саму функцию `scout-find`, а **не** в общий `_cleanup_loop` (`roy.py:168`), чтобы не менять поведение 1.0. Неавторизованный `POST` очистку не запускает. Отдельный rate-limit/дедуп не вводится (P-04).
- **PA-7. Зависший сервер и число тредов.** Механизм: отдельный тред + `timeout=5` (P-07) — consumer не блокируется. `timeout=5` в `requests` — раздельные 5 с на подключение и 5 с на чтение (проверено: суммарного лимита `total` нет), то есть тред может удерживаться до отдельных таймаутов connect/read, а не гарантированно ровно 5 с; число одновременно живущих тредов при потоке находок отдельного верхнего ограничения не имеет. Это допущение, а не мера защиты: допустимо при ожидаемо низкой частоте находок бирж; возможная защита (пул/семафор) — новая механика, вне scope.
- **PA-8. Смена королевства в GUI между находкой и публикацией — закрыто контрактом P-06.** `kingdom` фиксируется
  в результате находки при его создании, публикация GUI не перечитывает (PT-18). **Остаточное допущение:** очередь неограничена,
  поэтому между съёмкой кадра и созданием результата значение в GUI ещё может смениться. **Гарантируется только неизменность K после создания результата, но не то, что K соответствует моменту захвата конкретного кадра.** Это окно остаётся сознательным допущением этой спеки; закрытие его фиксацией K при старте сессии в неё не входит [→ Часть A/B]. Номер вводится участником
  добровольно и не проверяется: неверно указанное королевство даст находку под чужим номером (сервер не отличает).
- **PA-9. Изоляция 1.0.** Механизм: только новые символы (P-12). Обход: правка общего `_broadcast`. Результат:
  запрещена P-03; PT-14 проверяет, что `GET /roy/pool` и `roy_pool` не меняются после публикации 2.0.
- **PA-10. Порядок P-01 при таймауте ответа списания.** Если ответ `/use_credit` потерян, `charged` неизвестен →
  публикация **не выполняется** (`charged is True` — строгая проверка). Результат: находка не выложена, кредит
  мог списаться — вопрос потерянного ответа разобран в спеке монетизации (§2.8).
- **PA-11. X/Y и kingdom вне 32-битного `Integer` — закрыто контрактом P-02.** Колонка `Integer` (Postgres, 32 бита), поэтому
  схема ограничивает x, y (и kingdom сверху) тем же диапазоном: значение вне диапазона → 422 до обращения к БД, а не 500 из БД.
  Тест PT-03 проверяет обе границы диапазона и оба выхода за диапазон.

- **PA-12. `db.begin()` после autobegin → 500.** Правило `ANTI-PATTERNS.md` (Хангоф #70) относится к эндпоинтам, где dependency выполняет SELECT до тела. У `scout-find` такой dependency нет (4.2); поиск пользователя стоит внутри блока `db.begin()`. Проверено: тот же паттерн у `/roy/report` (`roy.py:265`) и `/use_credit` (`main.py:315`) работает в проде; тесты плана (POST-ветки PT-03, PT-06, PT-07) проходят весь путь без `InvalidRequestError`. Утверждение «всегда 500» — не подтверждено.
- **PA-13. Конкуренция `DELETE` просроченных строк при параллельных публикациях и общий пул соединений.** Механизм: каждая публикация удаляет строки `found_at <= now − 20 мин` в своей транзакции (P-13). Обход: много параллельных POST при накопленных просроченных строках — транзакции ждут row-locks друг друга. Результат: очередь блокировок возможна только пока просроченные строки ещё не удалены; первая транзакция удаляет их и снимает блокировку, следующие `DELETE` находят 0 строк по индексу `found_at` и ничего не блокируют. При проверенном плане выполнения (индексный доступ по `found_at`, без последовательного скана) `DELETE`-операции проходят строки в одном порядке по индексу; для описанного сценария это делает взаимный deadlock маловероятным. Универсальная гарантия отсутствия deadlock при любом плане PostgreSQL не заявляется; нагрузочным тестом поведение не проверено.

  **Дополнительный риск (найден Gemini, проверен по коду).** Пока запрос ждёт row-lock, он удерживает соединение из общего `engine` (`pool_size=10, max_overflow=20` — максимум 30 соединений, `server/database.py:24-25`), который обслуживает **весь** backend, не только Рой. Достаточно большой параллельный флуд `POST /roy/scout-find` при накопленном backlog просроченных строк (PA-6: например, 1000 находок после суток без публикаций) теоретически может временно исчерпать пул и задержать несвязанные эндпоинты (Сундуки, Древний, авторизация, Vault sync). Категория риска шире, чем PA-3: там цена — засорение списка находок, здесь — временная недоступность несвязанных функций.

  Перенос очистки в `_cleanup_loop` запрещён P-12/P-13 (изменил бы поведение 1.0); rate-limit/дедуп запрещены P-04; ограничение размера одного `DELETE` (`LIMIT`) сознательно не вводится — при большом backlog это превратило бы одну очистку в серию очисток на последующих публикациях, увеличивая число обращений к БД там, где нужно их минимизировать (принцип проекта — не нагружать сервер лишними запросами). Никакая дополнительная механика или фоновые запросы ради этого риска не вводятся. **Риск принят владельцем (2026-09-19):** экстремальный параллельный флуд может временно конкурировать за общий DB pool — принятый остаточный риск, наравне с PA-3.
