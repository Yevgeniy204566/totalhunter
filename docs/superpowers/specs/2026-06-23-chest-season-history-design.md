# Спека: Архив сезонов сундуков (chest_season_history)

Дата: 2026-06-23
Статус: одобрено владельцем, готово к написанию плана реализации

## Проблема

Сейчас все собранные сундуки навечно лежат в одной таблице `chests`, привязанной
к `chest_collectors` (один ряд = один клан-сборщик). `period_start`/`period_end`
на коллекторе — это только фильтр отображения текущего сезона на публичной
странице/в кабинете, физического архивирования или удаления старых данных нет.
Владелец хочет: когда сезон клана заканчивается — старые данные сразу уходят
в историю, таблица `chests` не растёт бесконечно, а историю прошлых сезонов
можно посмотреть и в кабинете, и на публичной странице. Хранить историю 3 месяца,
потом удалять.

## Архитектура

### Новая таблица `chest_season_history`

Одна строка = один закрытый сезон одного коллектора (клана).

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | Integer PK | |
| `collector_id` | FK → chest_collectors.id, indexed | |
| `period_start` | TIMESTAMP(timezone=True) | начало архивированного сезона |
| `period_end` | TIMESTAMP(timezone=True) | конец архивированного сезона |
| `target_points_snapshot` | Integer, nullable | копия `chest_collectors.target_points` на момент закрытия |
| `target_chests_snapshot` | Integer, nullable | копия `chest_collectors.target_chests` на момент закрытия |
| `summary_json` | JSON/JSONB | готовый пивот: тот же формат, что отдаёт `GET /chests/summary/{slug}` (`chest_types`, `players[]` с `points/counts/quota_chests/name`, `totals`) |
| `closed_at` | TIMESTAMP(timezone=True), server_default=func.now() | момент архивации — точка отсчёта retention |

**Почему `summary_json`, а не сырые `Chest`-строки:** очки/квота считаются
СЕЙЧАС через живой JOIN на `ChestConfiguration` (веса очков по типу сундука,
заданные владельцем). Эта конфигурация может измениться к следующему сезону.
Если бы история хранила только сырые `Chest`-строки, при пересчёте через
ИЗМЕНИВШИЙСЯ `ChestConfiguration` итоги старого сезона "переписались" бы
задним числом — неверно. Берём уже посчитанный снимок один раз в момент
закрытия — цифры зафиксированы навсегда. Аналогично `target_points_snapshot`/
`target_chests_snapshot` — чтобы цветовая раскраска строк истории (зелёный/
жёлтый/красный по % от цели) не сбивалась, если владелец позже поменяет цели
для нового сезона.

### Авто-цикл закрытия/открытия сезона

Фоновый тик в `main.py`, по аналогии с уже существующим `_tick_roy_drain`
(`server/roy.py`) — отдельная асинхронная функция, запускается каждые
несколько минут (предлагаю 5 минут — сезоны измеряются неделями, частая
проверка не нужна). На каждой итерации — независимо для КАЖДОГО
`chest_collectors`, у которого `period_end` не `NULL`:

1. Вычислить "время клана": `clan_now = utcnow() + timedelta(minutes=collector.timezone_offset_minutes or 0)`.
   **Важно**: `period_end` в БД хранится как буквальные цифры (как и `collected_at`,
   см. ANTI-PATTERNS.md "Время на публичной странице сундуков") — НЕ настоящий UTC.
   Сравнивать нужно как буквальные значения (naive-сравнение даты/времени без
   повторного TZ-сдвига), иначе сразу получим тот же +3ч баг, который только
   что чинили на фронте.
2. Если `clan_now >= period_end` (по буквальным цифрам) — закрыть сезон:
   - Посчитать summary тем же кодом, что использует `GET /chests/summary/{slug}`
     (вынести построение пивота в общую функцию, реюзать).
   - Записать строку в `chest_season_history` (с snapshot целей).
   - Удалить из `chests` все строки этого `collector_id` с
     `collected_at BETWEEN period_start AND period_end`.
   - Открыть новый сезон: `period_start = старый period_end`,
     `period_end = period_start + (старый period_end - старый period_start)`
     (та же длительность, что была — например 2 недели).
3. Если данных за сезон не было вообще (`summary["players"]` пусто) — всё равно
   архивировать пустой снимок и переоткрыть, чтобы цикл не завис.

### Retention — удаление старой истории

Отдельный ежедневный тик: `DELETE FROM chest_season_history WHERE closed_at < now() - interval '90 days'`.
Реюзаем паттерн `_cleanup_loop` из `server/roy.py` (там тоже периодическая
асинхронная задача).

### API

- `GET /chests/history/{slug}` — публичный (как текущий `/chests/summary/{slug}`,
  без токена управления): список закрытых сезонов коллектора
  (`period_start`, `period_end`, итоговые очки клана) + параметр `?season_id=`
  чтобы получить полный `summary_json` одного конкретного сезона.

### Frontend

- Публичная страница (`ChestSummaryPage.jsx`): блок/вкладка "История" со списком
  прошлых сезонов (даты), при выборе — рендерится той же таблицей, что и текущий
  сезон (реюз существующей разметки/CSS, включая sticky-шапку и tier-цвета).
- Кабинет (`/dashboard/chests`): аналогичный блок истории.

## Тестирование (TDD)

- Юнит-тесты на функцию построения summary (уже есть как часть `get_chest_summary`,
  выносим в реюзаемую функцию — тест на неё).
- Тест авто-цикла: коллектор с истёкшим `period_end` → после тика появляется
  строка в `chest_season_history`, `chests` за период очищены, `period_start`/
  `period_end` коллектора сдвинуты на следующий цикл той же длительности.
- Тест retention: строка истории старше 90 дней удаляется, моложе — остаётся.
- Тест snapshot целей: смена `target_points` ПОСЛЕ архивации не влияет на уже
  сохранённый `target_points_snapshot`.
- Тест на пустой сезон (без сундуков) — архивация не падает, цикл не виснет.

## Зоны риска / открытые решения для плана реализации

- Вынесение текущей логики пивота из `get_chest_summary` в реюзаемую функцию —
  затронет существующий рабочий эндпоинт, делать аккуратно с покрытием
  существующими тестами `test_chests.py` до и после рефакторинга.
- Сравнение "буквальных" datetime в Python (без реального tzinfo-сравнения) —
  нужно явно решить на уровне кода (например сравнивать `.replace(tzinfo=None)`
  с обеих сторон), не полагаясь на то, что Python сам разберётся.
