## 2.1 Единственный реальный прецедент конкурентности в проекте — `PacmanEngine` (1.0)

Прочитано лично, `navigator.py:930-1050`. Это единственный существующий в проекте пример
producer-подобного треда с `start()`/`stop()` — эталон для сравнения, не копируемый один в один (2.0 —
producer **и** consumer, 1.0 — только один тред), но реальный прецедент того, как здесь уже решались
похожие вопросы.

**`start()` (`navigator.py:988-997`):**
```python
def start(self):
    if self._thread and self._thread.is_alive():
        self._thread.join(timeout=3.0)
    ...
    self._thread = threading.Thread(target=self._run, daemon=True)
    self._thread.start()
```
- Тред создаётся с `daemon=True` — при завершении процесса Python убьёт его принудительно, без ожидания.
- **`join(timeout=3.0)` уже существует в проекте** — не в `stop()`, а защитным шагом внутри `start()`: если
  предыдущий тред ещё жив на момент повторного `start()`, `start()` ждёт до 3 секунд его естественного
  завершения, прежде чем создать новый. Это готовый, работающий в проде паттерн «bounded wait, потом
  действовать», а не то, что нужно изобретать с нуля для Части B.
- Число `3.0` нигде не обосновано явно (не найдено ни в коде, ни в спеках/памяти) — вероятно эмпирическое;
  Часть B не обязана его переиспользовать, но должна учитывать, что похожий бюджет ожидания уже принят как
  приемлемый в этом же коде для аналогичной задачи.

**`stop()` (`navigator.py:999-1000`):**
```python
def stop(self):
    self.is_running = False
```
Буквально — только флаг. **Не join, не ждёт**. Тред при `_run()`-цикле дообработает текущую итерацию и
выйдет сам, когда в следующий раз проверит `is_running`.

**`_run()` (`navigator.py:1006-1045+`):** цикл вида
```python
while self.is_running:
    ...
    if self.yolo_model is not None:
        if time.time() >= self._yolo_unblock_time:
            results = self.yolo_model.predict(...)   # потенциально медленный блокирующий вызов
            ...
    if not self.is_running:
        break
    ...
```
Флаг `is_running` проверяется **в двух точках** цикла: в заголовке `while` и сразу после блока YOLO. Между
этими точками (пока идёт `predict()`) `stop()` не может прервать поток — задержка выхода после `stop()` ≈
длительность текущего вызова `predict()`, если тред застал именно его. Для 2.0 аналогичная точка —
`YOLO.predict()` **и** OCR (`PositionReader.read()`, до 24 вызовов tesseract, зафиксировано в файле 15,
A-2/2.1) внутри consumer'а — потенциально куда дольше одного YOLO-вызова 1.0. Число `3.0` из `start()` 1.0
**нельзя** механически перенести на 2.0 без пересчёта под этот более медленный шаг.

**Вывод для Contract Extraction:** в проекте уже есть работающий прецедент «bounded join с таймаутом»,
но нет прецедента **точного места и величины** этого таймаута для потенциально более медленного consumer'а
2.0 (YOLO + OCR, а не только YOLO). Это подтверждает, что кластер A (жизненный цикл тредов) реален и не
тривиален — не «просто скопировать 1.0».
