# Спека: «Заполнить из Сундуков» — массовое добавление костяка клана в ростер Древнего

Дата: 2026-07-01
Статус: одобрено владельцем, готово к написанию плана реализации

## Проблема

Ростер Древнего (`AncientRoster`) сейчас наполняется только двумя способами:
строки из OCR турнирной таблицы (полная замена при каждом импорте бота) и
записи, которые лидер/редактор добавляет вручную по одной
(`POST /{slug}/roster/manual`, реализовано ранее в этой же сессии). Игрок,
который носит сундуки (есть в `PlayerAlias.canonical_name` этого коллектора),
но ещё ни разу не попал в турнирную таблицу и не добавлен вручную — не
отображается в ростере Древнего вообще.

Владелец хочет разовую кнопку «Заполнить из Сундуков»: массово добавить в
ростер весь актуальный костяк клана из базы Сундуков одним действием — для
подготовки к событию (назначить состав войск заранее, до турнира).

## Архитектура

Никаких изменений в существующей логике не требуется — новое значение
`AncientRoster.source` (`'chests'`, третье к уже существующим `'ocr'` и
`'manual'`) само по себе корректно проходит через уже построенные механизмы:

- **Расчёт квоты** (`ancients_dashboard.py calculate()`, Стратегия Б) уже
  берёт весь `AncientRoster` этого коллектора и включает в расчёт любую
  строку с проставленным `troop_level`, независимо от `source`. Изменений
  не требуется.
- **Удаление** (`DELETE /{slug}/roster/{player_name}`, уже реализовано) уже
  не фильтрует по `source` — удаляет любую строку. Изменений не требуется.
  Удалённая `'chests'`-строка не воскресает сама: заполнение — разовое
  действие по кнопке, не постоянная синхронизация.
- **Импорт турнира** (`tournaments.py`) уже: (а) исключает из
  full-replace-удаления только строки с `source == 'ocr'` — `'chests'`-строки
  переживут переимпорт так же, как сейчас переживают `'manual'`; (б) при
  апдейте существующей строки безусловно ставит `source='ocr'` — если игрок
  реально попадёт в турнирную таблицу, его `'chests'`-строка корректно
  становится обычной `'ocr'`-строкой. Изменений не требуется.
- **Тик сгорания ручных записей** (`ancient_retention.py`,
  `run_manual_entry_expiry_tick`) фильтрует строго `source == 'manual'` —
  `'chests'`-строки никогда не сгорают (это доверенная база, а не
  неподтверждённая догадка лидера). Изменений не требуется.

### Единственное новое: эндпоинт массового добавления

`POST /web/dashboard/ancients/{slug}/roster/populate-from-chests` — доступ
владелец **или** редактор (`_get_own_or_editor_collector`, как у всех
остальных write-эндпоинтов этого модуля).

Логика: взять все `PlayerAlias.canonical_name` этого коллектора, для каждого
имени, которого ещё нет в `AncientRoster.player_name` этого коллектора —
создать строку: `place=None`, `points=None`, `troop_level=None`, `rank=None`,
`source='chests'`, `manual_expires_at=None`. Имена, уже присутствующие в
ростере (любого `source`), пропускаются молча — без ошибки/предупреждения
(в отличие от ручного добавления одной записи, тут массовое действие и
дубли — ожидаемый штатный случай при повторном нажатии кнопки).

Ответ: `{"added": N}` — сколько новых строк добавлено, для короткого
UI-фидбека («Добавлено 12 игроков»).

### Фронтенд

Кнопка «Заполнить из Сундуков» в `AncientsPage.jsx`, рядом с формой ручного
добавления (Часть 5 предыдущей спеки). После клика — вызов нового
API-хелпера `dashboardAncientsPopulateFromChests(slug)`, короткое сообщение
с числом добавленных, `refresh()`.

## Тестирование (TDD)

- Пустой ростер + N алиасов в Сундуках → после вызова в ростере N строк с
  `source='chests'`, `place=None`, `points=None`.
- Повторный вызов на том же коллекторе → `added: 0`, дублей не появилось
  (уникальный индекс `(collector_id, player_name)` и так не даст, но тест
  фиксирует явно отсутствие ошибки/500 при столкновении).
- Имя уже есть в ростере (любой source, включая уже существующий `'ocr'`) →
  пропускается, не перезаписывается.
- Редактор (не только владелец) может вызвать эндпоинт.
- Существующий тест `run_manual_entry_expiry_tick` (уже есть с сессии) —
  добавить один новый case: `source='chests'` строка с искусственно
  выставленным прошлым `manual_expires_at` (аномалия, в реальности такого не
  бывает, но фиксирует что тик смотрит именно на `source=='manual'`, не на
  сам факт наличия даты) — тик её не трогает.
- Существующий тест на `tournaments.py` full-replace — добавить один case:
  `source='chests'` строка переживает переимпорт, аналогично уже
  протестированному `'manual'` case.

## Зоны риска / открытые решения для плана реализации

- Нет отдельной миграции: `source` уже `String(8)` без ограничения набора
  значений (enum), новое строковое значение `'chests'` не требует изменения
  схемы БД.
- Порядок полей в ответе `{"added": N}` и текст фронтенд-сообщения — не
  критично, разумные значения по контексту.
