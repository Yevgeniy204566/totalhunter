# Спека: «Заполнить из Сундуков» — массовое добавление костяка клана в ростер Древнего

Дата: 2026-07-01
Статус: одобрено владельцем, готово к написанию плана реализации

## Проблема

Ростер Древнего (`AncientRoster`) сейчас наполняется только двумя способами:
строки из OCR турнирной таблицы (полная замена при каждом импорте бота) и
записи, которые лидер/редактор добавляет вручную по одной
(`POST /{slug}/roster/manual`, реализовано ранее в этой же сессии). Игрок,
который носит сундуки (есть в `PlayerAlias.canonical_name` этого коллектора),
но ещё ни разу не попал в турнирную таблицу и не добавлен вручную — не
отображается в ростере Древнего вообще.

Владелец хочет разовую кнопку «Заполнить из Сундуков»: массово добавить в
ростер весь актуальный костяк клана из базы Сундуков одним действием — для
подготовки к событию (назначить состав войск заранее, до турнира).

**Пересмотрено после первого живого теста (2026-07-01):** первая версия была
чисто additive (только добавляла недостающих, не трогая существующие сырые
OCR-строки) — владелец увидел результат живьём и явно потребовал другого
поведения: «отзеркалить точный список имён с Сундуков... всё остальное
удалить». Ниже — уже финальная, пересмотренная версия архитектуры.

## Архитектура

Никаких изменений в существующей логике не требуется — новое значение
`AncientRoster.source` (`'chests'`, третье к уже существующим `'ocr'` и
`'manual'`) само по себе корректно проходит через уже построенные механизмы:

- **Расчёт квоты** (`ancients_dashboard.py calculate()`, Стратегия Б) уже
  берёт весь `AncientRoster` этого коллектора и включает в расчёт любую
  строку с проставленным `troop_level`, независимо от `source`. Изменений
  не требуется.
- **Удаление** (`DELETE /{slug}/roster/{player_name}`, уже реализовано) уже
  не фильтрует по `source` — удаляет любую строку. Изменений не требуется.
  Удалённая `'chests'`-строка не воскресает сама: заполнение — разовое
  действие по кнопке, не постоянная синхронизация.
- **Импорт турнира** (`tournaments.py`) уже: (а) исключает из
  full-replace-удаления только строки с `source == 'ocr'` — `'chests'`-строки
  переживут переимпорт так же, как сейчас переживают `'manual'`; (б) при
  апдейте существующей строки безусловно ставит `source='ocr'` — если игрок
  реально попадёт в турнирную таблицу, его `'chests'`-строка корректно
  становится обычной `'ocr'`-строкой. Изменений не требуется.
- **Тик сгорания ручных записей** (`ancient_retention.py`,
  `run_manual_entry_expiry_tick`) фильтрует строго `source == 'manual'` —
  `'chests'`-строки никогда не сгорают (это доверенная база, а не
  неподтверждённая догадка лидера). Изменений не требуется.

### Финальная версия: эндпоинт полного зеркалирования (не additive)

`POST /web/dashboard/ancients/{slug}/roster/populate-from-chests` — доступ
владелец **или** редактор (`_get_own_or_editor_collector`, как у всех
остальных write-эндпоинтов этого модуля).

Логика (mirror, не merge-only):
1. Взять все `PlayerAlias.canonical_name` этого коллектора — это целевой,
   окончательный список имён ростера.
2. Для каждой существующей строки `AncientRoster`:
   - если `player_name` **точно совпадает** с каноническим именем — данные
     (`place`/`points`/`troop_level`/`rank`/`source`) сохраняются как «лучшие
     известные» для этого канонического имени;
   - иначе если есть **подтверждённая** (`AncientNameMapping.confirmed=True`)
     запись `raw_ocr_name → canonical_name` — данные строки точно так же
     сохраняются, но уже под каноническим именем (переименование по факту);
   - иначе (нет никакой связи с базой Сундуков — включая вручную добавленные
     записи `source='manual'` для игроков, которых нет в Сундуках) — строка
     удаляется безвозвратно. Это осознанное требование владельца: кнопка
     означает «точная копия Сундуков», без исключений.
3. Все строки коллектора удаляются, затем создаются заново строго по списку
   канонических имён, используя сохранённые «лучшие известные» данные
   (`place`/`points`/`troop_level`/`rank`), либо `NULL`+`source='chests'`,
   если для имени не нашлось никакой существующей строки.

Ответ: `{"synced": N, "removed": M}` — сколько строк в итоговом ростере и
сколько было безвозвратно удалено (для UI-предупреждения после подтверждения).

### Фронтенд

Кнопка «Заполнить из Сундуков» в `AncientsPage.jsx` — теперь с двухшаговым
подтверждением (как «Удалить коллектор»/«Скрыть»), т.к. действие
деструктивно. Текст предупреждения явно называет, что вручную добавленные
записи тоже могут быть удалены. После подтверждения — вызов
`dashboardAncientsPopulateFromChests(slug)`, сообщение с итогами, `refresh()`.

## Тестирование (TDD)

- Пустой ростер + N алиасов в Сундуках → после вызова N строк с
  `source='chests'`, `place=None`, `points=None`; `removed: 0`.
- Повторный вызов на уже синхронизированном ростере → идемпотентно, тот же
  результат, без ошибок.
- Строка с именем, точно совпадающим с каноническим (например, бот уже
  верно распознал OCR) — сохраняет реальные `place`/`points`/`source='ocr'`.
- Строка с сырым OCR-именем + подтверждённым маппингом на каноническое имя —
  переименовывается, данные (`place`/`points`/`troop_level`) сохраняются,
  дубля не остаётся.
- Строка без всякой связи с Сундуками (в т.ч. `source='manual'` запись
  игрока, который не носит сундуки) — удаляется, `removed` увеличивается.
- Редактор (не только владелец) может вызвать эндпоинт.
- Взаимодействие с уже существующими механизмами (`run_manual_entry_expiry_tick`,
  full-replace в `tournaments.py`) не требует отдельных изменений — они уже
  корректно работают с `source='chests'`, тесты на это добавлены ранее в
  этой же сессии (см. предыдущий коммит `feat(ancients): bulk-populate...`).

## Зоны риска / открытые решения для плана реализации

- Нет отдельной миграции: `source` уже `String(8)` без ограничения набора
  значений (enum).
- Формат ответа `{"synced": N, "removed": M}` заменил изначальный
  `{"added": N}` — фронтенд обновлён синхронно, отдельного плана миграции
  API-контракта не требуется (единственный потребитель — этот же фронтенд,
  один коммит).
