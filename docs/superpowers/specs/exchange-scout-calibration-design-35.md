## 4.1 Единая структура данных (реализует C-02, C-08)

Заменяет три сегодняшние разрозненные структуры (`TUNE_TARGET_NAMES`, `_TUNE_POINT_TARGETS`,
`_CHEST_TUNE_RECTS`) и отдельное хранение `REF_A`/`REF_B` одним упорядоченным списком из 12 записей.
Поле `kind` — ровно три значения из C-02 (`точка`/`OCR-область`/`смещение-к-YOLO`); `REF_A`/`REF_B`
относятся к `kind="точка"` — они рисуются тем же крестиком, что и остальные точки (C-03), различие с
7 офсетными точками — не в типе, а в способе хранения (см. 4.2).

| Поле | Смысл |
|---|---|
| `id` | техническое имя (`ref_a`, `ref_b`, `wt_icon`, `carter`, `crypt_open`, `crypt_select`, `top_accel`, `march_accel`, `arena_reset`, `chest_sender`, `chest_type`, `chest_collect`) |
| `kind` | `точка` \| `OCR-область` \| `смещение-к-YOLO` (C-02) |
| `storage` | `absolute` (только `ref_a`, `ref_b` — `coord_manager._point_a/_point_b`) или `offset` (остальные 10 — `coord_manager.ui_offsets`, без изменения формата, C-05) |
| `theme` | необязательный тег группировки, независимый от `kind` (сегодня единственная тема — `сундуки` для `chest_sender`/`chest_type`/`chest_collect`; C-04) |
| `label_key` | ключ `LANGS` для подписи на экране |
| `ref_rect` | только для `kind="OCR-область"` — `chest_reader.SENDER_REF_RECT`/`SOURCE_REF_RECT` |
| `base_pos_fn` | только для `kind="точка"` с `storage="offset"` — та же функция, что уже в `_TUNE_POINT_TARGETS` (`main.py:5120-5135`), без изменений |

Значения `id`/`kind`/`storage`/`theme` для всех 12 — таблица файла 33 (2.2) плюс `ref_a`/`ref_b` из
`coord_manager.REF_A`/`REF_B`. Реестр — обычный Python-список словарей/дата-класс в `main.py` рядом с
существующими константами (`TUNE_TARGET_NAMES` и т. п. выводятся из употребления, не удаляются резко —
переходный период до полной миграции вызовов).

## 4.2 Единый вход и навигация (реализует C-01)

`self._cal_frame` **уже является** `CTkScrollableFrame` (`main.py:1845`) — единый вход строится внутри
него, ничего нового по типу виджета не вводится. `CTkOptionMenu` (дропдаун тюнинга) и отдельная кнопка
«калибровка A/Б» упраздняются как два независимых входа; вместо них — список из 12 строк (одна на цель
из реестра 4.1), каждая строка кликабельна и открывает **панель редактирования этой цели** ниже/рядом со
списком (тот же принцип «выбор из списка → область редактирования», что уже работает в тюнинге сегодня,
`main.py:5137-5162`, просто на 12 целей вместо 10+«Калибровка»).

**Способ редактирования зависит не от `kind`, а от `storage`:**
- `storage="absolute"` (`ref_a`, `ref_b`) — открывается существующий живой магнифайер
  (`calibration_ui.calibrate_one_point`, без изменений) — цена ошибки якорей кратно выше (файл 33, 2.6),
  точность лупы обоснованно сохраняется.
- `storage="offset"` (10 целей тюнинга) — существующий D-Pad + шаг 1px/5px (`main.py:5164-5199`), без
  изменений.

Это не нарушает C-01 (единственный пользовательский **вход** — список из 12 строк) и не требует
унификации самого способа правки числа, который контрактами не регламентирован.

## 4.3 Единая отрисовка маркера на тип (реализует C-03)

- `kind="точка"` — единый крестик `main._show_crosshair_at` (`main.py:3464-3488`) для всех точек, включая
  `ref_a`/`ref_b`. `calibration_ui._show_red_dot` выводится из употребления: магнифайер вызывает тот же
  `_show_crosshair_at` (модуль `calibration_ui.py` получает ссылку на метод главного окна через `parent`,
  который уже передаётся в `run_calibration`, `calibration_ui.py:212`).
- `kind="OCR-область"` — единый `main._show_chest_rect_overlay` (`main.py:3499-3526`), параметризованный
  произвольным `ref_rect`/`id` из реестра 4.1, а не только двумя захардкоженными сундуками.
- `kind="смещение-к-YOLO"` (`crypt_select`) — вместо тишины (сегодня ничего не показывается) добавляется
  **текстовая подпись** рядом с D-Pad: «Позиция определяется вживую по детекции склепа — статичное превью
  недоступно» (перевод существующего обоснования из комментария `main.py:5124-5130` в видимый пользователю
  текст, на всех 19 языках через `LANGS`). Это не новый визуальный маркер, а объяснение отсутствия маркера
  — снимает потенциальное «баг или так и задумано?» при унификации списка.

## 4.4 Независимость темы и типа (реализует C-04)

Каждая строка списка показывает **два независимых визуальных признака**: индикатор `kind` (единый на все
12 строк: маленькая иконка/значок — точка/прямоугольник/волна, одна и та же форма независимо от темы) и
подсветку `theme` (цвет текста подписи, как сегодняшний `TUNE_CHEST_GROUP`/`TUNE_CHEST_HIGHLIGHT_COLOR`,
`main.py:5083-5095`, — механизм не меняется, только применяется по полю `theme` из реестра, а не по
захардкоженному списку имён). Пользователь видит тип по значку и тему по цвету текста — одно не
подменяет другое, поэтому `chest_collect` (точка) и `chest_sender`/`chest_type` (области) остаются одной
темой, но разными значками типа.

## 4.5 Координатная модель не меняется (реализует C-05)

Реестр 4.1 — слой представления. Запись значения по-прежнему идёт через `coord_manager.calibrate()`
(для `storage="absolute"`) или `coord_manager.set_ui_offset()` (для `storage="offset"`) — без изменений
сигнатур и семантики (`coord_manager.py:57-68, 87-90`).

## 4.6 Видео-ссылка (реализует C-06)

Кликабельный текстовый элемент вверху вкладки калибровки (`webbrowser.open(url)` — модуль `webbrowser`
уже импортирован, `main.py:42`), подпись «Видео-инструкция (YouTube)» на 19 языках. `url` — именованная
константа-заглушка (`CALIBRATION_VIDEO_URL = ""`), реальный адрес подставляется владельцем позже
(Context, п.3, уже закрыт) — до этого элемент показывается неактивным/скрытым, а не битой ссылкой.

## 4.7 Рекомендуемые значения — зелёная зона (реализует C-07…C-10)

19 значений — константы из таблицы файла 32 (owner decision), один словарь `RECOMMENDED_VALUES = {slider_id:
value}`. Зона — сегмент дорожки `CTkSlider`, подсвеченный `MD3["green_btn"]`, шириной `±5%` диапазона
(`(to - from) * 0.05` в каждую сторону от рекомендуемого, обрезано по `[from, to]`) — C-10, провизорно.

Технически `CTkSlider` не поддерживает произвольный цветной сегмент дорожки «из коробки» (`progress_color`
красит только от начала до текущего значения бегунка, не независимый от него сегмент). Решение: тонкий
`Canvas`/`Frame`-оверлей, отрисованный поверх дорожки слайдера на этапе создания виджета (тот же общий
приём, что уже используется в проекте для оверлеев поверх других виджетов — `_show_chest_rect_overlay`,
`_dot_win` и т. п., просто как дочерний виджет в layout, а не отдельный `Toplevel`). Overlay пересчитывается
один раз при создании (диапазон и рекомендуемое значение фиксированы), не на каждое движение бегунка.

## 4.8 Порядок отображения 12 целей (закрывает non-goal 1, файл 34 — решение Design, не владельца)

Context (файл 32, «Что НЕ решено», п.1) явно передал этот вопрос в Design, не владельцу. Выбор: **порядок
использования в игровом сценарии** — калибровка сначала (`ref_a`, `ref_b`), затем цели по режимам в
порядке вкладок бота (`CLAUDE.md`, §3: Склепы → Биржи → Рефералы): `crypt_select`, `crypt_open`, `carter`
(Склепы) → `wt_icon`, `top_accel`, `march_accel`, `arena_reset` (общие/биржи) → `chest_sender`,
`chest_type`, `chest_collect` (Сундуки). Обоснование: пользователь калибрует бота в том порядке, в котором
потом им пользуется, а не по алфавиту/порядку объявления в коде — это соответствует уже принятому owner
decision 5 (файл 32) о том, что пользователь должен «однозначно понимать, что именно сейчас калибруется».

## 4.9 Non-goals этого Design (не расширяются сверх контрактов)

1. Не меняется способ редактирования офсетов (D-Pad остаётся) и якорей (магнифайер остаётся) — только
   точка входа в них унифицируется (4.2).
2. Не вводится новый формат профиля/`gui_config.json` — реестр 4.1 не сериализуется отдельно, он
   вычисляется в коде при старте GUI.
3. Ширина зелёной зоны (±5%) и цвет (`MD3["green_btn"]`) — провизорные (C-10), меняются при реализации
   без нового owner decision, если понадобится.
4. Раздел 2 (рекомендуемые значения) не получает собственного входа/вкладки — зона рисуется на
   существующих 19 слайдерах на своих текущих местах, без реорганизации вкладок.
