## 2.1 Два структурно не связанных друг с другом механизма

**Механизм 1 — калибровка якорных точек A/Б** (`calibration_ui.py`, вызывается из `main.py:_calibrate`,
`:4972-4986`). Отдельная кнопка сворачивает главное окно (`self.iconify()`, не `withdraw` — комментарий в
коде явно объясняет: `withdraw` ломает дочерние Toplevel) и последовательно открывает **два отдельных
модальных окна** — по одному на точку — с живым zoom-магнифаером (`_grab_region_live`, 600%, обновление
каждые 150 мс), кликом по лупе для смещения, ручными спинбоксами X/Y и кнопками «Зафиксировать»/«Отмена».
Возврат — `coord_manager.calibrate(point_a, point_b)`, который пересчитывает `scale_x`/`scale_y` от разницы
между `REF_A`/`REF_B` (эталон 1920×1080) и введёнными пользователем экранными координатами.

**Механизм 2 — тюнинг 10 целей** (`main.py:5047-5210`). Выпадающий список (`CTkOptionMenu`, 11 пунктов:
«Калибровка» + 10 имён из `TUNE_TARGET_NAMES`) переключает отображение **внутри той же вкладки**, без
сворачивания окна. Редактирование — крестовина D-Pad (▲◄►▼, шаг 1px/5px), не клик по изображению.

**Ключевое отличие в данных, не только в UI:** `REF_A`/`REF_B` — это **абсолютные экранные координаты**
(`coord_manager._point_a`/`_point_b`, устанавливаются напрямую). Все 10 целей тюнинга — это **смещения
`[dx, dy]`** (`coord_manager.ui_offsets`, `coord_manager.py:41,53-55`), прибавляемые к уже вычисленной
базовой позиции (`get_ui_offset`/`set_ui_offset`, `:82-90`). Это не два варианта одного механизма, а два
разных типа хранимых данных с разной семантикой редактирования — «поставить точку» и «подвинуть уже
существующую точку».

## 2.2 Три разных типа целей внутри одного списка тюнинга — источник неоднозначности точка/область

Хотя все 10 целей тюнинга формально равноправны в `TUNE_TARGET_NAMES`, код фактически различает **три
типа** с разным визуальным откликом (`main.py:5102-5142`):

| Тип | Имена | Оверлей при выборе | Источник |
|---|---|---|---|
| **Точка** (7) | `wt_icon`, `carter`, `crypt_open`, `top_accel`, `march_accel`, `arena_reset`, `chest_collect` | живой крестик поверх игры (`_show_crosshair_at`) в точке клика с учётом офсета | `_TUNE_POINT_TARGETS`, `:5120-5135` |
| **Область** (2) | `chest_sender`, `chest_type` | рамка-прямоугольник поверх игры (`_show_chest_rect_overlay`) — это зоны чтения OCR, не точки клика | `_CHEST_TUNE_RECTS`, `:5102-5105` |
| **Динамическая, без статичного превью** (1) | `crypt_select` | **ничего** — ни крестик, ни рамка | комментарий `:5124-5130` |

**Находка прямо по запросу — где UI может создавать неоднозначность точка/область.** Пользователь выбирает
любую из 10 целей из **одного и того же выпадающего списка**, крутит **один и тот же** D-Pad — но получает
на экране либо крестик, либо рамку, либо вообще ничего, в зависимости от типа, который никак не обозначен
в самом списке (кроме подсветки текста для группы сундуков — см. 2.4). `chest_sender`/`chest_type`
находятся в **одной подсвеченной группе** с `chest_collect` (`TUNE_CHEST_GROUP`, `main.py:135`), но
`chest_collect` — точка, а первые два — области; группировка по цвету сейчас основана на «это про сундуки»,
а не на «это одного типа объект». Ровно тот сценарий, который просил проверить владелец: визуальная
унификация («все три — сундуки, значит один стиль») уже сегодня рискует **скрыть** реальное различие
точка/область, если её делать не глядя на эту таблицу.

**`crypt_select` — третий, отдельный случай, не «недоделанный», а осознанный.** Комментарий в коде
(`main.py:5124-5130`) объясняет: Y этой кнопки определяется живым YOLO-детектом склепа в списке, а не
фиксированной точкой — статичный крестик «был бы враньём». Офсет для неё всё равно настраивается через
тот же D-Pad, суммируясь с живой позицией в `crypt_hunter.py:_scroll_and_find`. Это не пробел в
реализации, которую нужно «доделать до единообразия» — это осознанная граница: не у каждой из 12 целей
физически может быть корректное статическое превью.

## 2.3 Уже существующий, но не переиспользуемый между механизмами код отрисовки маркера

Обе точки A/Б и все 10 целей тюнинга концептуально делают одно и то же — «показать, где сейчас находится
точка на экране» — но код рисует это **двумя независимыми реализациями**:

- `calibration_ui.py:_show_red_dot` (строки 54-66) — используется только внутри `run_calibration()` для
  A/Б. Красный квадратный `Toplevel` с белыми крестообразными линиями, без авто-скрытия.
- `main.py:_show_crosshair_at` (строки 3464-3488) — используется для (а) джойстик-центра (`_show_calibration_dot`)
  и (б) превью точки при тюнинге (`_tune_show_point_crosshair_if_relevant`). Красный круг с жёлтой
  обводкой, авто-скрытие через 3 секунды. **Уже документирован в самом коде как намеренно переиспользуемый**
  между двумя случаями («Shared by the joystick-center dot and the click-tuning preview so every action
  that sets cursor coordinates gets the same marker», `main.py:3466-3467`) — то есть частичная унификация
  уже была сделана раньше, просто не распространена на калибровку A/Б.

`_show_chest_rect_overlay` (`main.py:3499-3526`) для областей **намеренно копирует паттерн**
`_show_crosshair_at` (тот же Toplevel + `after`-таймер 3с), о чём прямо говорит комментарий в коде
(«mirrors `_show_calibration_dot`'s Toplevel/after pattern but sized to the real crop»). То есть на уровне
паттерна реализации согласованность уже есть; на уровне общего переиспользуемого кода — нет (три похожие,
но отдельные функции: квадрат с крестом, круг с крестом, прямоугольник).

## 2.4 Статичные иллюстрации — тоже два разных представления

Для A/Б (`main.py:4798-4841`) — **два постоянно видимых** цветных «card»-виджета side-by-side (сетка
1×2): у каждого свой цвет подписи (`MD3["primary"]` для А, `#B060FF` для Б), статичный PNG
(`calib_point_a.png`/`calib_point_b.png`, 175px), текстовое описание.

Для 10 целей тюнинга (`main.py:4843-4869`) — **один** `CTkLabel`, переключаемый по выбору в списке
(`_show_tune_image`, картинка из `_TUNE_SCREEN_MAP`, 380px), без цветового кода конкретной цели, без
постоянного присутствия — виден только пока эта цель выбрана.

**Существующая частичная группировка по цвету:** подсветка текста в самом выпадающем списке для группы
сундуков (`tune_chest_group_entry_indices`, применяется в `_tune_apply_chest_highlight`,
`main.py:5083-5095`, цвет `TUNE_CHEST_HIGHLIGHT_COLOR`) — рабочий прецедент «выделить подмножество цветом
текста внутри одного списка», уже применяемый в проекте. Это ближайший существующий инструмент к
требованию «единый визуальный язык, различия только там, где значимы» (Context, owner decision 5) — но
сейчас группировка по цвету идёт по теме («сундуки»), а не по типу объекта («точка» vs «область»), что и
создаёт находку 2.2.

## 2.5 Вкладка и навигация

`_show_calibration_tab` (`main.py:3413-3422`) — отдельная янтарная кнопка вне сегментированной группы
режимов (не взаимоисключающая: возврат идёт на ту же вкладку, что была открыта до неё, через
`_toggle_cal`/`_active_tab_key`, `:3424-3430`). Калибровка A/Б доступна только через отдельную кнопку
внутри этой вкладки, минуя выпадающий список тюнинга полностью — списка, объединяющего все 12 целей в одном
месте, сегодня не существует.

## 2.6 Область действия координат — асимметрия по значимости, не по стилю

`REF_A`/`REF_B` через `coord_manager.to_screen()`/`to_screen_dialog()` лежат в основе **практически всех**
игровых кликов проекта (используются во множестве файлов — `navigator.py`, `crypt_hunter.py`, `main.py` и
др.). Офсеты 10 целей тюнинга потребляются точечно, каждый в своём узком месте вызова (например,
`crypt_select` — только в `crypt_hunter.py:_scroll_and_find`). Это не влияет на визуальный стиль
единой панели, но объясняет, почему A/Б исторически получили более тщательный отдельный UI (живой
магнифайер, а не просто D-Pad) — цена ошибки калибровки анкеров кратно выше цены ошибки в одном офсете.

## Дальше

Материала достаточно для Contract Extraction (Stage 3) по разделу 1 (единая панель). Ключевой вход для
Design, который Stage 3 должен явно унести дальше, не решая сам: **тип цели (точка/область/динамическая)
должен быть частью данных о каждой из 12 целей, а не выводиться из того, в какой отдельной структуре кода
(`_TUNE_POINT_TARGETS` vs `_CHEST_TUNE_RECTS` vs ничего) она сегодня перечислена** — иначе единый список
физически нельзя будет отрисовать по одному правилу.
