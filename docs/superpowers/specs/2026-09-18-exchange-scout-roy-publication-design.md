## Стадия 1. Context

Цепочка 2.0 (решение владельца, дословно по смыслу): **YOLO нашёл биржу → списать 10◆ → показать пользователю
находку → обработать сохранённый скрин → получить из него координаты → выложить находку на сайте в разделе
«Рой».**

Закрытые решения владельца, не предмет обсуждения здесь:
1. Telegram для публикации не используется — только сайт.
2. Механизма выкладки на сайт нет — его проектирует этот документ.
3. Дедупликация находок сейчас НЕ нужна (никакой защиты от повторной находки одной биржи).
4. Биржа 1.0 и её код/защиты не меняются (`feedback_exchange_10_untouchable`).
5. Очередь скриншотов не ограничена, кадры не выбрасываются (пауза змейки на пороге — балансировка, не лимит).
6. X/Y из OCR — координаты позиции экрана в момент кадра, а не самой биржи; владелец знает, что этого
   достаточно для визуального поиска на месте («примерное расположение»).

Что считается «сайтом»: `https://total-hunter.com`, страница РОЙ (`web/src/pages/RoyPage.jsx`), API —
`https://api.total-hunter.com` (`roy/roy_client.py:8`).

## Стадия 2. Code Archaeology — что реально есть (всё открыто и прочитано лично)

**2.1 Страница РОЙ на сайте показывает только королевства, координат на ней нет.**
`web/src/pages/RoyPage.jsx`: данные — `fetch(.../roy/kingdoms)` (:25) и `EventSource(.../roy/status-stream)`
(:30); тело страницы — список `kingdoms.map(...)` (:84-110): точка статуса, номер королевства, счётчики.
Ни `pool`, ни `x/y` в файле нет (grep по `pool|coord|\.x\b` нашёл лишь текст meta-описания :19).
Текст meta говорит «Коллективный пул координат бирж» — на странице этого пула нет. Страница двуязычная
(`isRu`), других языков нет.

**2.2 `POST /roy/report` — существующий канал координат 1.0 (`server/roy.py:244-294`).**
- Схема `ReportRequest`: `hwid, kingdom, x, y, percent` — `percent: int` **обязателен** (:192-197). У 2.0
  процента нет: диалог биржи не открывается.
- Rate limit `RATE_LIMIT_SEC = 10` с одного hwid (:39, :256-258): при превышении возвращает
  `{"success": True, "note": "rate_limited"}` — **молча отбрасывает** запись, клиент видит «успех».
- Дедуп по (kingdom, x, y) с продлением TTL (:266-278); `UniqueConstraint` в `models.py:274-277`.
- TTL записи 20 мин (`POOL_TTL_MIN = 20`, :33).
- После записи — `_broadcast(db, pool_updated=True)` (:289) → SSE-подписчики.
- При новой записи во время ивента «Торговые Пути» — тизер в Telegram (:291-292, `send_telegram_alert`).

**2.3 Пул `roy_pool` потребляют боты 1.0.** `GET /roy/pool` стоит `POOL_COST_SEC = 60` баланса времени (:37);
клиент — `roy/roy_client.py:87-96`; в `main.py:4213` новые записи пула вызывают звук (`truly_new`).
→ Запись примерных координат 2.0 в `roy_pool` подсунула бы ботам 1.0 неточные данные и изменила бы поведение
1.0. **Переиспользовать `/roy/report` и `roy_pool` для 2.0 нельзя** (вывод из 2.1-2.3).

**2.4 Источник номера королевства.** `PositionReader` K не читает; в `scout_results.jsonl` поля `kingdom` нет
(Часть A, C-10, `…-part-a-02-contracts-design.md` §4.6). В GUI есть поле номера королевства:
`self._roy_kingdom_entry` (`main.py:3955-3970`), `_get_roy_kingdom()` возвращает `0`, если поле пустое или не
число (`main.py:4141-4145`). Сервер показывает только королевства с `k > 0` (`roy.py:130`).
Решение владельца: номер королевства берётся от участников, исследующих это королевство, — они вносят его
**сами и добровольно** в это поле; бот его не определяет и не проверяет. Публикация 2.0 использует то же поле.
**Номер королевства (со слов участника) и X/Y (прочитаны OCR с сохранённого скрина, где YOLO нашёл биржу)
независимы друг от друга** — из одного источника они не выводятся и друг с другом не сверяются.

**2.5 Клиент РОЙ.** `RoyClient.report()` — fire-and-forget в отдельном **не-daemon** треде, `_TIMEOUT = 5`,
все исключения проглатываются (`roy/roy_client.py:9, 27-48`). Это готовый прецедент формы клиентского вызова.

**2.6 Валидация hwid на сервере — прецедент.** `/use_credit` проверяет существование пользователя и бан:
404 «User not found» / 403 «Banned» (`server/main.py:324-332`). `/roy/report` hwid не проверяет вообще.

**2.7 Тесты сервера РОЙ.** `server/tests/test_roy.py`: `pytest.mark.asyncio`, `AsyncClient` +
`ASGITransport`, фикстура `db_session`, autouse `clear_roy_rate_limits` (:17-18).

**2.8 Аналоги.** Публичного списка координат в РОЙ **нет** (2.1). Ближайший фундаментальный механизм —
пара «клиентский метод `RoyClient` + серверный эндпоинт в `roy.py` + чтение страницей сайта»; берётся как
форма, семантика `roy_pool` — нет (2.3).

## Стадия 3. Contract Extraction

Формат: `Требование → Контракт → Enforcement → Verification`. Нумерация: контракты **P-**, находки **PA-**,
тесты **PT-** (не пересекаются с C-/A-/T- других спек).

| № | Контракт | Enforcement (планируемый) | Verification |
|---|---|---|---|
| P-01 | Порядок: списание 10◆ **успешно** → показ находки → OCR скрина → публикация. Публикация не вызывается, если списание не прошло или OCR не вернул координаты. | ветка consumer'а: `publish` вызывается только при `charged is True and coords_ok is True` | PT-01, PT-02 |
| P-02 | Публикуются ровно: `kingdom` (int > 0), `x` (int), `y` (int). Время `found_at` ставит сервер. Не публикуются: hwid (наружу), изображение, `percent`, `conf`, `box`. | pydantic-схема `ScoutFindRequest` + публичная схема ответа без hwid | PT-03, PT-04 |
| P-03 | Отдельный механизм: новая таблица `roy_scout_finds` и эндпоинт `POST /roy/scout-find`. **Не** используются `/roy/report`, `roy_pool`, `_report_rate`, `_broadcast(pool_updated=True)`, `send_telegram_alert`. | отдельная функция в `server/roy.py`, отдельная модель в `server/models.py`, alembic-миграция | PT-05 |
| P-04 | Для публикации 2.0 нет rate limit и нет дедупликации (решение владельца). Каждый вызов = новая строка. | в коде эндпоинта нет лимитера и нет `UNIQUE` на (kingdom,x,y) | PT-06 |
| P-05 | Валидация: `hwid` существует и не забанен (404/403 как в `/use_credit`); `kingdom > 0`; `x`, `y` — целые. | проверка пользователя как `server/main.py:324-332` + pydantic `int` + `kingdom >= 1` | PT-07, PT-08 |
| P-06 | Клиент: если `_get_roy_kingdom()` вернул `0`, публикация **не выполняется** (сервер такое королевство не показывает, `roy.py:130`); причина пишется в лог сессии. Списание при этом уже состоялось (P-01) — находка остаётся в `scout_results.jsonl`. | проверка `kingdom > 0` в клиентском методе перед запросом | PT-09 |
| P-07 | Публикация не блокирует consumer: вызов идёт в отдельном треде с `_TIMEOUT = 5`, как `RoyClient.report()` (2.5); consumer сразу берёт следующий кадр. | новый метод `RoyClient.report_scout_find()` по образцу `report()` | PT-10 |
| P-08 | Сбой публикации (сеть, 4xx/5xx, таймаут) НЕ отменяет списание и НЕ теряет находку: находка уже записана локально (`scout_results.jsonl`, Часть A §4.6); повтор публикации не делается (non-goal), сбой пишется в лог сессии. | `try/except` вокруг запроса, исключение не выходит из треда | PT-11 |
| P-09 | Чтение сайтом: публичный `GET /roy/scout-finds` (без авторизации) возвращает список `{kingdom, x, y, found_at}`, новые первыми; hwid в ответе отсутствует. Показываются только находки не старше **20 минут** (`found_at > now - 20 мин`, P-13). | отдельная функция в `roy.py` с явным `select` только этих колонок | PT-12 |
| P-10 | Сайт: на `RoyPage.jsx` добавляется блок «Находки Биржи 2.0» (список из P-09), данные грузятся при открытии страницы и кнопкой «Обновить». Существующий список королевств и SSE не меняются. | отдельный `useEffect`/`fetch`, отдельное состояние | PT-13 (ручная проверка страницы) |
| P-11 | Текст на сайте — только факты: «Примерное расположение: позиция экрана бота в момент кадра, не точные координаты биржи». Языки — те же, что у страницы (RU/EN). | строки в `RoyPage.jsx` по образцу `isRu` | PT-13 |
| P-13 | Срок жизни находки на сайте — **20 минут** (решение владельца, как у пула 1.0). Константа `SCOUT_FIND_TTL_MIN = 20` — **своя**, не `POOL_TTL_MIN` (правка общей константы задела бы 1.0). Чтение отфильтровывает старше срока; каждая вставка в `scout-find` удаляет строки старше срока (общий `_cleanup_loop` не трогаем). | фильтр в `select` + `delete` в той же транзакции вставки | PT-15, PT-16 |
| P-12 | Биржа 1.0 не затронута: `/roy/report`, `/roy/pool`, `roy_pool`, `_report_rate`, SSE-поток, `RoyClient.report/get_pool` остаются байт-в-байт прежними. | добавляются только новые символы; существующие не редактируются | PT-05, PT-14 |

Неявные границы контрактов: P-09/P-10 — единственное, что видит посторонний посетитель сайта; всё, что не
перечислено в P-02, наружу не выходит.

## Стадия 4. Design

**4.1 Данные.** Таблица `roy_scout_finds`: `id` (PK), `kingdom` (Integer, index), `x`, `y` (Integer),
`reporter_hwid` (String(16), для админской трассировки, наружу не отдаётся), `found_at`
(`TIMESTAMP(timezone=True)`, `server_default=func.now()`, index). Типы — по образцу `RoyPool`
(`models.py:279-289`). Без `UNIQUE` (P-04).

**4.2 Серверные эндпоинты (в `server/roy.py`, router `/roy`).**
- `POST /roy/scout-find` — тело `{hwid, kingdom, x, y}`. Шаги: найти пользователя → 404/403 (P-05) → вставка
  строки → `commit` → `{"success": True}`. Одна транзакция, `async with db.begin()` как в остальном файле.
  SSE не трогается.
- `GET /roy/scout-finds` — публичный список (P-09).

**4.3 Клиент.** В `roy/roy_client.py` — новый метод `report_scout_find(kingdom, x, y)`; существующие методы не
меняются. Вызывается consumer'ом 2.0 после OCR (Часть B определит точку вызова).

**4.4 Сайт.** Новый блок под списком королевств в `RoyPage.jsx`: заголовок, поясняющая строка (P-11), список
`K · X · Y · время`, кнопка «Обновить», пустое состояние.

**4.5 Внешние вызовы и отказы** (A — ошибка, B — зависание, C — повтор, D — дважды, E — частично, F — параллельно):

| Вызов | A | B | C | D | E | F |
|---|---|---|---|---|---|---|
| `POST /roy/scout-find` из клиента | лог, находка остаётся локально (P-08) | таймаут 5 с, тред завершается (P-07) | повтора нет (non-goal) | две строки — решение владельца (P-04) | транзакция БД атомарна: строка есть или нет | два процесса 2.0 одного hwid — две независимые вставки, конфликтов нет |
| `GET /roy/scout-finds` с сайта | блок показывает пустое состояние/ошибку | браузерный таймаут по умолчанию | безопасен (read-only) | безопасен | — | безопасен |

**4.6 Состояния одной находки (что происходит при сбое/повторном запуске).**
`FOUND → CHARGED → SHOWN → OCR_DONE → PUBLISH_SENT → {PUBLISHED | PUBLISH_FAILED | SKIPPED_NO_KINGDOM |
SKIPPED_NOT_CHARGED | SKIPPED_NO_COORDS}`. Переходы вперёд необратимы. Краш процесса между `CHARGED` и
`PUBLISH_SENT`: кредит списан, находка есть в `scout_results.jsonl` (если запись сделана до краха — порядок
записи определяет Часть B), публикация не выполнена и **при рестарте не доигрывается** (нет журнала повторов —
non-goal).

**4.7 Non-goals (явно вне документа).** Публикация изображения/кропа мини-карты (в `CLAUDE.md` запрещено
хранить файлы на GCP; в цепочке владельца только координаты); повтор неудачной публикации; дедупликация;
live-обновление сайта через SSE; уведомления/звук у других пользователей; сортировка/фильтры на сайте;
правка Части A (`scout_results.jsonl` не получает новых полей).

## Стадия 5. Adversarial Review (формула `claim → mechanism → bypass → result`)

- **PA-1. «Посторонний не увидит hwid».** Механизм: явный `select` колонок (P-09). Обход: `SELECT *` в
  будущей правке. Результат: тест PT-04 падает, если в JSON ответа есть `hwid`/`reporter_hwid`.
- **PA-2. «Через x/y нельзя внедрить разметку».** Механизм: только `int` (pydantic) + React экранирует текст.
  Обход: строка вместо int → 422, строка в БД не попадёт. Результат: безопасно; PT-03.
- **PA-3. Флуд публичной страницы.** Механизм: только hwid существующего небаненого пользователя (P-05).
  Обход: любой зарегистрированный (в т.ч. бесплатный триал) может слать без лимита, а server не связывает
  публикацию со списанием. **Контрпример найден и ПРИНЯТ:** rate limit и дедуп запрещены решением владельца
  (P-04); ограничение — бан пользователя. Это осознанный остаточный риск, не закрытый механизмом.
- **PA-4. Один и тот же объект в нескольких кадрах.** Без дедупа список содержит повторы одной биржи.
  Принято владельцем (решение 3). Не «баг», ожидаемое поведение.
- **PA-5. Путь к записи без списания (НЕ принятый риск, описан отдельно).** Штатная цепочка гарантирует порядок
  P-01: публикация вызывается только после успешного списания. Но `POST /roy/scout-find` принимает только
  hwid, сервер не видит факта списания, поэтому вызов модифицированным клиентом в обход списания сервер не
  отличит. Этот документ путь не закрывает: закрытие требует связи публикации со списанием на сервере
  (новая механика, вне scope). Не заносится в «принятые риски»; решение — за владельцем, если понадобится.
- **PA-6. Рост таблицы.** Без очистки `roy_scout_finds` растёт бесконечно; БД сейчас 38 МБ, e2-micro (проверено
  сегодня). Механизм очистки — P-13 (срок 20 мин, решение владельца); очистка при вставке — в самой функции
  `scout-find`, а **не** в общем `_cleanup_loop` (`roy.py:168`), чтобы не менять поведение 1.0.
- **PA-7. Зависший сервер блокирует consumer.** Механизм: отдельный тред + `timeout=5` (P-07). Обход: много
  зависших запросов подряд → много тредов по 5 с. Результат: конечно (каждый тред живёт ≤5 с), но число
  одновременных тредов не ограничено — принято: находок бирж мало.
- **PA-8. Смена королевства в GUI между находкой и публикацией.** `_get_roy_kingdom()` читается в момент
  публикации, а не находки. Возможна публикация в «не то» королевство. Принято: смена во время сканирования —
  нештатное действие пользователя. Так же принято, что номер вводится добровольно и не проверяется: участник
  может указать неверное королевство — тогда находка появится под чужим номером (сервер это не отличает).
- **PA-9. Изоляция 1.0.** Механизм: только новые символы (P-12). Обход: правка общего `_broadcast`. Результат:
  запрещена P-03; PT-14 проверяет, что `GET /roy/pool` и `roy_pool` не меняются после публикации 2.0.
- **PA-10. Порядок P-01 при таймауте ответа списания.** Если ответ `/use_credit` потерян, `charged` неизвестен →
  публикация **не выполняется** (`charged is True` — строгая проверка). Результат: находка не выложена, кредит
  мог списаться — вопрос потерянного ответа разобран в спеке монетизации (§2.8).
