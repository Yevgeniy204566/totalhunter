Уточнение к C-04/C-05 (найдено ревью этого раунда): **контракты не были потеряны** — C-04 всегда был
покрыт архитектурно Design 4.4, C-05 всегда был покрыт PC-02/PC-05 (Stage 7, файл 42, был прав). Пропуск
был именно в отсутствии **отдельного именованного test path**, уже названного спекой (T-04/T-05) — Stage
7 корректно оценил покрытие контракта, но не сверился построчно со списком тестов `tests-gate-37.md`;
это сверка, которую производит именно Stage 9, не повторная находка «контракт был потерян».

**Ни один обязательный контракт спеки не потерян/ослаблен:** проверено построчно C-01…C-06 выше — все
на месте, ни один PC не ослабляет формулировку спеки (например PC-02 требует `==`, не подмножество,
хотя спека формально допускала бы более слабую трактовку C-05).

**Ни один плановый шаг не противоречит спеке:** самопротиворечия, найденные в предыдущих раундах
(`tune_card` 4.2, границы кода Stage 0, PC-04/«не удаляются резко»), были противоречиями ПЛАНА самому
себе, не плана спеке — все закрыты. Отдельных противоречий план↔спека не найдено.

**Каждый acceptance criterion спеки имеет implementation path; там, где применим runtime-test — он
именован:** таблица выше — 100% строк C-01…C-06 и релевантных A-1/A-3/A-4 имеют путь к коду; из них
все, кроме A-4, имеют именованный runtime-тест (файл 41). A-4 — implementation path без теста по
построению (см. разбор выше), не пропуск.

**План не добавляет изменения вне scope спеки без явного решения:** PositionReader/OCR-geometry/
PLAN-B/Scout Priority — ни одного из них нет в файлах 38-42 как код для изменения (Self-Audit, файл 42,
раздел 7.4); все явно припаркованы отдельно в памяти сессии по решению владельца.

**State transitions и failure semantics, применимые к PLAN-A, проверены и совпадают со спекой, не
переизобретены:** координатная модель (`coord_manager.calibrate()`/`set_ui_offset()`) не меняется
(C-05, PC-02/PC-05) — буквально то же, что требует спека, не альтернативная реализация; переходы
состояния выбора цели (`selected_id`/видимость `tune_card`) — новая для PLAN-A стадия работы, но не
описана спекой как конкретные transitions (спека фиксирует только контракты C-01…C-06, а не конкретный
state machine выбора — тот появился только в Design этого PLAN, файл 40) — переизобретения нет, потому
что переизобретать было нечего, спека этот уровень детализации сознательно не покрывает (Design,
не Contract Extraction спеки). **Concurrency — N/A** (Tk single-thread, обосновано в 9.1). **Resource
budgets — N/A** (PLAN-A не вводит retry/фоновые worker'ы/сетевые вызовы, обосновано в 9.1) — оба явно
проверены и отклонены как неприменимые, не молча пропущены.

### 9.3 Итог Final Gate

Все блокирующие условия протокола проверены и закрыты. SPEC→PLAN consistency check прошёл с одной
существенной находкой: **список именованных тестов Раздела 1 в `tests-gate-37.md` не был полностью
отражён в PLAN.** T-04/T-05 отсутствовали как test path (хотя сами контракты C-04/C-05 были покрыты),
T-01/T-06 имели PLAN-специфичные имена вместо имён спеки, T-02 был поглощён существующим более широким
тестом, T-11/T-13 получили cross-reference на более сильные существующие тесты. Всё исправлено в этом
же раунде, не отложено.

**PLAN-A (файлы 38-43) проходит Final Gate.**
