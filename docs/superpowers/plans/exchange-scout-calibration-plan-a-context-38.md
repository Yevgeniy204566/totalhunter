## Стадия 0 — Scope Decomposition Gate

Спека закрывает ДВА раздела: Раздел 1 (единый реестр 12 целей калибровки, Design 4.1–4.5, 4.8) и
Раздел 2 (зелёная зона на 19 существующих `CTkSlider`, Design 4.7). Проверка по критерию протокола
(«один функционал vs несколько независимых частей»):

- **Разный код.** Раздел 1 трогает только вкладку Калибровки (`main.py:4772–5229`,
  `coord_manager.py`) — один самодостаточный виджет-дерево (`self._cal_frame`). Раздел 2 трогает 19
  слайдеров, физически расположенных на ДРУГИХ вкладках (навигация `main.py:1920–2180`, крипт-слайдеры
  `main.py:2440–2520`, комбо `main.py:3140–3160`, сундуки `main.py:4560–4600`) — вкладки Калибровки не
  касается вообще.
- **Разный механизм.** Раздел 1 — замена структуры данных и точки входа в уже существующий UI
  (список вместо дропдауна, тот же D-Pad/магнифайер). Раздел 2 — НОВЫЙ визуальный примитив, которого в
  проекте нет: цветной сегмент дорожки слайдера через `Canvas`/`Frame`-оверлей с обязательным
  resize-инвариантом (Design 4.7, последний абзац). Ни один enforcement-механизм не общий между
  разделами.
- **Разный риск.** Раздел 2 явно помечен Adversarial Review (файл 36, находка A-2) как требующий
  ОТДЕЛЬНОГО живого resize-теста, не только чтения кода — это самостоятельный источник находок, который
  не должен блокировать более простой и уже до деталей проработанный Раздел 1.

**Решение (Stage 0, в рамках уже одобренных владельцем полномочий на реализационные решения):
разделить на PLAN-A (этот файл, Раздел 1 — единый реестр) и PLAN-B (Раздел 2 — зелёная зона,
отдельный файл позже).** Простая и полнее проработанная часть (Раздел 1) идёт первой согласно
правилу протокола «простая часть реализуется и закрывается первой». PLAN-B не начинается, пока PLAN-A
не пройдёт Final Gate и не будет одобрен владельцем (User Review, Stage 10) — «часть за частью, не
пачкой».

**Ключевой факт для Design 4.2:** `ref_a`/`ref_b` НИКОГДА не были частью `tune_card`/дропдауна — они
редактируются отдельной кнопкой (`_cal_manual_btn` → `run_calibration`), физически выше по вкладке.
10 целей тюнинга УЖЕ используют один общий набор виджетов редактирования (`tune_card`) на все 10 —
меняется только `_tune_idx` и то, что подставляется в `_tune_display_lb`/картинку/оверлей. То есть
«единая панель редактирования» для offset-целей уже реализована сегодня; PLAN-A должен расширить это
общее редактирование, поглотив выбор через СПИСОК вместо `CTkOptionMenu`, и добавить `ref_a`/`ref_b`
как ещё 2 строки списка, ведущие к магнифайеру вместо `tune_card` (Design 4.2 — способ редактирования
зависит от `storage`, не унифицируется).

**Реестр офсетов — `coord_manager.py:41` `_UI_BUTTON_NAMES`** (прочитано полностью):
```python
_UI_BUTTON_NAMES = ("wt_icon", "carter", "crypt_open", "crypt_select", "top_accel",
                     "march_accel", "arena_reset", "chest_sender", "chest_type", "chest_collect")
```
Ровно те же 10 имён, что и `TUNE_TARGET_NAMES` (`main.py:130`, другой порядок — порядок роли не
играет, оба используются как множества/по ключу, не по позиции). `set_ui_offset(name, dx, dy)`
(`coord_manager.py:87–90`) **молча игнорирует неизвестное имя** — `if name in self.ui_offsets: ...`,
иначе no-op без исключения и без лога. `ref_a`/`ref_b` НЕ входят в `_UI_BUTTON_NAMES` и НЕ хранятся в
`ui_offsets` — они `storage="absolute"` через `self._point_a`/`self._point_b`, отдельный путь
(`calibrate()`, `coord_manager.py:57–68`).

**🔴 Новая находка Context (не была явно зафиксирована в Design/Adversarial 4.5/A-х):** реестр 4.1
обязан гарантировать **двустороннее** соответствие между `id` записей с `storage="offset"` и именами
`coord_manager._UI_BUTTON_NAMES` — не только «каждый `id` реестра есть в `_UI_BUTTON_NAMES`» (иначе
`set_ui_offset()` тихо не сохранит значение — никакой ошибки пользователю, D-Pad будет выглядеть
рабочим, но правка потеряется при следующем чтении через `get_ui_offset()`, которое вернёт `[0,0]` по
умолчанию), но и обратно — «каждое имя из `_UI_BUTTON_NAMES` есть в реестре» (иначе будет офсет,
недоступный для правки ни из одной точки нового UI, и односторонняя проверка `registry ⊆
_UI_BUTTON_NAMES` этот случай не поймает). Это ровно тот класс бага, которого протокол требует явно
проверять контрпримером (Stage 5). Переносится в Contract Extraction (Стадия 3 этого PLAN) как
отдельный контракт с двусторонней проверкой (механизм — `assert`/тест/import-time validation —
выбирается в Stage 3, не здесь), а не полагаться на «имена и так совпадают, мы их сами писали». Сам
реестр при этом остаётся источником GUI-метаданных цели (`kind`/`storage`/`label_key`/…), а не
подменяет собой `_UI_BUTTON_NAMES` (storage-level whitelist в `coord_manager`) или `ui_offsets`
(фактические значения) — эти два остаются отдельными сущностями, чью дальнейшую судьбу (независимый
whitelist / производный от реестра / дальнейшая централизация) решает Stage 3, не Context.

**Существующий тест, который придётся мигрировать — `test_tune_menu_labels.py`** (прочитан полностью):
тестирует ИМЕННО дропдаун-механизм: `tune_menu_labels()` (нумерованные пункты «N. …», первый пункт —
заголовок «Калибровка»), `tune_chest_group_entry_indices()` (индексы ENTRY ВНУТРИ tkinter-дропдауна
для подсветки темы «сундуки», `main.py:5083–5095`, `menu.entryconfigure(i, foreground=...)` — API,
специфичный для `CTkOptionMenu._dropdown_menu`, не переносится на список виджетов). Design 4.2 упраздняет
`CTkOptionMenu` как точку входа → эти тесты в текущем виде проверяют механизм, которого после PLAN-A не
станет. Регрессия, которую они реально защищают (см. `ANTI-PATTERNS.md` — «Дублирование логики генерации
i18n-labels между init и change_lang()», Сессия #137, коммит с фиксом): **при смене языка выбранная
цель определяется по стабильному `id` записи реестра 4.1; переведённая строка НЕ используется для
определения выбранной цели.** Позиция/индекс строки в списке — только представление в UI (порядок
может меняться, например при добавлении цели), не источник идентичности. `main.py:4425–4435`
(`change_lang()`) уже реализует эквивалент этого принципа для сегодняшнего дропдауна (`self._tune_idx`
— источник истины на момент дропдауна, `_ui_tune_btn_var` только получает новую строку по тому же
индексу) — **PLAN-A обязан перенести этот же инвариант identity-по-`id`, а не identity-по-индексу**, на
новый список-виджет, и написать НОВЫЙ тест на него; старые тесты `test_tune_menu_labels.py`,
специфичные для дропдаун-API, размечаются на замену/удаление в PLAN-A (Contract Extraction), не молча.

- Хангоф #? («клик по лупе — точка не двигается») — `calibration_ui.py` не переписывается в PLAN-A

## Стадия 2 — Code Archaeology

**Прямого аналога — «список записей с разнородными полями (`kind`/`storage`/`theme`), управляющий
генерацией GUI-виджетов» — в клиентском коде (`main.py`, `*.py` в корне) НЕТ.** Проверено: нет циклов
вида `for X in <реестр>: <построить виджет>` ни по `TUNE_TARGET_NAMES`, ни по `_UI_BUTTON_NAMES`, ни по
другому списку — сегодняшние 10 целей тюнинга генерируют не 10 виджетов, а 1 набор виджетов
(`tune_card`, см. Стадию 1) и переключаются по индексу `_tune_idx`; сам список используется только как
источник строк дропдауна и валидности индекса, не как источник построения множества виджетов. Значит
PLAN-A не адаптирует существующий «list → N виджетов» механизм — пишет его с нуля (список → N строк
кликабельного списка вместо одного дропдауна — новый для проекта паттерн отрисовки).

**Ближайшие 3 аналога (не прямые, но по существу вопроса, который решают):**

1. **`TUNE_TARGET_NAMES`/`_UI_BUTTON_NAMES` — плоский кортеж имён, ОДИН источник, много потребителей**
   (`main.py:130`, `coord_manager.py:41`). Это уже применённый в проекте принцип «одна константа модуля,
   не копия литерала» — но БЕЗ метаданных на элемент (только имя, без kind/theme/label_key). PLAN-A
   расширяет этот же принцип до реестра словарей с полями, а не изобретает его заново.

2. **🔴 AP-DUP-HARDCODE (`ANTI-PATTERNS.md:778-797`, Хангоф #100) — прямой негативный прецедент в ЭТОЙ
   ЖЕ подсистеме.** Список целей тюнинга существовал как ДВЕ независимые копии-литерала
   (`_TUNE_INTERNAL` в виджете и `_tko` в `change_lang`); при расширении списка с 4 до 6 пунктов одну
   копию обновили, вторую — забыли → `IndexError` при смене языка на новой цели. Причина по протоколу:
   «один концептуальный список существовал как N независимых копий вместо одного источника правды».
   **Это ровно тот класс бага, который отсутствие единого реестра допускает, а реестр PLAN-A
   структурно исключает** — сильнейший аргумент «почему сейчас», не абстрактный.

3. **`server/chest_catalog.py` + `models.py` (`ChestTypeCatalog`/`ChestLocalization`) — тот же принцип
   на серверном слое, другой домен.** Разрозненные per-chest значения (очки, локализованный текст)
   заменены одной таблицей-реестром с полем-ключом (`canonical_type`) и метаданными на запись
   (`pattern`/`points` либо `language`/`display_text`), с единой точкой импорта
   (`sync_catalog_to_db.py`), а не хардкодом по местам использования. Структурно ближе всего к форме
   реестра PLAN-A (запись = id + разнородные поля), но это БД/сервер, не клиентский in-memory список —
   аналогия только по форме решения, не по механизму (PLAN-A согласно 4.9 non-goals НЕ вводит
   сериализацию реестра, вычисляет его в коде при старте GUI).

**Вывод для Stage 3 (Contract Extraction):** реестр PLAN-A — новая для клиентского кода структура
(список словарей с разнородными полями), не миграция существующего клиентского механизма. Ближайший
довод «за» — не позитивный прецедент успешной унификации в GUI (такого нет), а негативный прецедент
дрейфа при ручном дублировании списка в этой же подсистеме (AP-DUP-HARDCODE). Двусторонняя проверка
`registry ⊆ _UI_BUTTON_NAMES ⊆ registry` (находка Стадии 1) — по той же логике, что вывела правило
AP-DUP-HARDCODE, только применённая на уровне двух РАЗНЫХ структур (реестр PLAN-A и
`coord_manager._UI_BUTTON_NAMES`), а не двух копий одной.
