## Стадия 0 — Scope Decomposition Gate

Спека закрывает ДВА раздела: Раздел 1 (единый реестр 12 целей калибровки, Design 4.1–4.5, 4.8) и
Раздел 2 (зелёная зона на 19 существующих `CTkSlider`, Design 4.7). Проверка по критерию протокола
(«один функционал vs несколько независимых частей»):

- **Разный код.** Раздел 1 трогает только вкладку Калибровки (`main.py:4772–5229`,
  `coord_manager.py`) — один самодостаточный виджет-дерево (`self._cal_frame`). Раздел 2 трогает 19
  слайдеров, физически расположенных на ДРУГИХ вкладках (навигация `main.py:1920–2180`, крипт-слайдеры
  `main.py:2440–2520`, комбо `main.py:3140–3160`, сундуки `main.py:4560–4600`) — вкладки Калибровки не
  касается вообще.
- **Разный механизм.** Раздел 1 — замена структуры данных и точки входа в уже существующий UI
  (список вместо дропдауна, тот же D-Pad/магнифайер). Раздел 2 — НОВЫЙ визуальный примитив, которого в
  проекте нет: цветной сегмент дорожки слайдера через `Canvas`/`Frame`-оверлей с обязательным
  resize-инвариантом (Design 4.7, последний абзац). Ни один enforcement-механизм не общий между
  разделами.
- **Разный риск.** Раздел 2 явно помечен Adversarial Review (файл 36, находка A-2) как требующий
  ОТДЕЛЬНОГО живого resize-теста, не только чтения кода — это самостоятельный источник находок, который
  не должен блокировать более простой и уже до деталей проработанный Раздел 1.

**Решение (Stage 0, в рамках уже одобренных владельцем полномочий на реализационные решения):
разделить на PLAN-A (этот файл, Раздел 1 — единый реестр) и PLAN-B (Раздел 2 — зелёная зона,
отдельный файл позже).** Простая и полнее проработанная часть (Раздел 1) идёт первой согласно
правилу протокола «простая часть реализуется и закрывается первой». PLAN-B не начинается, пока PLAN-A
не пройдёт Final Gate и не будет одобрен владельцем (User Review, Stage 10) — «часть за частью, не
пачкой».

**Ключевой факт для Design 4.2:** `ref_a`/`ref_b` НИКОГДА не были частью `tune_card`/дропдауна — они
редактируются отдельной кнопкой (`_cal_manual_btn` → `run_calibration`), физически выше по вкладке.
10 целей тюнинга УЖЕ используют один общий набор виджетов редактирования (`tune_card`) на все 10 —
меняется только `_tune_idx` и то, что подставляется в `_tune_display_lb`/картинку/оверлей. То есть
«единая панель редактирования» для offset-целей уже реализована сегодня; PLAN-A должен расширить это
общее редактирование, поглотив выбор через СПИСОК вместо `CTkOptionMenu`, и добавить `ref_a`/`ref_b`
как ещё 2 строки списка, ведущие к магнифайеру вместо `tune_card` (Design 4.2 — способ редактирования
зависит от `storage`, не унифицируется).

**Реестр офсетов — `coord_manager.py:41` `_UI_BUTTON_NAMES`** (прочитано полностью):
```python
_UI_BUTTON_NAMES = ("wt_icon", "carter", "crypt_open", "crypt_select", "top_accel",
                     "march_accel", "arena_reset", "chest_sender", "chest_type", "chest_collect")
```
Ровно те же 10 имён, что и `TUNE_TARGET_NAMES` (`main.py:130`, другой порядок — порядок роли не
играет, оба используются как множества/по ключу, не по позиции). `set_ui_offset(name, dx, dy)`
(`coord_manager.py:87–90`) **молча игнорирует неизвестное имя** — `if name in self.ui_offsets: ...`,
иначе no-op без исключения и без лога. `ref_a`/`ref_b` НЕ входят в `_UI_BUTTON_NAMES` и НЕ хранятся в
`ui_offsets` — они `storage="absolute"` через `self._point_a`/`self._point_b`, отдельный путь
(`calibrate()`, `coord_manager.py:57–68`).

**🔴 Новая находка Context (не была явно зафиксирована в Design/Adversarial 4.5/A-х):** реестр 4.1
обязан гарантировать **двустороннее** соответствие между `id` записей с `storage="offset"` и именами
`coord_manager._UI_BUTTON_NAMES` — не только «каждый `id` реестра есть в `_UI_BUTTON_NAMES`» (иначе
`set_ui_offset()` тихо не сохранит значение — никакой ошибки пользователю, D-Pad будет выглядеть
рабочим, но правка потеряется при следующем чтении через `get_ui_offset()`, которое вернёт `[0,0]` по
умолчанию), но и обратно — «каждое имя из `_UI_BUTTON_NAMES` есть в реестре» (иначе будет офсет,
недоступный для правки ни из одной точки нового UI, и односторонняя проверка `registry ⊆
_UI_BUTTON_NAMES` этот случай не поймает). Это ровно тот класс бага, которого протокол требует явно
проверять контрпримером (Stage 5). Переносится в Contract Extraction (Стадия 3 этого PLAN) как
отдельный контракт с двусторонней проверкой (механизм — `assert`/тест/import-time validation —
выбирается в Stage 3, не здесь), а не полагаться на «имена и так совпадают, мы их сами писали». Сам
реестр при этом остаётся источником GUI-метаданных цели (`kind`/`storage`/`label_key`/…), а не
подменяет собой `_UI_BUTTON_NAMES` (storage-level whitelist в `coord_manager`) или `ui_offsets`
(фактические значения) — эти два остаются отдельными сущностями, чью дальнейшую судьбу (независимый
whitelist / производный от реестра / дальнейшая централизация) решает Stage 3, не Context.

**Существующий тест, который придётся мигрировать — `test_tune_menu_labels.py`** (прочитан полностью):
тестирует ИМЕННО дропдаун-механизм: `tune_menu_labels()` (нумерованные пункты «N. …», первый пункт —
заголовок «Калибровка»), `tune_chest_group_entry_indices()` (индексы ENTRY ВНУТРИ tkinter-дропдауна
для подсветки темы «сундуки», `main.py:5083–5095`, `menu.entryconfigure(i, foreground=...)` — API,
специфичный для `CTkOptionMenu._dropdown_menu`, не переносится на список виджетов). Design 4.2 упраздняет
`CTkOptionMenu` как точку входа → эти тесты в текущем виде проверяют механизм, которого после PLAN-A не
станет. Регрессия, которую они реально защищают (см. `ANTI-PATTERNS.md` — «Дублирование логики генерации
i18n-labels между init и change_lang()», Сессия #137, коммит с фиксом): **при смене языка выбранная
цель определяется по стабильному `id` записи реестра 4.1; переведённая строка НЕ используется для
определения выбранной цели.** Позиция/индекс строки в списке — только представление в UI (порядок
может меняться, например при добавлении цели), не источник идентичности. `main.py:4425–4435`
(`change_lang()`) уже реализует эквивалент этого принципа для сегодняшнего дропдауна (`self._tune_idx`
— источник истины на момент дропдауна, `_ui_tune_btn_var` только получает новую строку по тому же
индексу) — **PLAN-A обязан перенести этот же инвариант identity-по-`id`, а не identity-по-индексу**, на
новый список-виджет, и написать НОВЫЙ тест на него; старые тесты `test_tune_menu_labels.py`,
специфичные для дропдаун-API, размечаются на замену/удаление в PLAN-A (Contract Extraction), не молча.

- Хангоф #? («клик по лупе — точка не двигается») — `calibration_ui.py` не переписывается в PLAN-A

## Стадия 2 — Code Archaeology

**Прямого аналога — «список записей с разнородными полями (`kind`/`storage`/`theme`), управляющий
генерацией GUI-виджетов» — в клиентском коде (`main.py`, `*.py` в корне) НЕТ.** Проверено: нет циклов
вида `for X in <реестр>: <построить виджет>` ни по `TUNE_TARGET_NAMES`, ни по `_UI_BUTTON_NAMES`, ни по
другому списку — сегодняшние 10 целей тюнинга генерируют не 10 виджетов, а 1 набор виджетов
(`tune_card`, см. Стадию 1) и переключаются по индексу `_tune_idx`; сам список используется только как
источник строк дропдауна и валидности индекса, не как источник построения множества виджетов. Значит
PLAN-A не адаптирует существующий «list → N виджетов» механизм — пишет его с нуля (список → N строк
кликабельного списка вместо одного дропдауна — новый для проекта паттерн отрисовки).

**Ближайшие 3 аналога (не прямые, но по существу вопроса, который решают):**

1. **`TUNE_TARGET_NAMES`/`_UI_BUTTON_NAMES` — плоский кортеж имён, ОДИН источник, много потребителей**
   (`main.py:130`, `coord_manager.py:41`). Это уже применённый в проекте принцип «одна константа модуля,
   не копия литерала» — но БЕЗ метаданных на элемент (только имя, без kind/theme/label_key). PLAN-A
   расширяет этот же принцип до реестра словарей с полями, а не изобретает его заново.

2. **🔴 AP-DUP-HARDCODE (`ANTI-PATTERNS.md:778-797`, Хангоф #100) — прямой негативный прецедент в ЭТОЙ
   ЖЕ подсистеме.** Список целей тюнинга существовал как ДВЕ независимые копии-литерала
   (`_TUNE_INTERNAL` в виджете и `_tko` в `change_lang`); при расширении списка с 4 до 6 пунктов одну
   копию обновили, вторую — забыли → `IndexError` при смене языка на новой цели. Причина по протоколу:
   «один концептуальный список существовал как N независимых копий вместо одного источника правды».
   **Это ровно тот класс бага, который отсутствие единого реестра допускает, а реестр PLAN-A
   структурно исключает** — сильнейший аргумент «почему сейчас», не абстрактный.

3. **`server/chest_catalog.py` + `models.py` (`ChestTypeCatalog`/`ChestLocalization`) — тот же принцип
   на серверном слое, другой домен.** Разрозненные per-chest значения (очки, локализованный текст)
   заменены одной таблицей-реестром с полем-ключом (`canonical_type`) и метаданными на запись
   (`pattern`/`points` либо `language`/`display_text`), с единой точкой импорта
   (`sync_catalog_to_db.py`), а не хардкодом по местам использования. Структурно ближе всего к форме
   реестра PLAN-A (запись = id + разнородные поля), но это БД/сервер, не клиентский in-memory список —
   аналогия только по форме решения, не по механизму (PLAN-A согласно 4.9 non-goals НЕ вводит
   сериализацию реестра, вычисляет его в коде при старте GUI).

## Стадия 4 — Design

### 4.1 Место реестра в файловой структуре

**Решение: модуль-уровня список в `main.py`, рядом с сегодняшним `TUNE_TARGET_NAMES` (`main.py:130`),
НЕ новый файл.** Обоснование: PC-04 (Стадия 3) подтвердил grep'ом — единственный потребитель реестра
везде, где сегодня используются `TUNE_TARGET_NAMES`/`_TUNE_POINT_TARGETS`/`_CHEST_TUNE_RECTS`, это сам
`main.py`; ни один внешний модуль их не импортирует. Реестр ссылается на объекты из других модулей
(`chest_reader.SENDER_REF_RECT`, `coord_manager.to_screen_dialog` и т. п.) так же, как это уже делают
сегодняшние `_CHEST_TUNE_RECTS`/`_TUNE_POINT_TARGETS` — то есть остаётся GUI-слоем, а не доменной
логикой, которую стоило бы выносить отдельно. Выносить структуру с единственным потребителем в новый
файл добавило бы модуль ради модуля, не устраняя ничего (Design 4.1 оставляет выбор PLAN'у именно
потому, что это деталь реализации, не архитектурное решение).

### 4.2 Виджет списка (реализует C-01, PC-01)

Внутри `_cal_frame` (`CTkScrollableFrame`, уже существует) текущий `tune_card` (контейнер дропдауна +
D-Pad, `main.py:86-93` иерархии Стадии 1) заменяется на:
- `_target_list_frame` (`CTkFrame`) — 12 дочерних `_target_row` (`CTkFrame`), одна на запись реестра, в
  порядке 4.8 спеки (калибровка → Склепы → общие/биржи → Сундуки).
- Каждая `_target_row` — `CTkLabel` со значком типа (канал `kind`, C-03) + `CTkLabel` с переведённой
  подписью (`LANGS[lang][label_key]`, канал `theme` — цвет текста, C-04) + клик-биндинг
  (`.bind("<Button-1>", ...)` на фрейм И на оба дочерних `CTkLabel` — Tkinter не пробрасывает клик с
  дочернего виджета на родителя автоматически, три привязки на одну и ту же функцию `_on_target_row_click(id)`).
- Визуально выбранная строка подсвечивается (граница/фон, тем же `MD3["card"]`/акцентным цветом, что
  уже используется в проекте для активных состояний) — не отдельное требование спеки, минимальная
  реализационная деталь для usability самого списка (без неё непонятно, какая цель сейчас
  редактируется).
- Панель редактирования (D-Pad/статус/картинка) остаётся ПОД списком, на прежнем месте `tune_card`
  внутри `_cal_frame` — переиспользует существующие виджеты (`_tune_display_lb`, `dpad_frame`,
  `_tune_step`, `_tune_reset_btn`, `_tune_img_label`/`_cal_imgs_frame`) без пересоздания, только источник
  данных для них меняется с `_tune_idx` (индекс в кортеже) на выбранный `id` (строка, ключ реестра).

### 4.3 Способ редактирования по `storage`, не по `kind` (реализует Design 4.2, C-01)

**`storage="offset"` (10 целей):** клик по строке → показать существующую панель D-Pad, заполнить
`_tune_display_lb` текущим `get_ui_offset(id)`, показать `_tune_img_label` (картинка через существующий
словарь `key → "tune_*.png"`, `main.py:5041-5045`) либо OCR-оверлей (`_show_chest_rect_overlay`, для
`kind="OCR-область"`) либо крестик (`_show_crosshair_at`, для `kind="точка"`) либо текст «недоступно»
(для `kind="смещение-к-YOLO"`, PC-06).

**`storage="absolute"` (`ref_a`, `ref_b`):** клик по строке → **сразу** вызывает существующую локальную
функцию `_calibrate()` (`main.py:4972-4987`, сегодня — обработчик `_cal_manual_btn.command`), не
`calibration_ui.run_calibration()` напрямую — `_calibrate()` дополнительно сворачивает окно
(`self.iconify()`/`deiconify()` вокруг вызова, `run_calibration` не создаёт свой Toplevel поверх видимого
окна бота), пересчитывает стартовые точки лупы пропорционально реальному разрешению
(`start_a/start_b` от `REF_A`/`REF_B` × `sw/1920, sh/1080`, иначе на 2K/4K лупа стартует далеко от цели)
и вызывает `coord_manager.calibrate(point_a, point_b)` по возврату. Это и есть тот же комбинированный
поток «сначала А, потом Б» за один вызов (`calibration_ui.py:211-249`, проверено: `run_calibration` НЕ
умеет калибровать одну точку отдельно — единый двухшаговый сеанс). Следствие: клик по строке `ref_a`
ИЛИ по строке `ref_b` запускает **один и тот же** сеанс — это не баг, а прямое следствие того, что
сегодняшний механизм и так не разделяет точки; независимого редактирования «только Б» в проекте никогда
не было и PLAN-A это не меняет (4.9 non-goals — способ редактирования absolute не меняется).

**Следствие для C-01:** сегодняшняя отдельная кнопка `_cal_manual_btn` («Калибровать»,
`main.py:83-84` иерархии Стадии 1) — это и есть второй независимый пользовательский вход, который C-01
явно запрещает оставлять рядом с новым списком (иначе строки `ref_a`/`ref_b` в списке и кнопка ниже
делают одно и то же двумя разными путями). **`_cal_manual_btn` как отдельный самостоятельный виджет
удаляется**; вызов её сегодняшнего обработчика `_calibrate()` переносится в обработчик клика по строкам
`ref_a`/`ref_b`. Кнопка «АВТОКАЛИБРОВАТЬ» в это решение не входит — проверено (`grep` по `main.py`):
перевод `cal_auto_btn` существует в словарях `LANGS` всех 19 языков, но **нигде не потребляется** ни
одним виджетом; локальная функция `_auto_calibrate()` (`main.py:4931-4970`, полный рабочий
auto-detect+лупа поток) тоже определена, но нигде не вызывается (`grep` на `_auto_calibrate\b` — только
её собственное определение). Живой кнопки «АВТОКАЛИБРОВАТЬ» в сегодняшнем GUI нет — мёртвый код с обеих

### 4.4 Состояние выбора (реализует PC-03)

Один атрибут `self._cal_selected_id: str | None` — заменяет `self._tune_idx: int`. `None` — ничего не
выбрано (начальное состояние при открытии вкладки, до первого клика по строке — эквивалент сегодняшнего
`_tune_idx == -1`, экран показывает только список, без открытой панели редактирования снизу). Клик по
строке → `self._cal_selected_id = <id из реестра>` → диспетчеризация по 4.3. `change_lang()`
(`main.py:4425-4435`) переписывается на поиск текущей записи реестра по `self._cal_selected_id` (не по
пересчитанному индексу) и обновление только текста подписи выбранной и всех остальных строк — сама
идентичность выбора не пересчитывается заново из индекса (PC-03).

### 4.5 Failure modes

- **Реестр — статические данные кода, не пользовательский ввод.** Отсутствие обязательного поля
  (`ref_rect` для OCR-области, `base_pos_fn` для точки/offset) — программная ошибка, ловится тестом
  PC-01 на этапе разработки/CI, не требует runtime-валидации/try-except в GUI (проект не вводит защиту
  от сценариев, которые не могут произойти после того, как тест зафиксировал структуру данных).
- **Клик по строке во время уже открытого магнифайера (`run_calibration`)** — `run_calibration`
  модальный по построению (блокирует до `point_b`/отмены, `calibration_ui.py:234-248`), повторный клик
  по строке списка физически невозможен, пока магнифайер держит фокус — новых состояний гонки не
  возникает (Tk single-threaded event loop, тот же режим, что и сегодня у `_cal_manual_btn`).
- **Смена языка при `self._cal_selected_id is None`** — обновляются только подписи строк списка, панель
  редактирования снизу не показывается (как и сегодня при `_tune_idx == -1`) — не новое поведение,
  явное следствие 4.4.

## Стадия 5 — Adversarial Review

**Найдена и сразу исправлена неточность собственного Stage 4** (не откладывая до отдельного раунда):
4.3 сначала утверждал прямой вызов `calibration_ui.run_calibration(parent=self)` из обработчика строки
— проверка кода (`main.py:4972-5003`) показала, что сегодняшняя кнопка вызывает не `run_calibration`
напрямую, а локальную `_calibrate()` (сворачивает окно, пересчитывает стартовые точки лупы под реальное
разрешение, вызывает `coord_manager.calibrate()` по возврату) — 4.3 исправлен на вызов `_calibrate()`.

1. **Быстрый повторный клик по одной и той же offset-строке.** Tk — однопоточный event loop, каждый
   обработчик клика выполняется до конца, прежде чем следующее событие начнёт обрабатываться; повторный
   клик просто переустанавливает `self._cal_selected_id` в то же значение — идемпотентно, гонки нет.

2. **Клик по `ref_a`/`ref_b` во время уже открытого магнифайера той же/другой строки.** `_calibrate()`
   вызывает `self.iconify()` перед стартом (`main.py:4974`) — главное окно физически скрыто с экрана на
   всё время сеанса, кликнуть по строке списка (она в свёрнутом окне) невозможно. Повторного входа не
   существует не потому, что где-то стоит проверка, а потому, что виджет недоступен для клика — тот же
   режим защиты, что и у сегодняшней `_cal_manual_btn` (PLAN-A не меняет и не ослабляет его).

3. **Клик по offset-строке во время открытого магнифайера.** Тот же аргумент — окно свёрнуто целиком,
   весь список недоступен, не только строки absolute.

4. **`_emergency_stop` (ESC, `main.py:3710-3739`) во время выбранной цели/открытого магнифайера.**
   Прочитан целиком (`main.py:3710-3739` и далее) — не трогает `_tune_idx`/`self._cal_selected_id` и
   ничего из состояния вкладки Калибровки вообще, только останавливает engine'ы охоты (Биржа/Склепы). ESC
   во время калибровки не взаимодействует с этим решением — не новый риск, не существующий.

5. **Смена профиля (`_load_profile`, `main.py:4918-4929`) при выбранной offset-цели с несохранённым
   D-Pad-вводом.** `coord_manager.load(path)` заменяет `ui_offsets` целиком из файла профиля — любая
   правка через D-Pad для текущей цели, сделанная против СТАРОГО профиля и не сохранённая явной кнопкой
   «Сохранить», будет молча перезаписана новым профилем. **Это не новый риск от PLAN-A** — идентичное
   поведение существует в сегодняшнем коде один в один (тот же `_load_profile`, не изменяется PLAN-A);
   выбор цели по `id` вместо индекса ничего здесь не меняет. Зафиксировано как унаследованное поведение,
   не регрессия — исправление (если владелец сочтёт нужным) вне scope этого PLAN.

6. **`label_key` отсутствует в `LANGS` для одного из 19 языков.** Реальный, но НЕ новый риск: все
   `label_key` реестра — те же строки (`cal_tune_wt_icon` и т. п.), что уже используются сегодняшним
   дропдауном (`main.py:4427`, `tune_menu_labels(val, TUNE_TARGET_NAMES)`) — если бы ключ отсутствовал
   хоть в одном из 19 языков, это уже падало бы в проде сегодня, до PLAN-A. Не вводит новый риск, но раз
   тест PC-01 всё равно проходит по всем 12 записям реестра — дёшево расширить его же (не новый
   контракт) проверкой, что `label_key` каждой записи присутствует во всех 19 блоков `LANGS`, а не только
   структурно валиден. Добавлено в PC-01 (Стадия 3) как уточнение теста, не новый пункт.

7. **Граница списка (первая/последняя из 12 строк, поведение скролла).** `_target_list_frame` —
   стандартный `pack()` внутри уже существующего `CTkScrollableFrame` (`_cal_frame`) — скролл-механика не
   пишется заново, наследуется от уже работающего виджета. Контрпримера, специфичного для PLAN-A, не
   найдено.

**Итог:** один реальный найденный дефект (п.1 — неточность в 4.3, тут же исправлен). Остальные 6
адверсариальных вопросов — либо структурно невозможны (Tk single-thread + iconify), либо унаследованы
без изменений от сегодняшнего кода (не регрессия PLAN-A), либо дают дешёвое уточнение уже существующего
контракта, а не новый.
