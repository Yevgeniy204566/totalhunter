## Стадия 0 — Scope Decomposition Gate

Спека закрывает ДВА раздела: Раздел 1 (единый реестр 12 целей калибровки, Design 4.1–4.5, 4.8) и
Раздел 2 (зелёная зона на 19 существующих `CTkSlider`, Design 4.7). Проверка по критерию протокола
(«один функционал vs несколько независимых частей»):

- **Разный код.** Раздел 1 трогает только вкладку Калибровки (`main.py:4772–5229`,
  `coord_manager.py`) — один самодостаточный виджет-дерево (`self._cal_frame`). Раздел 2 трогает 19
  слайдеров, физически расположенных на ДРУГИХ вкладках (навигация `main.py:1920–2180`, крипт-слайдеры
  `main.py:2440–2520`, комбо `main.py:3140–3160`, сундуки `main.py:4560–4600`) — вкладки Калибровки не
  касается вообще.
- **Разный механизм.** Раздел 1 — замена структуры данных и точки входа в уже существующий UI
  (список вместо дропдауна, тот же D-Pad/магнифайер). Раздел 2 — НОВЫЙ визуальный примитив, которого в
  проекте нет: цветной сегмент дорожки слайдера через `Canvas`/`Frame`-оверлей с обязательным
  resize-инвариантом (Design 4.7, последний абзац). Ни один enforcement-механизм не общий между
  разделами.
- **Разный риск.** Раздел 2 явно помечен Adversarial Review (файл 36, находка A-2) как требующий
  ОТДЕЛЬНОГО живого resize-теста, не только чтения кода — это самостоятельный источник находок, который
  не должен блокировать более простой и уже до деталей проработанный Раздел 1.

**Решение (Stage 0, в рамках уже одобренных владельцем полномочий на реализационные решения):
разделить на PLAN-A (этот файл, Раздел 1 — единый реестр) и PLAN-B (Раздел 2 — зелёная зона,
отдельный файл позже).** Простая и полнее проработанная часть (Раздел 1) идёт первой согласно
правилу протокола «простая часть реализуется и закрывается первой». PLAN-B не начинается, пока PLAN-A
не пройдёт Final Gate и не будет одобрен владельцем (User Review, Stage 10) — «часть за частью, не
пачкой».

## Стадия 1 — Context

### 1.1 Что должно стать истинным (из Design/Contracts спеки)

- C-01/4.2: единственная точка входа для выбора цели калибровки/тюнинга — список из 12 строк внутри
  уже существующего `self._cal_frame` (`CTkScrollableFrame`), вместо сегодняшних ДВУХ независимых
  входов (кнопка «Калибровать» → магнифайер для `ref_a`/`ref_b`; `CTkOptionMenu` → D-Pad для 10 целей
  тюнинга).
- C-02/4.1: единый реестр данных (12 записей, поля `id`/`kind`/`storage`/`theme`/`label_key`/
  `ref_rect`/`base_pos_fn`), заменяющий `TUNE_TARGET_NAMES`, `_TUNE_POINT_TARGETS`, `_CHEST_TUNE_RECTS`.
- C-03/4.3: единая отрисовка маркера по `kind` (`_show_crosshair_at` для точек, включая `ref_a`/`ref_b`;
  `_show_chest_rect_overlay` для OCR-областей, параметризованный произвольным `ref_rect`; текстовая
  подпись вместо маркера для `crypt_select`).
- C-04/4.4: независимые визуальные каналы `kind` (значок) и `theme` (цвет подписи).
- C-05/4.5: координатная модель не меняется — запись по-прежнему идёт через `coord_manager.calibrate()`
  (`storage="absolute"`) или `coord_manager.set_ui_offset()` (`storage="offset"`).
- C-06/4.6: кликабельная видео-ссылка (заглушка URL, неактивна до реального адреса).
- 4.8: порядок 12 строк — калибровка → Склепы (`crypt_select`, `crypt_open`, `carter`) → общие/биржи
  (`wt_icon`, `top_accel`, `march_accel`, `arena_reset`) → Сундуки (`chest_sender`, `chest_type`,
  `chest_collect`).
- 4.9 non-goals: способ редактирования (D-Pad/магнифайер) не меняется; новый формат профиля/
  `gui_config.json` не вводится — реестр вычисляется в коде при старте GUI, не сериализуется отдельно.

### 1.2 Существующий код — проверено лично в этой сессии (не по памяти)

**Реальная контейнерная иерархия `_cal_frame`** (не была проверена на стадии Design/Adversarial —
закрывает находку A-4, файл 36; прочитано `main.py:4772–5229` целиком в этой сессии):

```
self._cal_frame (CTkScrollableFrame, main.py:1845; ребёнок self._content_frame)
├── _cal_title_lb, _cal_desc_lb — CTkLabel, packed напрямую в _cal_frame
├── _img_area (CTkFrame, transparent) — общая область изображений калибровки/тюнинга
│   ├── _cal_imgs_frame (CTkFrame) — 2 карточки (grid col=0/1): фото + подпись + описание
│   │     для ref_a/ref_b (магнифайер запускается кнопкой _cal_manual_btn НИЖЕ, не отсюда)
│   └── _tune_img_label (CTkLabel) — картинка текущей цели тюнинга;
│         _cal_imgs_frame и _tune_img_label взаимоисключающе pack/pack_forget через
│         _show_cal_images()/_show_tune_image(key)
├── profile_frame (CTkFrame) — CTkOptionMenu выбора профиля
├── self._cal_status_label (CTkLabel) — packed напрямую в _cal_frame
├── self._cal_manual_btn (CTkButton «Калибровать») — packed напрямую, запускает
│     calibration_ui.run_calibration() → магнифайер для ref_a/ref_b (ЕДИНСТВЕННЫЙ путь их правки)
├── save_load_row (CTkFrame) — _cal_save_btn / _cal_load_btn
├── tune_card (CTkFrame, fg_color=MD3["card"], border) — packed напрямую в _cal_frame;
│     ЭТО контейнер всех 10 целей тюнинга (единый на все 10, не по одному на цель):
│   ├── _tune_title_lb (CTkLabel)
│   ├── self._tune_option_menu (CTkOptionMenu — дропдаун: idx=-1 «Калибровка» + 10 целей)
│   ├── self._tune_display_lb (CTkLabel — текст "X: ±Npx  Y: ±Npx")
│   ├── _tune_step (CTkSegmentedButton "1px"/"5px")
│   ├── dpad_frame (CTkFrame) — 4 CTkButton (▲◄►▼), grid
│   └── _tune_reset_btn (CTkButton)

```

**Ключевой факт для Design 4.2:** `ref_a`/`ref_b` НИКОГДА не были частью `tune_card`/дропдауна — они
редактируются отдельной кнопкой (`_cal_manual_btn` → `run_calibration`), физически выше по вкладке.
10 целей тюнинга УЖЕ используют один общий набор виджетов редактирования (`tune_card`) на все 10 —
меняется только `_tune_idx` и то, что подставляется в `_tune_display_lb`/картинку/оверлей. То есть
«единая панель редактирования» для offset-целей уже реализована сегодня; PLAN-A должен расширить это
общее редактирование, поглотив выбор через СПИСОК вместо `CTkOptionMenu`, и добавить `ref_a`/`ref_b`
как ещё 2 строки списка, ведущие к магнифайеру вместо `tune_card` (Design 4.2 — способ редактирования
зависит от `storage`, не унифицируется).

**Реестр офсетов — `coord_manager.py:41` `_UI_BUTTON_NAMES`** (прочитано полностью):
```python
_UI_BUTTON_NAMES = ("wt_icon", "carter", "crypt_open", "crypt_select", "top_accel",
                     "march_accel", "arena_reset", "chest_sender", "chest_type", "chest_collect")
```
Ровно те же 10 имён, что и `TUNE_TARGET_NAMES` (`main.py:130`, другой порядок — порядок роли не
играет, оба используются как множества/по ключу, не по позиции). `set_ui_offset(name, dx, dy)`
(`coord_manager.py:87–90`) **молча игнорирует неизвестное имя** — `if name in self.ui_offsets: ...`,
иначе no-op без исключения и без лога. `ref_a`/`ref_b` НЕ входят в `_UI_BUTTON_NAMES` и НЕ хранятся в
`ui_offsets` — они `storage="absolute"` через `self._point_a`/`self._point_b`, отдельный путь
(`calibrate()`, `coord_manager.py:57–68`).

**🔴 Новая находка Context (не была явно зафиксирована в Design/Adversarial 4.5/A-х):** реестр 4.1
обязан гарантировать, что каждая запись с `storage="offset"` использует `id`, совпадающий БУКВАЛЬНО
с одним из 10 имён в `coord_manager._UI_BUTTON_NAMES` — иначе `set_ui_offset()` тихо не сохранит
значение (никакой ошибки пользователю, D-Pad будет выглядеть рабочим, но правка потеряется при
следующем чтении через `get_ui_offset()`, которое просто вернёт `[0,0]` по умолчанию). Это ровно тот
класс бага, которого протокол требует явно проверять контрпримером (Stage 5). Переносится в
Contract Extraction (Стадия 3 этого PLAN) как отдельный контракт с проверкой на старте (assert/тест),
а не полагаться на «имена и так совпадают, мы их сами писали».

**Существующий тест, который придётся мигрировать — `test_tune_menu_labels.py`** (прочитан полностью):
тестирует ИМЕННО дропдаун-механизм: `tune_menu_labels()` (нумерованные пункты «N. …», первый пункт —
заголовок «Калибровка»), `tune_chest_group_entry_indices()` (индексы ENTRY ВНУТРИ tkinter-дропдауна
для подсветки темы «сундуки», `main.py:5083–5095`, `menu.entryconfigure(i, foreground=...)` — API,
специфичный для `CTkOptionMenu._dropdown_menu`, не переносится на список виджетов). Design 4.2 упраздняет
`CTkOptionMenu` как точку входа → эти тесты в текущем виде проверяют механизм, которого после PLAN-A не
станет. Регрессия, которую они реально защищают (см. `ANTI-PATTERNS.md` — «Дублирование логики генерации
i18n-labels между init и change_lang()», Сессия #137, коммит с фиксом): **при смене языка индекс выбранной
цели не должен определяться повторным сравнением переведённой строки** — должен сохраняться как
стабильный `id`/индекс, а строка только перерисовывается. `main.py:4425–4435` (`change_lang()`) уже
делает это правильно для дропдауна (`self._tune_idx` — источник истины, `_ui_tune_btn_var` только
получает новую строку по тому же индексу). **PLAN-A обязан перенести этот же инвариант на новый
список-виджет** и написать НОВЫЙ тест на него; старые тесты `test_tune_menu_labels.py`, специфичные для
дропдаун-API, размечаются на замену/удаление в PLAN-A (Contract Extraction), не молча.

**Анти-паттерны, релевантные PLAN-A** (`ANTI-PATTERNS.md`, грепнуто и прочитано):
- Сессия #137 (i18n-labels init/change_lang дублирование) — см. выше, прямое применение.
- Хангоф #? («клик по лупе — точка не двигается») — `calibration_ui.py` не переписывается в PLAN-A
  (Design 4.9: способ редактирования absolute не меняется), но `_show_crosshair_at`/`_show_red_dot`
  замена (Design 4.3) трогает модуль `calibration_ui.py` → при реализации перечитать этот анти-паттерн
  повторно перед правкой файла, не полагаться на то, что PLAN-A его не касается вообще.
- «D-Pad список целей хранился в двух местах до централизации» (Сессия ~туда же, `main.py:735–744`) —
  подтверждает, что направление централизации (реестр вместо разрозненных структур) уже один раз
  устраняло реальный баг в этом же коде; регресса в обратную сторону быть не должно.
- «Тюнинг=0 не сохраняется, откатывается на старое значение» — если PLAN-A вводит промежуточный слой
  чтения/записи через реестр поверх `get_ui_offset`/`set_ui_offset`, явный `0` обязан доходить до
  `coord_manager` как есть, без «0 — то же что не задано».
- «Запись профиля на диск при каждом нажатии стрелки» — текущий D-Pad (`main.py:5156–5162`, `_tune_apply`)
  НЕ пишет файл на каждый клик (только меняет `coord_manager.ui_offsets` в памяти, запись на диск — по
  кнопке «Сохранить», `_save_profile`). PLAN-A обязан сохранить это поведение при рефакторинге —
  не вводить autosave на каждый D-Pad клик как побочный эффект унификации.

### 1.3 Что НЕ решено в Design и передано в PLAN (прямая цитата 4.7, п. «геометрия», и 4.1)

- Конкретное место размещения реестра в файловой структуре (новый файл `calibration_registry.py` vs
  модуль-уровень список в `main.py`) — Design явно оставил это PLAN.
- Конкретный виджет списка из 12 строк (какой контейнер, scroll-поведение внутри уже скроллируемого
  `_cal_frame`, высота строки) — не выбран Design, только «список, где строка кликабельна».
- План миграции/устаревания `TUNE_TARGET_NAMES`/`_TUNE_POINT_TARGETS`/`_CHEST_TUNE_RECTS` — Design 4.1
  говорит «выводятся из употребления, не удаляются резко», но не называет порядок/критерий полной
  миграции — вопрос для Contract Extraction этого PLAN.

### 1.4 Не переспрашивать (уже решено выше по цепочке спека→PLAN)

Зелёная зона (Раздел 2), видео-URL, точный текст подписи `crypt_select`, порядок 12 строк, разделение
`kind`/`theme`/`storage` — все закрыты Final Gate спеки (файл 37) и Design (файл 35). PLAN-A их не
пересматривает, только реализует.
