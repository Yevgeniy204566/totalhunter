## 🔴 «СЕРВЕР НЕДОСТУПЕН» — ОДНА ФРАЗА, УЖЕ 4 РАЗНЫХ ПЕРВОПРИЧИНЫ ПОДРЯД

**Что было:** За две недели (24.06 → 09.07) один и тот же пользовательский текст «Сервер недоступен. Данные сохранены локально.» появлялся 4 раза, и каждый раз причина была РАЗНАЯ: двойной клик/необработанный `IntegrityError` (24.06), TZ-баг сравнения datetime как строк в дедупликации (07.07), nginx `client_max_body_size` 1 МБ по умолчанию (08.07), клиентский `requests.post(timeout=10)` короче реального времени обработки на слабом сервере (09.07, v1.8.12). Причина №4: nginx access.log показал `499` (клиент сам оборвал соединение) и `200 OK` от uvicorn на том же запросе секундой позже — сервер не падал, просто отвечал иногда дольше 10 сек.

**Правило:** Эта фраза — симптом обработки ошибок в `main.py`/`chest_reader.py` (любой не-2xx/исключение схлопывается в один и тот же текст), не диагноз. **Никогда не считать автоматически, что это уже известный баг** — каждый раз диагностировать заново с нуля (логи GCP, nginx access/error.log, реальные таймстампы). С v1.8.12 клиент логирует настоящую причину (тип исключения/HTTP-код) через `log_error_to_server()` — при следующем повторе сначала смотреть этот канал в админке «Логи», это должно исключить необходимость поднимать 2 параллельных агента заново.

## 🔴 NGINX `proxy_pass http://localhost:PORT` — РЕЗОЛВИТСЯ И В IPv4 И В IPv6

**Что было:** `/etc/nginx/sites-enabled/totalhunter_api` использовал `proxy_pass http://localhost:8000`. `localhost` резолвится nginx'ом в оба адреса (`127.0.0.1` и `::1`), а uvicorn (`--host 0.0.0.0`) слушает только IPv4. Каждый раз, когда nginx выбирал `::1`, получал `Connection refused` мгновенно — 305 таких ошибок за сутки в `/var/log/nginx/error.log`, в основном на частых эндпоинтах (`/vault/sync`, `/roy/pool`), добавляя случайные задержки/сбои на ровном месте.

**Правило:** Всегда указывать `proxy_pass http://127.0.0.1:PORT` явно (не `localhost`) для upstream, который слушает только IPv4 — устраняет 50% случайных промахов резолвинга без побочных эффектов. Проверка после фикса: `sudo grep "::1" /var/log/nginx/error.log` — новых записей после `nginx -t && systemctl reload nginx` быть не должно.

## 🔴 «СЕРВЕР НЕДОСТУПЕН» С ПУСТЫМ JOURNALCTL — ПРОВЕРЯТЬ NGINX ERROR.LOG ОТДЕЛЬНО

**Что было:** Владелец получал «Сервер недоступен. Данные сохранены локально.» при выгрузке крупного батча сундуков (~1.09 МБ, кириллические имена). `journalctl -u totalhunter` (лог uvicorn/приложения) показывал **ноль** реальных запросов на `/api/v1/chests/import`, хотя владелец кликал «Отправить» многократно — что выглядело как баг в клиенте/сборке (это была свежесобранная v1.8.11). Потратили время на диагностику сборки (Nuitka/PyInstaller/certifi/firewall/антивирус — всё оказалось чистым, два независимых агента подтвердили) прежде чем догадались проверить `/var/log/nginx/error.log` отдельно.

**Реальная причина:** `/etc/nginx/sites-enabled/totalhunter_api` — реверс-прокси перед uvicorn — не имел директивы `client_max_body_size`, действовал дефолт nginx **1 МБ**. nginx резал запрос `413` **до** проксирования на `localhost:8000` — uvicorn физически не видел эти запросы, поэтому `journalctl -u totalhunter` был пуст. Прямое доказательство было в `/var/log/nginx/error.log`: `client intended to send too large body: 1141433 bytes`, с точным совпадением таймстампов.

**Правило:** Если `journalctl -u <service>` показывает НОЛЬ запросов там, где клиент точно их отправлял (не таймаут на уровне приложения, а полное отсутствие) — это сигнал, что запрос не дошёл до приложения вообще. Первым делом проверять слой ПЕРЕД приложением: `/var/log/nginx/{access,error}.log` (или аналог reverse-proxy), а не тратить время на аудит клиентского кода/сборки. Типичные nginx-причины: `client_max_body_size` (413), таймауты прокси, `connect() failed` к upstream (сервис не поднят). См. [[project_chest_nginx_body_size_limit]] в памяти Claude.

## 🔴 СРАВНЕНИЕ DATETIME КАК СТРОК — TZ-AWARE POSTGRES ПРОТИВ NAIVE КЛИЕНТА

**Что было:** `_dedupe`/`_load_existing_keys` в `server/chests.py` сравнивали `collected_at` через `.isoformat()` — сырые строки. `Chest.collected_at` — `TIMESTAMP WITH TIME ZONE`, `asyncpg` всегда возвращает такие значения как tz-aware UTC (`"...+00:00"`), а клиент (`chest_reader.py`) шлёт naive-строку без смещения. Строки никогда не совпадали → защита от повторной отправки уже сохранённого батча не работала на проде НИКОГДА, хотя задумывалась и была явно закомментирована как рабочая. Любой ретрай (сетевой таймаут, двойной клик) доходил до реального unique constraint в БД → `IntegrityError` → необработанный `500` → бот показывал «Сервер недоступен», хотя данные уже были сохранены.

**Ловушка с тестами:** 4 теста на этот сценарий были **зелёными** — тестовая БД (`sqlite+aiosqlite:///:memory:`, `conftest.py`) не воспроизводит tz round-trip Postgres (`DateTime(timezone=True)` в SQLite тихо остаётся naive). Ложная уверенность держалась с момента первой реализации идемпотентности до 2026-07-07, пока не проявилась на реальных данных владельца (851 запись застряла в локальной очереди бота).

**Правило:** Для любого сравнения ключей с datetime-полем `TIMESTAMP WITH TIME ZONE` — сравнивать как объекты `datetime`, нормализованные к одному представлению (naive UTC-эквивалент), не как сырые `.isoformat()` строки. Если тестовая БД — SQLite, а прод — Postgres, и логика завязана на datetime/timezone — писать юнит-тест, который явно подсовывает tz-aware значение (имитируя реальный Postgres), а не полагаться на round-trip через ORM/тестовую БД: SQLite может тихо прятать баг. См. [[project_chest_import_tz_dedup_fix]] в памяти Claude.

## 🔴 АБСОЛЮТНЫЕ ПОРОГИ ОЧКОВ (50К/500К) БЕЗ ПРИВЯЗКИ К КВОТЕ КЛАНА

**Что было:** Красивый шрифт «победителя» на паблик-таблице Сундуков (`ChestSummaryTable.jsx`) включался по 6 фиксированным абсолютным порогам очков (50к…500к). Для кланов с маленькой квотой (пример владельца: 14к) это никогда бы не сработало — реальный перебор над квотой обычно исчисляется тысячами, а не сотнями тысяч.

**Правило:** Любая градация/тир для показателя, который сравнивается с квотой конкретного коллектора (очки, сундуки) — считать относительно квоты этого коллектора (`points - targets.points`), а не абсолютными константами. Абсолютные пороги подходят только для величин, не завязанных на индивидуальную квоту.

## 🔴 `max()` НА BOOLEAN-КОЛОНКЕ — РАБОТАЕТ В SQLITE (ТЕСТЫ), ПАДАЕТ В POSTGRES (ПРОД)

**Что было:** `chest_summary.py` считал `func.max(ChestConfiguration.counts_toward_quota)` и `func.max(ChestConfiguration.is_in_pattern)` (обе — `Boolean`-колонки) в GROUP BY запросе. Все тесты (SQLite) зелёные, но публичная страница Сундуков (`GET /api/v1/chests/by/{kingdom}/{slug}`) отдавала 500 на реальном сервере.

**Причина:** SQLite хранит булевы как 0/1 и терпит `max()` на них. PostgreSQL — нет: `function max(boolean) does not exist`. Это регрессия из **предыдущего** фикса того же файла: `bool_or()` (Postgres-only, отсутствует в SQLite) заменили на `max()`, чтобы почистить тесты — но `max(boolean)` не существует и в Postgres тоже. Обе функции диалект-специфичны в противоположные стороны — искать замену, а не менять шило на мыло.

**Правило:** Для агрегации boolean-колонки, которая должна работать и в проде (Postgres), и в тестах (SQLite) — оборачивать колонку в `cast(col, Integer)` ДО `func.max()`. Работает в обоих диалектах. Проверять на реальной БД через `psql` перед деплоем, если меняется что-то в этой зоне (`SELECT max(CAST(col AS INTEGER)) FROM ...`) — тесты на SQLite это не поймают.

## 🔴 IIFE В JSX-ФРАГМЕНТЕ — ОШИБКА ВНУТРИ УБИВАЕТ КНОПКИ СНАРУЖИ

**Что было:** В `AncientsPage.jsx` внутри `{c.roster.length === 0 ? ... : (<>...</>)}` использовался паттерн `{(() => { const sort = ...; return <table>...</table> })()}` (IIFE). В том же фрагменте снаружи IIFE стояла кнопка «Сохранить маппинги». Если IIFE бросал исключение — весь `<>...</>` не рендерился, включая кнопку вне IIFE.

**Симптом:** Нет кнопки «Сохранить», нет таблицы, ползунок не работает, список пуст — несмотря на то что код кнопки находился ПОСЛЕ закрытия IIFE.

**Причина:** React вычисляет весь JSX-фрагмент перед рендером; исключение в любом подвыражении прерывает рендер всего выражения.

**Правило:** Никогда не использовать IIFE внутри JSX для вычисления переменных. Все `const sort = ...`, `const sortedRoster = ...`, `const srcSlug = ...` — вычислять ДО `return (...)` в теле функции-коллбэка `array.map(item => { const x = ...; return <div>...</div> })`. Кнопки и другие элементы НИКОГДА не ставить в тот же фрагмент с IIFE — они могут не отрендериться если IIFE упадёт.

## 🔴 PYAUTOGUI.SCROLL БЕЗ ФОКУСА ИГРЫ — ALWAYS-ON-TOP БОТ ПЕРЕХВАТЫВАЕТ СОБЫТИЯ

**Что было:** `pyautogui.scroll(-2)` после `moveTo(cx, cy)` над диалогом игры не скроллил диалог. Бот читал первый экран (~4 строки) и завершал работу через 5 секунд.

**Причина:** GUI-окно бота (CustomTkinter, always-on-top) удерживает фокус после клика «Старт». `scroll(-2)` уходит в бот-окно, а не в игру — даже когда курсор физически над игровым диалогом. Диалог не сдвигается → `zero_shift_streak=2` → ранний выход из цикла.

**Правило:** Перед первым `scroll(-2)` в потоке с GUI — явный `click` в безопасную зону игрового диалога (`ANTI_AFK_HEADER_Y_FRAC = 0.03` = верхние 3%, title bar). `moveTo` недостаточно — нужен именно клик для передачи фокуса. Один клик при старте, дальше `anti_afk_click` раз в 3 минуты.

**🔴 УТОЧНЕНИЕ (Сессия #112, 2026-06-30): `pyautogui.click(x, y)` НЕ ЭКВИВАЛЕНТНО `moveTo(x, y, duration=0.3)` + `click()`**

`click(x, y)` телепортирует курсор мгновенно (duration=0). Игровое окно может не успеть зарегистрировать hover-событие и не принять последующий click как смену фокуса — `scroll(-2)` продолжает уходить в бот-окно. Протестировано на clan_chat_reader.py — три итерации с `click(x,y)` не дали скролла, переход на `moveTo(x,y, duration=0.3)` + `pyautogui.click()` (без аргументов) дал скролл. **Всегда использовать именно этот двухшаговый паттерн, не однострочный `click(x,y)`.**

## 🔴 JSX СТРУКТУРНЫЕ ОБЁРТКИ (div/table) — ТОЛЬКО В ОДНОМ Edit-ВЫЗОВЕ

**Что было:** При добавлении `<div style={{overflowX:'auto'}}>` вокруг `<table>` два вызова
Edit: первый добавил открывающий тег `<div>` перед `<table>`, второй — `</table></div>` после
закрывающего `</table>`. В итоге в файле оказалось `</table></table></div>` — дублирующий
закрывающий тег. Vercel построил билд с синтаксической ошибкой JSX, два деплоя упали в
`ERROR` state.

**Правило:** Любую пару открывающий/закрывающий тег обёртки вокруг уже существующего блока
вносить в ОДНОМ вызове Edit — вырезать весь обёртываемый блок и вставить его с новыми тегами
сразу. Нельзя открывающий тег в одном вызове, закрывающий — в другом.

## 🔴 TESSERACT CONFIDENCE НЕ ЗНАЧИТ «ПРАВИЛЬНО» — НЕ ВЫБИРАТЬ OCR-КАНДИДАТА ПО CONFIDENCE БЕЗ ДОПОЛНИТЕЛЬНОГО ФИЛЬТРА (tournament_reader.py)

**Что было:** По рекомендации внешнего ревью (Gemini) переписали выбор лучшего OCR-варианта
имени с «самая длинная строка» на «строка с наибольшей средней confidence по словам»
(`image_to_data`), плюс эскалация на тяжёлый adaptive-threshold+FULL-lang проход при низкой
confidence. Звучало строго правильнее в теории.

**Что случилось на практике:** Tesseract выдаёт ВЫСОКУЮ confidence на уверенно прочитанный
мусор («ровные» чёрные пятна после adaptive threshold читаются как буквы с уверенностью под
99%) не реже, чем на настоящий текст. Эскалационный проход регулярно перебивал корректно
прочитанное первым проходом имя («VikTor Я») мусором с более высокой confidence
(«VikTor Я — р. » a m >= Aun ea Hoa»). Откачено целиком в той же сессии.

**Правило:** Confidence от Tesseract — это уверенность движка в СВОЁМ прочтении, не сигнал
правильности результата относительно реальности. Не использовать как единственный критерий
выбора между OCR-кандидатами без дополнительной проверки (длина в разумных пределах, словарь
допустимых символов, что угодно ВНЕШНЕЕ по отношению к самому Tesseract). Простое
`max(candidates, key=len)` после прогона 4 фиксированных вариантов (psm×invert) на практике
оказалось надёжнее.

## 🔴 ПОЛНЫЙ НАБОР ЯЗЫКОВ OCR ОДНОВРЕМЕННО = БОЛЬШЕ ОШИБОК НА ПРОСТЫХ ИМЕНАХ, НЕ ТОЛЬКО МЕДЛЕННЕЕ (tournament_reader.py, chest_reader.py)

**Что было:** Предположение «раз FULL-набор (8 скриптов: rus/eng/Latin/Cyrillic/ara/jpn/
chi_sim/chi_tra/kor) надёжнее, просто на ~2.5x медленнее» — оказалось неверным.
Живой тест: тег `[K229] Scaramouche` с FULL-набором прочитался как `1229] Scaramouche`
(потерял `[`/`K`), а с LIGHT-набором (`rus+eng+script/Latin`) — корректно. Чем больше
алфавитов одновременно разрешено классификатору, тем выше шанс спутать похожие глифы
разных скриптов даже на однозначно-латинском/кириллическом тексте.

**Правило:** LIGHT-набор — дефолт всегда. FULL — только явный opt-in (тумблер в GUI/API
параметр), и только когда в нике реально есть экзотический скрипт (арабский/японский/
китайский/корейский). Не включать FULL «на всякий случай» или «для надёжности».

## 🔴 `cv2.matchTemplate` НА ДВУХ ПОСЛЕДОВАТЕЛЬНЫХ КАДРАХ — КРОПЫ ВСЕГДА ИЗ СВОИХ РАЗМЕРОВ, НЕ ИЗ РАЗМЕРОВ СОСЕДНЕГО КАДРА (tournament_reader.py::measure_scroll_shift)

**предыдущего** кадра (`prev_dialog.shape`). При любом 1-2px различии в детекции границ
диалога между кадрами (не реальный resize окна — игра не меняет размер диалогов, просто
шум детекции) `search` мог оказаться МЕНЬШЕ `template` → `cv2.error: (-215:Assertion
failed) img.size().height <= templ.size().height` — крашило весь скан, терялся весь
собранный прогресс.

**Правило:** Каждый кроп из кадра — считать координаты/размеры строго из **своего** кадра,
никогда не переиспользовать размеры другого кадра «для удобства». Плюс defensive-guard:
если после этого `search` всё равно меньше `template` — вернуть `None`/sentinel и
трактовать как временный глитч (retry), НЕ как реальный «нулевой сдвиг» (что обычно
означает «конец списка» и прерывает сбор раньше времени).

## 🔴 FULL-REPLACE ВСТАВКА БЕЗ ВАЛИДАЦИИ «ВСЕ СТРОКИ СРАЗУ» БЛОКИРУЕТ ВЕСЬ САЙВ ОДНОЙ ПЛОХОЙ СТРОКОЙ (Сундуки, кабинет)

**Что было:** `POST /web/dashboard/chests/rows` (full-replace) сначала проверяет ВСЕ
строки payload на валидность `catalog_id` (`if not in known_ids: raise 400`), и только
потом удаляет+вставляет. Если в таблице клана осталась хотя бы ОДНА строка с давно
устаревшим/мусорным `catalog_id` (с прошлых сессий, никем не почищено) — ЛЮБОЕ
сохранение ЛЮБОГО другого изменения в этой же таблице (включая совсем не связанные с
этой строкой правки) отбивается полностью, ничего не сохраняя.

**Корень:** Валидация всего батча целиком перед записью — это правильный паттерн
(fail-fast, не частичная запись), но он означает, что технический долг (неразрешённые
строки) накопленный за прошлые сессии становится БЛОКЕРОМ для любых будущих
несвязанных изменений, а не просто «висит сам по себе».

**Правило:** Неразрешённые/мусорные строки (catalog_id без реального соответствия в
каталоге) — не оставлять «на потом» бессрочно, если в той же таблице ожидаются будущие
сохранения. Либо разрешать их сразу, либо удалять мусорный alias целиком (раз нет
реального каталожного соответствия — строка просто вернётся в статус «не сопоставлено»
при следующей загрузке `GET`, это безопасно).

## 🔴 FULL-REPLACE ВСТАВКА БЕЗ ДЕДУПА ПО УНИКАЛЬНОМУ КЛЮЧУ, КОГДА НЕСКОЛЬКО ВХОДНЫХ СТРОК ССЫЛАЮТСЯ НА ОДНУ СУЩНОСТЬ (Сундуки, кабинет)

**Что было:** `_collector_rows` (GET) рисует одну строку таблицы на каждый
`ChestTypeAlias` (raw_type→catalog_id) — это правильно, два разных сырых OCR-текста
МОГУТ легитимно вести на один официальный сундук (напр. «Exan» и «Ёкай» оба → Yogwai).
Но `post_dashboard_rows` (POST, full-replace) при сохранении создавал ОДНУ
`ChestConfiguration` НА КАЖДУЮ СТРОКУ payload, не на каждый уникальный `catalog_id` —
вторая строка с тем же `catalog_id` нарушала `UniqueConstraint(collector_id, catalog_id)`
и весь сейв падал с 500 (`IntegrityError`).

**Корень:** Модель данных асимметрична: `ChestTypeAlias` — много-к-одному (много сырых
имён → один сундук), `ChestConfiguration` — один-к-одному (одна настройка очков на
сундук). Код записи писался по образу одной таблицы (один insert на строку), не
учитывая, что вторая таблица имеет другую кардинальность относительно тех же входных
строк.

**Правило:** При full-replace записи в ДВЕ таблицы из ОДНОГО списка строк, где у таблиц
разная кардинальность относительно общего поля (`catalog_id`) — дедуплицировать вставку
по этому полю явно (`seen_catalog_ids` set), не предполагать «одна строка = одна запись»
для обеих таблиц одновременно. Поймать это можно было раньше: тест на сценарий «два
разных raw_type, один catalog_id» не был написан ни в Фазе 4, ни в Спеке 1 («Считать в
квоту»), хотя сама возможность такого many-to-one была заложена в архитектуре с самого
начала (`_collector_rows` уже поддерживает это на чтении — несколько строк с одним
`catalog_id` рендерятся корректно).

## 🔴 РЕГИСТРОЗАВИСИМЫЙ МАТЧИНГ ТЕНАНТА ПО OCR/ВВОДНОМУ ТЕКСТУ (Сундуки)

**Что было:** `_get_or_create_collector` в `server/chests.py` искал существующий
`ChestCollector` точным сравнением строк `kingdom == kingdom AND clan == clan`. Клан
229/BERS попал на сервер в разных импортах с регистром «BERS» и «Bers» (источник —
вероятно вариативность того, как игра рендерит тег клана) → создались ДВА разных
коллектора, данные раздвоились (2981 сундук ушли не туда), на `/dashboard/chests`
показывались две идентичные карточки. Обнаружено не тестами, а владельцем визуально
(скриншот дубля), почти месяц после первого расхождения.

**Корень:** Любой ключ тенант-изоляции, построенный из текста, который ПРИШЁЛ ОТ

написания, которые человек не считает «разными значениями», но точное сравнение строк

символы).

**Правило:** При построении тенант-ключа из ЛЮБОГО внешнего текста (не из БД, не из
своего же slug/id) — сравнивать через `func.lower(...)`, не точным равенством,
ЗАРАНЕЕ, не дожидаясь живого дубля. Если дубль уже случился — мерджить данные вручную
SQL-транзакцией (move chests → delete loser), не просто фиксить код вперёд.

## 🔴 ПРЕФИКС НОВОГО РОУТЕРА СКОПИРОВАН С НЕПОДХОДЯЩЕГО ФАЙЛА (Сундуки Фаза 4)

**Что было:** Новый `server/chest_dashboard.py` (user-facing, для личного кабинета) был
зарегистрирован с префиксом `/api/v1/web/dashboard/chests` — по аналогии с bot-facing
роутерами (`chests.py`, `chest_aliases.py`, у которых `/api/v1/chests` — это конвенция ДЛЯ
БОТА). Но все остальные user-facing `/web/...` эндпоинты (`web_routes.py`) живут на голом

совпадало с реальным путём — каждый запрос 404-ился молча (без try/catch в `refresh()`),
страница кабинета вечно показывала «...» как если бы грузилась, без единой видимой ошибки.

не заметил, потому что каждый проверял соответствие фронтенда КОДУ бэкенда, а не реальному

**Корень:** В проекте ДВЕ разные конвенции префиксов в одном `main.py` (`/api/v1/...` для
бота, голый `/web/...` для сайта), и при добавлении нового user-facing роутера выбран
неправильный сосед для копирования.

**Правило:** При добавлении нового эндпоинта — сверять префикс с СОСЕДНИМ файлом ТОЙ ЖЕ
аудитории (bot-facing → `chests.py`/`/api/v1/chests`; user-facing/сайт →
`web_routes.py`/голый `/web`), не с любым существующим роутером. При ревью фронтенд↔бэкенд
интеграции — явно складывать `BASE + frontend_path` и `router_prefix + route_path` в одну
строку и сравнивать буквально, а не визуально "похоже совпадает".

## 🔴 OCR-REGEX ДЛЯ СТАБИЛЬНОГО UI-ЛЕЙБЛА — НЕ ПОКРЫВАЕТ ВСЕ ВАРИАНТЫ РЕНДЕРА (Хангоф #98)

**Что было:** Для отделения имени отправителя от лейбла «От:» в строке использовался regex `[OО0]т\s*[:;]\s*(.+)` (кириллица «т» + двоеточие/точка с запятой). На живом тесте OCR выдавал лейбл по-разному в зависимости от кадра: «От:», «От.», «Ot:», «Or:» — ни один фиксированный regex не покрывал все варианты, ~50% строк оставались с мусором («р От. Sarmat» вместо «Sarmat»).

**Корень:** Пытались бороться с нестабильностью OCR на уровне постобработки текста (regex), а не на уровне геометрии кропа. Если диалог имеет ВСЕГДА одинаковый рендер/композицию (статичный UI, не скроллится, не меняет раскладку) — сам лейбл «От:»/«Источник:» можно физически НЕ включать в OCR-кроп, тогда не нужен никакой regex для его отделения.

**Правильное решение (предложено пользователем, не Gemini и не Claude):** Найти точный пиксельный прямоугольник ТОЛЬКО значения (без лейбла) через живую утилиту-лупу (`coord_picker.py`), перевести в reference-координаты 1920×1080, читать через `coord_manager.to_region_dialog()` — привязка к профилю калибровки. OCR на чистом кропе не требует никакой постобработки regex для отделения лейбла.

**Правило:** Если UI-элемент статичен (не скроллится, фиксированная композиция) — для отделения значения от лейбла использовать ТОЛЬКО геометрию (узкий кроп без лейбла), а не regex/эвристики на распознанном тексте. Regex-постобработка OCR — последнее средство, не первое, и только когда геометрический кроп объективно невозможен (см. для контраста: clan_roster_reader.py, где сепаратор между карточками реально варьируется и геометрия НЕ работает — там regex обязателен).

## 🔴🔴 HSV-ДЕТЕКЦИЯ ПАНЕЛИ В КЛАНЕ — ЗАПРЕЩЕНА НАВСЕГДА (Хангоф #96)

## ⛔ ФИКСИРОВАННЫЙ ПОРОГ БИНАРИЗАЦИИ ДЛЯ OCR ИМЁН — ТЕРЯЕТ ТЕКСТ НА ~37% СТРОК (Хангоф #94)

**Симптом:** `cv2.threshold(gray, FIXED_VALUE, 255, cv2.THRESH_BINARY)` перед OCR имени — Tesseract возвращает `''` на части строк (визуально текст читаемый), независимо от количества перебираемых фиксированных порогов (150/180/130/200 — все пустые).

**Причина:** Разный фон строк (zebra-striping таблицы) — один и тот же порог делает изображение полностью чёрным/белым для части строк, текст пропадает целиком.

**Правило:** `cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY + cv2.THRESH_OTSU)` (+ `THRESH_BINARY_INV` вариант) — Otsu подбирает порог индивидуально под ROI. Дополнительно: `psm=7` (одна строка) возвращает `''`, если ROI захватывает 2 строки текста — добавить `psm=6` (блок) и взять первую строку результата. Лучшая стратегия — несколько кандидатов `(psm, invert)`, чистка regex, выбор самого длинного валидного.

**Применимо к:** `tournament_reader.py::ocr_name` (Фаза 2, готово и живо-протестировано — см. `project_tournament_reader_spec.md`), будущий OCR в Фазе 0 (имена/могущество/статус участников клана).

## ⛔ `cv2.absdiff(...).mean()` ДЛЯ ДЕТЕКЦИИ ЛОКАЛЬНОГО ИЗМЕНЕНИЯ — РАЗМЫВАЕТСЯ НА БОЛЬШОМ ROI (Хангоф #93)

**Симптом:** Функция вида `is_end_of_list` / "кадр изменился?" на основе `cv2.absdiff(prev, curr).mean() < THRESHOLD` не реагирует на реальное изменение контента (например, скролл списка), хотя визуально кадры разные.

**Причина:** `.mean()` усредняет diff по ВСЕМ пикселям ROI. Если ROI большой (например, 439×727×3 ≈ 957K элементов), а изменилась только небольшая область (например, 10×10px с diff=150), средний diff = `(10*10*3*150) / 957459 ≈ 0.047` — тонет ниже любого разумного порога (например, 2.0).

**Правило:** Для детекции «изменился ли контент в ROI» (конец списка, новый кадр после скролла) использовать `cv2.absdiff(prev, curr).max() < THRESHOLD`, не `.mean()`. `.max()` чувствителен к любому единичному изменению пикселя — корректно для статичных диалогов (raw-кадры `mss`, без JPEG-шума). Для raw-кадров `.max() == 0` означает побитово идентичные кадры.

**⚠️ Не провалидировано на живом скролле** — `END_DIFF_THRESHOLD=2.0` подобран только под синтетический тест (`np.full` + ручной diff=150), не под реальные кадры `Турнир.png`. Перед использованием в Фазе 0 (`ScrollableListScanner`) — живой тест: сравнить `.max()` между двумя кадрами БЕЗ скролла (должно быть ~0) и С реальным скроллом (должно быть >> 2.0).

**Применимо к:** будущий `ScrollableListScanner` (Фаза 0). `tournament_reader.py` с тех пор переписан на pixel-shift навигацию (`measure_scroll_shift`/`END_OF_LIST_ZERO_SHIFTS`) — `is_end_of_list`/`.mean()` в Фазе 2 больше не используется.

## ⛔ React `muted` атрибут — переключать только через ref, не state (Хангоф #89)

**Проблема:** `<video muted={isMuted}>` — React не синхронизирует атрибут `muted` после initial render. Это известный баг React: `muted` устанавливается только один раз при маунте, дальнейшие изменения через state игнорируются.
**Симптом:** Кнопка звука меняет иконку в UI, но видео не реагирует (остаётся muted или unmuted).
**Решение:**
```jsx
const videoRef = useRef(null)
const [isMuted, setIsMuted] = useState(true)  // только для кнопки UI

function toggleSound() {
  if (!videoRef.current) return
  videoRef.current.muted = !videoRef.current.muted  // прямая мутация DOM
  setIsMuted(videoRef.current.muted)
}
// <video ref={videoRef} muted ...>  ← initial state, потом только через ref
```
**Правило:** Для video/audio элементов React `muted`, `volume`, `currentTime` — всегда через `ref.current.property = value`. Никогда через state → prop.

## ⛔ DAEMON THREAD ДЛЯ YOLO-БЛОКА — RACE CONDITION ПРИ СТОП→СТАРТ (v1.5.5)

## 🔴 CSS: `overflow-x: auto` молча превращает элемент в скролл-ловушку для `position: sticky` (Сундуки, публичная таблица)

**Что было:** Заголовок публичной таблицы сундуков не прилипал к окну браузера при скролле
страницы. Причина — `.public-table-wrap { overflow-x: auto; }` (нужен для горизонтального
скролла широкой таблицы). По спецификации CSS, если задать `overflow-x` отличным от `visible`,
браузер автоматически вычисляет `overflow-y` как `auto` тоже — это превращает элемент в
полноценный скролл-контейнер, который становится "containing block" для `position: sticky`
у ЛЮБЫХ потомков (включая `<thead>` с `position: sticky; top: 0`). Раз контейнер сам никогда
не скроллится вертикально (высота не ограничена), `sticky`-потомок "прилипает" к точке (0,0)
этого статичного контейнера и визуально просто едет вместе со страницей — эффекта фиксации нет.

**Фикс v1 (2026-06-22, рабочий, но не то что хотел владелец):** дать обёртке явную
`max-height` + `overflow-y: auto` — превращает её в полноценное окошко с собственным
вертикальным скроллом, внутри которого `sticky`-заголовок действительно работает. Цена —
таблица ограничена высотой окна (не «вся страница», а внутренний скролл в рамке).

**Попытка v2 (2026-06-23, технически рабочая, отклонена владельцем по визуалу):**
разделить `<thead>` и `<tbody>` на ДВА отдельных `<table>` — шапку в `position: sticky`
БЕЗ собственного `overflow-x` (значит без скролл-ловушки, прилипает к реальному viewport),
горизонтальный скролл — в дочернем `div` ВНУТРИ шапки (не у самой шапки), ширины колонок
синхронизированы через JS-замер `getBoundingClientRect()` с тела таблицы. Технически
работало (sticky к viewport, бесконечная высота страницы), но владелец откатил без
уточнения причины («плохо, откатывай как было») — см. STATE.md «Задачи на следующую сессию».

**Фикс v3 (2026-06-23, ПРИНЯТО владельцем, закрыто):** правило выше оказалось неполным —
есть третий выход помимо «коробка 70vh» и «разделить на два DOM-узла». `overflow-y: clip`
(в отличие от `auto`/`hidden`/`scroll`) явно НЕ создаёт скролл-контейнер по спецификации
CSS Overflow Module — значит браузер не считает элемент с `overflow-y: clip` "containing
block" для `position: sticky` у потомков, и липкий `<thead>` ищет следующего предка up the
tree, находит вьюпорт. При этом `overflow-x: auto` на том же элементе продолжает работать
как обычно (горизонтальный скролл остаётся локальным для обёртки). Итог:
`.public-table-wrap { overflow-x: auto; overflow-y: clip; }` без `max-height` — один CSS
property, без JS-замеров, без второй таблицы, без риска разъехавшихся колонок. Коммит
`2b9edd8`. **Правило закрыто, переоткрывать не нужно** — если столкнёшься с этим узором
снова, начинай прямо с `overflow-y: clip`, а не с переразбиения DOM.

## 🔴 Время на публичной странице сундуков — `collected_at` хранится как буквальные цифры с ПК клиента, не как настоящий UTC

**Что было:** Владелец выгрузил данные в 8:54 по своим часам, публичная страница показывала
11:54 (+3ч). Причина — `Chest.collected_at = datetime.fromisoformat(item.timestamp)`
(`server/chests.py:118`) пишет наивные цифры с ПК бота напрямую в колонку
`TIMESTAMP(timezone=True)`, без реальной конвертации в UTC — Postgres просто помечает эти
цифры как "UTC" не сдвигая их. На фронте это аукается дважды: сначала `toLocaleString()`
конвертирует "08:54 как бы UTC" в локальный часовой пояс зрителя (+3ч → 11:54), а попытка
исправить через ручное `+ offsetMinutes*60000` add добавляет ещё один сдвиг сверху вместо
компенсации первого.

**Фикс (коммит `0f95716`):** не делать вообще никакой timezone-математики на фронте для
этого поля. `collected_at` — это уже литеральные цифры с ПК клиента (ровно то, что нужно
показать), поэтому парсить строкой как `formatPeriodPoint` (`isoString.split('T')` →
`datePart.split('-')` / `timePart.split(':')`), без объекта `Date` вообще. Тот же паттерн
уже применяется для `period_start`/`period_end` — теперь применён и здесь.

**Правило:** Любое поле, заполненное через `datetime.fromisoformat(<строка с клиента>)` в
этом проекте, хранит буквальные цифры клиента, а НЕ настоящий UTC-инстант, даже если
колонка объявлена `TIMESTAMP(timezone=True)`. На фронте такие поля показываются **только**
через строковый парсинг (split), никогда через `new Date(...)` + locale/offset-математику —
это гарантированно даёт ложный сдвиг.

## 🔴 OCR пустой строки как сигнал «списка нет» — Tesseract не возвращает "" на однотонном фоне

**Что было (Сундуки, кнопка «Открыть», 2026-06-23):** убрали HSV-поиск зелёной кнопки
полностью, заменили на фикс. точку + тюнинг-офсет. Стоп-условие цикла (когда список
сундуков закончился) сделали через «`chest_type` и `sender` оба пустые после OCR» —
звучало логично (в пустом диалоге нет текста), но в реальной игре бот после последнего
сундука продолжал кликать в пустоту бесконечно.

**Причина:** Tesseract на визуально пустой/однотонной области не гарантированно возвращает
`""` — он может прочитать шум текстуры фона как одиночный мусорный символ, который
переживает `clean_name()` (та функция чистит только хвостовые цифры/тег, не произвольный
шум). Поэтому `if not chest_type and not sender` практически никогда не срабатывает.

**Фикс:** вернули HSV-поиск кнопки, но **только как presence-сигнал** («есть ли кнопка
такого цвета в регионе» — да/нет, позиция из результата игнорируется). Сам клик всё равно
идёт по калиброванной точке + тюнинг-офсету — играют вместе: HSV решает «продолжать ли
цикл», тюнинг решает «куда кликать». Коммит `e3ff778`.

**Правило:** Не использовать «OCR вернул пустую строку» как надёжный сигнал «здесь нет
текста/контента». OCR-движки заточены на распознавание текста, а не на надёжное молчание
при его отсутствии — на чистом/однотонном фоне они могут выдать произвольный мусор. Для
сигнала присутствия/отсутствия контента — цветовая/контурная проверка (HSV) или анализ
дисперсии пикселей надёжнее, чем интерпретация результата OCR.

## 🔴 Фоновый asyncio-цикл без try/except на итерацию — одна ошибка убивает цикл навсегда

**Что было (chest_history.py, архивация сезонов, 2026-06-23):** `run_archive_tick` обходил
всех клановых коллекторов в одном `for`, без `try/except` вокруг обработки одного коллектора,
с единственным `db.commit()` в конце всего цикла. Финальное ревью перед деплоем нашло: один
"плохой" коллектор (без `period_start`, но с `period_end` — достижимо вручную через
существующий PATCH-эндпоинт) кидал `TypeError` внутри обработки, необработанное исключение
вылетало из `asyncio.create_task`-обёртки и **навсегда** убивало фоновый цикл для ВСЕХ
кланов — без видимой ошибки владельцу, тихо.

**Фикс:** `try/except Exception` вокруг обработки каждого элемента внутри цикла +
`logger.exception(...)`, и `db.commit()` переехал **внутрь** цикла (после каждого успешного
элемента), а не один раз в конце — чтобы сбой одного элемента не откатывал уже успешно
обработанные другие. Коммит `0939beb`.

**Правило:** Любой `while True: ... for item in items: ...` фоновый цикл (по аналогии с уже
существующим `_cleanup_loop` в `roy.py`) ОБЯЗАН оборачивать обработку каждого `item` в
собственный `try/except` с логированием, и коммитить per-item, а не одним батчем на весь
проход. Иначе один "плохой" элемент в любой момент тихо останавливает цикл навсегда для всех
остальных — обнаруживается только когда кто-то заметит, что фича перестала работать.

**Правило:** для любого «массового» действия (bulk sync/populate/import) явно спросить:
additive (только добавляет) или replace/mirror (приводит к точному соответствию, удаляя
лишнее)? Не выбирать «безопасный» вариант по умолчанию — «безопасно» и «то, что нужно
владельцу» не одно и то же, и разница выясняется только на живых данных. Если действие
потенциально деструктивно (replace) — сразу проектировать двухшаговое подтверждение в UI,
не добавлять его отдельным патчем после жалобы.

## 🔴 Мёртвый feature-флаг без GUI-переключателя → тихий источник крашей (Склепы, отслеживание масла)

**Что было (обнаружено 2026-07-02):** `crypt_hunter.py` содержал полноценную реализацию
проверки уровня масла (`_check_oil_level`, `_read_oil_panel`, `_check_oil_dialog` и т.д.),
но `oil_check_enabled` был жёстко `False` и принудительно сбрасывался в `main.py` перед
каждым запуском охоты — включить через интерфейс было physически невозможно. Плюс
неиспользуемый перевод `add_oil` на всех 19 языков. Один из путей внутри мёртвого кода
(`_oil_screen_region`) даже содержал необъявленную переменную `REF_B` — баг, который
никогда не всплывал именно потому что код был недостижим. Владелец охарактеризовал это
как «костыль на костыле» и попросил вычистить целиком.

**Правило:** если фича выключена флагом без пути её включить из GUI/конфига — это не
«выключенная фича», это мёртвый код, который создаёт риск (баги внутри недостижимых веток
никогда не ловятся тестами реальных сценариев) и путаницу для будущих правок. Планово
удалять целиком (код + тесты + переводы), а не оставлять «на всякий случай» с флагом
`False`. См. также git-коммит `e1f066b` (2026-05-11) — тот же паттерн уже применялся раньше
для template-matching в этом же файле (`_TEMPLATE_AVAILABLE`), тесты после того сноса не
почистили — ещё один урок: **удаление фичи из прод-кода обязано в том же коммите удалить
тесты, которые её проверяли**, иначе тестовый файл начинает врать о реальном покрытии.

## 🔴 Хардкод версии в print/debug-строках расходится с `version.py` за несколько релизов

и накопилось. Перед сборкой релиза стоит `grep -rn '\[TH v' --include="*.py"` на предмет
новых хардкодов.

## 🔴 Два теста с одинаковым именем в одном классе — второй молча убивает первый

**Что было (обнаружено 2026-07-02, `test_crypt_hunter.py`):**
`TestSendCaptainVerification` содержал два метода `def test_returns_true_always(self):` —
один тестировал `_send_captain`, другой `_click_captain_event`. Python class body — это
обычный namespace: второе определение молча перезаписывает первое как атрибут класса,
pytest никогда не видел и не запускал первый тест. Итог: `_send_captain` был без реального
теста несколько релизов, никто не заметил, т.к. `pytest` не предупреждает о дублирующихся
именах методов.

**Правило:** каждое имя теста в файле должно быть уникальным и описывать конкретное
поведение (`test_send_captain_returns_true_always`, не generic
`test_returns_true_always`) — особенно в классах с несколькими методами под тест.
Периодически стоит проверять `grep -n "def test_" file.py | sort | uniq -d` на дубли имён.

## 🔴 FASTAPI — СТАТИЧЕСКИЙ ПУТЬ ДОЛЖЕН БЫТЬ ЗАРЕГИСТРИРОВАН ДО ДИНАМИЧЕСКОГО С ТЕМ ЖЕ ПРЕФИКСОМ

динамический сегмент — регистрировать в файле СТРОГО ДО него (физически раньше по коду).
Проверять при ревью явным сравнением номеров строк `@router.<method>` декораторов.

## 🔴 NATIVE EnterWorktree ПАДАЕТ С EEXIST — ЕСТЬ FALLBACK

## 🔴 ПЛАН/СПЕКА ДОЛЖНЫ БЫТЬ ЗАКОММИЧЕНЫ НА MAIN *ДО* СОЗДАНИЯ WORKTREE-ВЕТКИ

**Что было:** Написал implementation plan (`docs/superpowers/plans/...`) в `main`, но забыл
`git add`+`commit` перед `git worktree add .worktrees/<name> -b <branch>`. Новая ветка branch
из HEAD `main` — файл плана остался только в untracked working tree основного checkout,
внутри worktree его физически нет. `scripts/task-brief` немедленно упал: `no such plan file`.

**Правило:** Порядок всегда: (1) написать спеку/план → (2) `git add` + `git commit` на
`main` → (3) только потом `git worktree add`/`EnterWorktree`. Если всё же забыл — не
пересоздавать worktree, а закоммитить на main постфактум и `git cherry-pick <sha>` в уже
существующий worktree (быстрее, не теряет уже сделанную работу в нём).
